## 一份术语表，全系统只此一份

```text
ch10 权威归并术语表:全系统唯一一份,17 类主题类目。
数据处理、预标、训练、推理、评测、前端全部 import 这里,不许各自抄一份。
类目名与边界说明采用课程 README 归并术语表原文;元组顺序即 label id,训练/推理共用。
severity 是容错档位:归错会带偏补知识优先级的类目从严。
```

这段话值得开篇就摆出来。ML 流水线最常见也最难查的一类 bug，就是标签表在几个地方各抄了一份，然后 label id 对不上：训练时「退换货」是 0，推理时是 3，模型没错、代码没报错，出来的结论全是错的。

### TopicClass

```python
@dataclass(frozen=True)
class TopicClass:
    name: str
    boundary: str                 # 一句边界说明:什么算这一类,近邻类目靠它划开
    examples: tuple[str, ...]     # 用户的说法示例
    severity: str                 # 容错档位:严 / 中 / 宽
```

一个类目带四样东西，其中 `boundary` 最容易被当成注释掠过：

```python
    TopicClass("退换货", "退货、换货、退款怎么办;修归保修维修,退归这里",
               ("退货", "退款", "退钱", "想退了", "七天无理由还能退不"), "严"),
```

```python
    TopicClass("运费", "运费谁出、运费险理赔;管的是钱,货走到哪了归物流",
               ("包邮吗", "退货运费谁承担", "运费险怎么赔"), "中"),
```

「修归保修维修，退归这里」「管的是钱，货走到哪了归物流」，这两句话在给近邻类目划界。没有它们，人工标注的两个人会标出两套结果，预标的模型也会在退换货和保修维修之间反复摇摆，最后训出来的分类器在这条边界上永远学不明白。

类目定义的质量直接决定数据质量的上限，而 `boundary` 就是质量的载体。

`severity` 是容错档位。归错「退换货」会直接带偏补知识的优先级，所以从严。归错「评价」影响不大，可以宽。

### 派生常量

```python
TOPIC_NAMES: tuple[str, ...] = tuple(c.name for c in TOPIC_CLASSES)
LABEL2ID: dict[str, int] = {name: i for i, name in enumerate(TOPIC_NAMES)}
ID2LABEL: dict[int, str] = {i: name for i, name in enumerate(TOPIC_NAMES)}
NUM_CLASSES = len(TOPIC_CLASSES)
SEVERITY: dict[str, str] = {c.name: c.severity for c in TOPIC_CLASSES}
```

全部由那个元组派生，一个字不手写。手写一份映射表，就等于给「改了类目忘了改映射」留了个坑。而这个坑不会报错，只会让预测悄悄错位。

```python
def terminology_table() -> str:
    """预标/造数 prompt 用的术语表文本:类目:边界说明(示例)。"""
    return "\n".join(
        f"- {c.name}:{c.boundary}(示例:{'、'.join(c.examples)})" for c in TOPIC_CLASSES
    )
```

预标和造数的 prompt 直接拿这个函数拼。于是 prompt 里给模型看的类目描述，跟代码里定义的永远是同一份。手抄一份进 prompt 的话，改了 `boundary` 而忘了改 prompt，标注标准就跟代码里写的对不上了。

### prelabel

预标的 prompt 直接拿前面那个 `terminology_table()` 拼出来，标注标准和代码里的类目定义永远是同一份：

```text
标注铁律:
1. 字面提到几个诉求就打几个标签,一个不多一个不少。「买大了想退」→ 尺码+退换货;\
「这鞋买大了一码」→ 只标尺码,不许因为「可能要退」就脑补退换货。
2. 近邻边界:修归保修维修、退归退换货;运费管钱、物流管货;价保是补差价、优惠活动是券和满减。
3. 方言、口语、错别字要看穿字面认诉求:「俺买的那玩意儿咋还没到俺这疙瘩」是物流;「退活」是「退货」的错字。
4. 都对不上就标「其他」;标签必须取术语表的类目名原文。
```

第一条治的是模型最爱犯的毛病：脑补。「这鞋买大了一码」它会顺手加一个退换货标签，理由是「买大了多半要退」。这一推理放在客服场景里很合理，放在标注里就是给数据掺假，训出来的模型会把尺码和退换货绑死。

第三条对应的是真实用户的说话方式，方言和错别字都得看穿字面认诉求。

```python
    except Exception as e:
        # 失败要看得见:无声标「其他」会污染语料,还会把黄金样例闸的通过率无声拉低
        print(f"[prelabel] 调用失败,兜底标「其他」: {text[:30]}… ({type(e).__name__}: {e})")
        return ["其他"]
    labels = [lb for lb in r.labels if lb in LABEL2ID]
    return labels or ["其他"]
```

失败兜底标「其他」，但要打印出来。不打印的话，上游抖动一批，一批样本悄悄变成「其他」，语料被污染了却没人知道，后面看到「其他」类特别大还会以为是数据本身的分布。

`lb in LABEL2ID` 那道过滤跟第 5 章意图分类器里那道是同一件事：模型给的标签名可能不在术语表里，schema 约束不了它编一个近似的类目名出来。

### split\_dataset

```python
def split_dataset(samples: list[dict], seed: int = 42) -> tuple[list, list, list]:
    """80/10/10 分层划分:按标签组合分层;组合样本 <10 条的并进其 label id 最小
    标签的单标签层,保证小类目不至于在验证/测试里绝迹。层内 <3 条全给训练集。"""
    rng = random.Random(seed)
```

多标签的分层比单标签麻烦。分层的单位是「标签组合」而不是单个标签，「退换货 + 运费」和「退换货」是两个不同的层。

问题是组合的种类会很多，有些组合总共就三五条。全按组合分层的话，某个小组合在验证集里一条都没有，评估时看不出模型在那种情况下的表现。所以样本少于 10 条的组合并进「它的最小 label id 那个标签的单标签层」，跟着大部队一起分。层内不到 3 条的干脆全给训练集，验证集里放一条孤样本没有统计意义。

`seed=42` 固定死。数据划分不可复现的话，今天训出来 0.86、明天 0.84，你分不清是改动生效了还是划分抖了。

### 增强只扩训练集

```text
ch10 数据集:分层划分 80/10/10 + 训练集增强(同义词替换/句式微调)。
增强只扩训练集——验证/测试是考题,不许照练习题变。运行:make ch10-dataset(需聊天上游)。
```

这句「验证/测试是考题，不许照练习题变」是本章最重要的一条纪律。

增强的做法是拿模型把一句话改写成同义变体。要是先增强再划分，同一句话的原句和变体会被分到训练集和测试集两边，模型在训练时见过那句话的孪生兄弟，测试分数自然虚高。线上一跑就现原形，而且你完全不知道为什么。

这类数据泄漏的特点是不报错、分数还好看，属于最坏的一种 bug。

```python
            except Exception as e:
                print(f"[augment] 改写失败,丢弃该变体: {s['text'][:30]}… ({type(e).__name__})")
                return None
```

改写失败就丢掉这个变体，不重试也不拿原句凑数。拿原句凑数等于往训练集里塞重复样本，模型会在那一条上过拟合。

## 训练

### 多标签怎么训

```python
def encode(samples: list[dict], tokenizer) -> list[dict]:
    enc = tokenizer([s["text"] for s in samples], truncation=True,
                    padding="max_length", max_length=128)
    items = []
    for i, s in enumerate(samples):
        vec = [0.0] * NUM_CLASSES                 # float 向量:BCEWithLogitsLoss 要求
        for lb in s["labels"]:
            vec[LABEL2ID[lb]] = 1.0
```

一条问题可以同时属于「退换货」和「运费」，比如「退货运费谁承担」。所以标签不是一个 id，是一个 17 维的 0/1 向量。

`vec` 用浮点不用整数，`BCEWithLogitsLoss` 要求标签和 logits 同为浮点。填整数会在计算损失时报类型错误，这个错误信息不太好读。

```python
    model = AutoModelForSequenceClassification.from_pretrained(
        BASE, num_labels=NUM_CLASSES, problem_type="multi_label_classification",
        id2label=ID2LABEL, label2id=LABEL2ID)
```

`problem_type` 指定成多标签，HF 会自动换成 `BCEWithLogitsLoss`。不指定的话默认按多分类走 `CrossEntropyLoss`，那个损失函数假设标签互斥，训出来的模型每条只会给一个类。

```python
def compute_metrics(eval_pred):
    logits, labels = eval_pred
    preds = (1 / (1 + np.exp(-logits)) >= 0.5).astype(int)
    return {"micro_f1": f1_score(labels, preds, average="micro", zero_division=0),
            "macro_f1": f1_score(labels, preds, average="macro", zero_division=0)}
```

评估也得按多标签的口径：sigmoid 之后逐位比阈值，不是 softmax 取 argmax。micro 和 macro 两个 F1 都算，前者看整体、后者看小类目有没有被淹没。

### BestInMemory

```python
class BestInMemory(TrainerCallback):
    """最优权重快照进内存,全程零磁盘 checkpoint。
    本机磁盘只剩几百 MB:Trainer 的 save/rotate 峰值要 2-3 份权重(实测两次撞满盘),
    改为 on_evaluate 时把更优的 state_dict 复制到 CPU 内存,训练完回填、只落一次盘。"""

    def __init__(self, model):
        self.model = model
        self.best_metric = -1.0
        self.best_state = None

    def on_evaluate(self, args, state, control, metrics=None, **kwargs):
        score = (metrics or {}).get("eval_micro_f1", -1.0)
        if score > self.best_metric:
            self.best_metric = score
            self.best_state = {k: v.detach().to("cpu", copy=True)
                               for k, v in self.model.state_dict().items()}
```

标准做法是 `load_best_model_at_end=True`，让 Trainer 每个 epoch 存一份 checkpoint、结束时加载最好的那份。问题是存 checkpoint 的峰值要两三份权重的空间，写新的时候旧的还没删。本机磁盘只剩几百 MB，实测撞满了两次。

改成 `save_strategy="no"` 一份都不存，评估时把更优的 `state_dict` 复制到 CPU 内存，训练完回填、只落一次盘。

`.to("cpu", copy=True)` 那个 `copy=True` 不能省。不复制的话拿到的是同一块显存/内存的引用，下一步训练一更新参数，你手里这份「最优权重」就跟着变了，等于什么都没存。

### 阈值也在这里定

```python
    logits = trainer.predict(val_ds).predictions
    probs = 1 / (1 + np.exp(-logits))
    gold = np.array([d["labels"] for d in val_ds])
    best_t, best_f1 = 0.5, -1.0
    for t in np.arange(0.30, 0.71, 0.05):
        f1 = f1_score(gold, (probs >= t).astype(int), average="micro", zero_division=0)
        if f1 > best_f1:
            best_t, best_f1 = round(float(t), 2), float(f1)
```

多标签的判定阈值不该拍 0.5。最优阈值跟类别不平衡程度、跟训练轮数都有关，0.5 只是个没有依据的默认值。训完在验证集上扫一遍，取 micro-F1 最高的那条线。

```python
    (OUT / "threshold.json").write_text(
        json.dumps({"threshold": best_t, "val_micro_f1": best_f1}))
```

阈值跟模型一起存。后面导出、服务、评测三处都读这个文件，不各自写死一个数。

这跟上一章那个置信度阈值校准是同一套方法论：阈值靠数据定，定完存下来，全链路读同一份。

## 导出与上线

```text
ch10 推理服务:ONNX + FastAPI 独立进程 :8110,轻运行时(onnxruntime + tokenizers,不背 torch)。
```

推理服务只需要跑图和分词，不需要自动求导、不需要优化器、不需要 CUDA 那一整套。导成 ONNX 之后依赖从 torch 加 transformers 缩到 `onnxruntime` 加 `tokenizers`，镜像和常驻内存都小一大截。

### export\_onnx

```python
class LogitsWrapper(torch.nn.Module):
    """HF 模型输出是 ModelOutput dict,导出前包一层只回 logits 张量。"""

    def __init__(self, model):
        super().__init__()
        self.model = model

    def forward(self, input_ids, attention_mask, token_type_ids):
        return self.model(input_ids=input_ids, attention_mask=attention_mask,
                          token_type_ids=token_type_ids).logits
```

HF 模型返回的是一个 `ModelOutput` 结构体，ONNX 只认张量，所以包一层把 `.logits` 取出来。

```python
    torch.onnx.export(
        wrapper,
        (sample["input_ids"], sample["attention_mask"], sample["token_type_ids"]),
        str(OUT / "model.onnx"),
        input_names=["input_ids", "attention_mask", "token_type_ids"],
        output_names=["logits"],
        dynamic_axes={"input_ids": dyn, "attention_mask": dyn,
                      "token_type_ids": dyn, "logits": {0: "batch"}},
        dynamo=False,
        opset_version=17,
    )
```

`dynamic_axes` 把 batch 和序列长度声明成动态。不声明的话，导出来的图只吃导出时那个样本的形状，线上来一条长度不同的句子就报错。

`dynamo=False` 那行是版本适配。新版 torch 的 `export` 默认走 dynamo 路线，导 HF 模型时问题不少，显式退回 TorchScript 导出器加 `dynamic_axes` 这条稳定路线。

### 参照模型必须重新加载

```python
    # 一致性校验:测试集全量,ONNX 与 torch 的过线标签必须完全一致。
    # 参照模型必须重新加载:tracing 会把 transformers v5 masking_utils 的分支
    # 打成常量、污染进程内已有模型(实测被污染的参照 logits 差到 1.88,而文件本身没问题)
    ref = AutoModelForSequenceClassification.from_pretrained(MODEL_DIR)
    ref.eval()
```

这个坑值得单独记住。

导出过程会对模型做 tracing，而 tracing 会把 transformers 内部那些依赖输入的分支按当次的取值打成常量。副作用是**进程内那个模型对象被改坏了**。你接着拿它当对照组去比对 ONNX 的输出，logits 能差出 1.88，然后得出「ONNX 导错了」的结论。

实际上导出的文件完全没问题，坏的是你手里的对照组。

解法是重新 `from_pretrained` 一个干净的参照模型。这类 bug 的欺骗性在于，所有证据都指向被冤枉的那一方。

```python
            t_pred = (1 / (1 + np.exp(-t_logits)) >= threshold)
            o_pred = (1 / (1 + np.exp(-o_logits)) >= threshold)
            mismatch += int((t_pred != o_pred).any(axis=1).sum())
```

校验的判据是「过线标签完全一致」，不是 logits 逐位相等。浮点运算在两套运行时之间必然有微小差异，`allclose` 给了容差，但业务结论不能变：同一条输入，两边打出来的标签集合必须一模一样。

```python
def _write_report(checked: int, mismatch: int) -> None:
    """一致性校验的结论落盘;失败也写,验收页要能看见「上次导出没过」而不是一片空白。"""
```

失败也写报告。验收页上「上次导出没过，3 条不一致」远比一片空白有用，后者你分不清是没跑过还是跑挂了。

### apply\_threshold

```python
"""ch10 推理纯函数:阈值应用与空标签兜底。evaluate 与 serve 共用,行为不许分叉。
轻依赖(仅 numpy),serve 的 ONNX 轻运行时可安全 import。"""
import numpy as np


def apply_threshold(probs: np.ndarray, threshold: float) -> np.ndarray:
    """sigmoid 概率 → 0/1 多标签矩阵:过线即命中;某行全不过线取最高分兜底,不产出空标签。"""
    preds = (probs >= threshold).astype(int)
    for r in range(len(preds)):
        if preds[r].sum() == 0:
            preds[r][probs[r].argmax()] = 1
    return preds
```

十六行的一个文件，两个理由让它值得单独存在。

一是评测和服务必须共用。这几行决定了「概率怎么变成标签」，两边各写一份的话，评测那边算出来的 F1 就不代表线上的真实表现。最典型的表现是评测很好但线上一堆空结果。

二是依赖要轻。服务那边的运行时里没有 torch，这个模块只依赖 numpy，才能被安全地 import 进去。

空标签兜底那三行是业务判断。一条问题所有类目都不过线时，与其返回空，不如给最高分那个。分类器交出空结果，下游统计里这条问题就凭空消失了，而「其他」这个兜底类目本来就是为这种情况准备的。

## 阈值扫描重演

```text
重演 train.py 的阈值扫描(教学演示):验证集 161 条经 ONNX 服务打分一次,
九个候选线(0.30~0.70 步进 0.05)套同一张分数表各算一遍 micro-F1,谁高谁当选。
```

训练时已经扫过一次阈值了，这个脚本再用线上服务重演一遍。定位是教学演示：让学员看见「阈值是选出来的」这件事，而不是接受一个从天而降的数字。

「打分一次，分数表固定」是这里的关键设计。九个候选线套的是同一份打分结果，只是过线的位置不同。要是每个阈值都重新调一次服务，模型推理本身的不确定性会混进比较里，谁高谁低就说不准了。

```python
        if f1 > best_f1:                       # 严格更高才换人:0.50 与 0.45 打平时,先到的 0.45 留任
            best_t, best_f1 = t, f1
```

打平时保留先到的那个，也就是更低的阈值。这个选择本身可以商榷，重要的是它被明确写下来了。不写清楚的话，`>` 和 `>=` 一字之差，重演的结果就跟训练时选的不是同一条线，而看到的人会以为是模型有问题。

```python

```

报告里带一个 `consistent` 字段，明确回答「重演选出来的线跟在用的那条是不是同一条」。这是整条链可复算的实证：同样的数据、同样的方法，跑两遍得到同一个结论。
