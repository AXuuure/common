晚上十一点半，客服团队下班两个小时了，店铺后台还在进消息：「这双鞋偏码吗」「昨天拍的怎么还没发货」「到手不喜欢能退不」。人要下班，问题不下班。想让机器把夜班接过去，咱们的智能客服就从这里动工。

![](<images/理论学习：LLM 接入与 Prompt 工程-01-night-message-inflow.png>)

从哪里动工呢？导读里那张系统全景图铺得挺大，RAG、工具调用、Agent 循环，看着千头万绪。其实你把随便哪个能力剥开，最里头都是同一个动作：把一段话发给大模型，等它回一段话。RAG 是发话之前先查资料，Function Calling 是发话时捎上工具清单，Agent 呢，无非把这一来一回循环着做。

![](<images/理论学习：LLM 接入与 Prompt 工程-02-llm-common-loop.png>)

这一章的任务是：把「跟大模型对话」这条通路打通，还得打得像样。什么叫像样？说得稳、说得专业，还得反应快、记得住上文。至于查订单、办退款，得等下一章 Function Calling 给它装上手脚；多步骤自主决策的 Agent 循环更靠后，后面架构章才展开。本章先安心跑通纯对话。

## 先跟大模型说上话

### 一次对话在网络上长什么样

大模型这东西听着很牛逼，接进系统的方式倒是很简单：它就是跑在某个机房里的一个服务，对外露一个 HTTP 接口。你 POST 一个 JSON 过去，它回一个 JSON 给你，跟调一个天气接口没有本质区别。这个接口如今最通行的形态，叫「Chat Completions」。

![](<images/理论学习：LLM 接入与 Prompt 工程-03-chat-http-request-response.png>)

发过去的 JSON 长什么样？给你看一次最小的调用：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system", "content": "你是喵购商城的智能客服"},
    {"role": "user", "content": "到手不喜欢能退吗？"}
  ]
}
```

核心是 `messages` 这个数组：整场对话被表示成一条条消息，每条消息标一个 `role`。`system` 是开发者塞给模型的幕后指令，用户看不见，立人设、定规矩全靠它；`user` 是用户说的话；还有一种 `assistant`，是模型自己说过的话。第一次调用里还没有 `assistant` 消息，等它回了话、下一轮把它的回话也码进数组，对话就续上了。



![](<images/理论学习：LLM 接入与 Prompt 工程-04-message-roles-chain.png>)

为什么模型自己说过的话，还要由你发回去？这个疑问先记着，本章后面讲多轮对话时一并揭开。



再看它回来的 JSON，挑重要的两块：

```json
{
  "choices": [{
    "message": {"role": "assistant", "content": "可以的，本店支持七天无理由退货……"},
    "finish_reason": "stop"
  }],
  "usage": {"prompt_tokens": 28, "completion_tokens": 45, "total_tokens": 73}
}
```

`message` 是回答本体。旁边的 `finish_reason` 标记这次生成是怎么停下来的：`stop` 是话说完了自然收尾；还有一种 `length`，是被长度上限硬掐断的，回答可能说到一半就断了，这个标记能帮你分清是正常说完还是被截断。



另一块 `usage`，是这次调用的账单。大模型的计量单位是「token」：模型读写文本之前，会先把文本切成一小段一小段的碎片，一个碎片就是一个 token。中文里可能一个字算一个 token，也可能半个词算一个，各家切法不一样，别拿字数直接换算。你发的、它回的，全都按 token 计量计费，像流量套餐，`usage` 就是这一单的流量明细。

![](<images/理论学习：LLM 接入与 Prompt 工程-05-token-billing-analogy.png>)

还有一件事，这份响应里看不出来，但特别重要：Chat Completions 是「无状态」的。服务器不替你保存任何对话，这次调用结束，它转头就把你忘了，下次调用在它眼里是全新的一单。这个设定牵出的麻烦和解法，本章后面多轮对话那节细说。

![](<images/理论学习：LLM 接入与 Prompt 工程-06-stateless-new-request.png>)

### OpenAI 协议怎么就成了普通话

刚才那套 JSON 格式，是 OpenAI 家定的。可你要接的未必是 OpenAI：国内团队用 DeepSeek、Qwen 的多，开发机上还常用 Ollama 这类工具在本地跑开源模型，图个省钱、数据不出门。难道每接一家就得学一套接口？



不用。OpenAI 把大模型 API 做成生意做得最早，Chat Completions 这套格式被全世界的应用用了个遍，后来者一合计：与其自创一套格式逼开发者重学，不如直接兼容它，大家迁移成本归零，拿来就用。于是 DeepSeek、Qwen、GLM 这些模型服务，连同 Ollama 这样的本地运行工具，全都提供 OpenAI 兼容接口。业内管这个叫「OpenAI 协议」。各家模型像各地方言，这套协议就是普通话：你跟一家学会了说话，换一家只是改个域名、换把钥匙。

![](<images/理论学习：LLM 接入与 Prompt 工程-07-openai-protocol-common-language.png>)

说是普通话，眼下其实有三套话在同时流通。先把格局摆清楚，后面你换上游、翻各家 API 文档的时候心里有底。



第一套就是刚说的「Chat Completions」，`/v1/chat/completions` 那个端点，覆盖面最广，你能想到的模型服务几乎都开着它。



第二套是 Anthropic 的「Messages 协议」，Claude 的原生形状，字段结构跟 OpenAI 那套对不上。这两年它的地盘变大了：Claude Code 这类原生说 Anthropic 协议的编程工具火起来之后，国内厂商反过来在自己服务器上也开了一套 Anthropic 兼容接口，图的是用户能直接把 Claude Code 指过去用他们家模型。智谱在 `open.bigmodel.cn/api/anthropic`、MiniMax 在 `/anthropic/v1/messages`、Kimi 在 `api.kimi.com/coding`，都能接。Messages 协议正在从「Claude 自己的方言」变成第二种普通话。



第三套是 OpenAI 2025 年推出的「Responses API」，端点是 `/v1/responses`。OpenAI 自己现在主推这个，新的推理和多模态能力会先落在它上面，Chat Completions 在官方口径里退成了兼容层，虽然明确说了短期不废弃。但它在国内的覆盖面还很薄，DeepSeek 到 2026 年 7 月底才随 V4-Flash 开出兼容端点，而且只有 flash 这一档能用。



**这门课的源码只说第一套，Chat Completions。** 一句话的理由：它是三套里唯一你换任何一家上游都大概率能接上的。这门课要让你把 `base_url` 指向 DeepSeek、指向硅基流动、指向本地 Ollama 都能跑起来，那就只能选覆盖面最广的那个。另外两套本身没什么毛病，只是这门课先不碰，以后真有需要再说。



知道有这回事就行，真要接另外两套也不难。Anthropic 协议那边，把 `base_url` 指到厂商的 anthropic 端点，客户端换成对应的 SDK。Responses API 这边更省事，LangChain 的 `ChatOpenAI` 有个 `use_responses_api` 开关，打开就走新端点。这门课都不动它们。

## 从裸调 API 到 LangChain

### 裸调能跑，撑不起一个系统

看到这里你可能手痒了：拿 `httpx` 把那个 JSON POST 出去，一晚上就能糊出一个能聊天的 demo。没错，而且我建议你真这么玩一次，对协议的体感会完全不一样。



可 demo 归 demo，离系统还差一段距离。往后走几步，麻烦不少：prompt 会越攒越多，散落在代码字符串里，改一处漏三处；模型输出要解析成结构化数据，逢用就得写一遍解析逻辑；等哪天要换模型、上流式、进编排，请求代码还得翻个底朝天，每一样都是重复劳动。

![](<images/理论学习：LLM 接入与 Prompt 工程-08-prompt-sprawl.png>)

这类大模型应用的通用零件，业界早出了现成框架，咱们课程选 LangChain。



本课钉的版本是 1.3.13，属于 LangChain 1.0 系列。1.0 是 2025 年 10 月才出的第一个稳定大版本，官方承诺 2.0 之前不做破坏性变更。



它把刚才那些东西拆成一个个标准组件，本章用到三个：`ChatOpenAI` 管调模型，`PromptTemplate` 管话术模板，「结构化输出」交给模型自带的 `with_structured_output` 方法。头一个马上讲，另外两个等本章后面 Prompt 工程那节再请出场。



![](<images/理论学习：LLM 接入与 Prompt 工程-09-langchain-three-components.png>)

### ChatOpenAI：把调模型收进一个对象

三个组件打头的是 `ChatOpenAI`，看它怎么把上一节手写的那些收拢起来：

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="deepseek-v4-flash",
    base_url="https://api.deepseek.com/v1",
    api_key="sk-xxx",
)
reply = llm.invoke("到手不喜欢能退吗？")
print(reply.content)
```

名字里带 OpenAI，认的其实是 OpenAI 协议。前面说了各家都讲这门普通话，`base_url` 指向 DeepSeek 就调 DeepSeek，指向本地 Ollama 就调本地模型。手搓 messages 数组、HTTP 收发、异常重试，这些琐碎全收进了对象里，`invoke` 进去一句话，出来一个带 `content` 的消息对象，就这么简洁。

![](<images/理论学习：LLM 接入与 Prompt 工程-10-chatopenai-wrapper.png>)

### 换模型不换代码：把上游收进配置

`base_url` 一改就能换模型，多模型这事是不是就算解决了？开发阶段算，生产系统还差一截。



你想啊，真跑起来的客服系统，模型从来不止一个：生成回答想用能力强的，后面意图识别或者数据飞轮章还可能要拿便宜的小模型压成本。API key 撒在各个服务的配置里，管理非常麻烦。再赶上 Claude 这种协议不同的，还得单独写一套接入。这些事全塞进业务代码，只会越塞越乱。



但仔细看这几件麻烦，变的都是「连谁」这件事。地址、模型名、密钥，三样都是配置。所以治它不用多绕，把这三样从代码里挪进 `.env`，代码只管读配置。



咱们这个系统要连三个上游，配置就分三组：

```bash
CHAT_BASE_URL=https://api.siliconflow.cn/v1CHAT_MODEL=deepseek-ai/DeepSeek-V4-FlashCHAT_API_KEY=sk-xxxEMBED_API_KEY=sk-xxx        # 嵌入 BAAI/bge-m3RERANK_API_KEY=sk-xxx       # 重排 BAAI/bge-reranker-v2-m3
```

为什么分三组，不共用一个。聊天、嵌入、重排是三件不同的事，各自的上游可以不一样。第 4 章你会看到重排走的根本不是 OpenAI 协议，它是 Jina 那套 `/rerank` 形状。分开配，换其中任何一个都不牵动另外两个。

换模型就是改 `CHAT_BASE_URL` 和 `CHAT_MODEL` 两行。这里有个容易踩的地方：`CHAT_MODEL` 必须写上游认的真实模型名。同一个 DeepSeek V4 Flash，在官方叫 `deepseek-v4-flash`，托管在硅基流动上叫 `deepseek-ai/DeepSeek-V4-Flash`，写错了上游会回一句 `Model does not exist`。



协议这件事前面已经摆过，三套话流通，这门课统一说 Chat Completions 那一套，换上游就是换 `base_url`，代码一行不动。



那什么时候才需要在应用和模型之间垫一层「网关」？公司里几十个应用共用一批 key，要按团队算成本、要留审计，这时候网关替你管的是账和权限，值这个复杂度。咱们这门课是一个应用连三个上游，多垫一层就是多一个进程、多一份配置、排障多一跳。

## Prompt 工程化：把话术当资产管

接入的事告一段落，该操心「说什么」了。



刚上手那几天，prompt 多半是想到哪写到哪：字符串里拼一句人设，效果不好就再补一句「请务必认真回答」。这东西上手快，失控也快：同一段人设复制了五份，政策口径一改就漏改两处；想要输出规整点，全靠在结尾大喊「请输出 JSON」。乱到一定程度你自然会想：真人客服团队是怎么管这些的？

![](<images/理论学习：LLM 接入与 Prompt 工程-13-prompt-chaos.png>)

人家有一整套家当：新人入职有培训手册，日常回复靠话术库，处理问题走工单表单。「Prompt 工程化」说白了就是把这套管理搬进代码，从临时手写升级成可维护的模板系统：培训手册对应「System Prompt」，话术库对应 PromptTemplate，往表单里填字段归 with\_structured\_output。

![](<images/理论学习：LLM 接入与 Prompt 工程-14-prompt-engineering-map.png>)

### System Prompt：立人设，更要划红线

system 消息前面露过面：数组里排第一、用户看不见的那条幕后指令。别看只是一段话，模型训练时就被教成优先遵从它，这一条等于攥在开发者手里的岗前培训。一份像样的客服 System Prompt，至少交代三层：我是谁，管什么，什么不能碰。

```text
你是「喵购商城」的智能客服小喵，语气亲切、回答简洁，不用网络烂梗。

你的职责范围：商品咨询、订单与物流查询、退换货政策解答。

必须遵守：
1. 只依据商城政策作答，拿不准就说「这边帮您转人工核实」，严禁编造；
2. 不承诺具体的退款到账时间，不对商品质量打包票；
3. 用户聊到职责之外的话题，礼貌把话拉回客服业务。
```

头一层是角色设定，定身份和语气；第二层圈定业务范围；更重要的是第三层行为约束。模型天性爱把话说圆说满，用户问「退款多久到账」，它顺口一句「24 小时内一定到账」，这承诺一出口就是一张客诉单。哪些话不能说、说到什么分寸，这类红线必须白纸黑字写进 system，别指望模型自己懂。

![](<images/理论学习：LLM 接入与 Prompt 工程-15-system-prompt-red-lines.png>)

丑话说在前头：System Prompt 说到底是在「劝」，劝得住大多数时候，劝不住的那一小撮拦不住，光靠一段 prompt 守不住生产系统。事实层面的兜底要靠检索，后面 RAG基础章节 会接手；答不准就得强制拒答，在更后面的 RAG 进阶章。本章先把该立的规矩立好，而且规矩要立在 system 里，别混在用户消息里，这一条到本章后面讲历史裁剪时，你会看到它的第二层用意。

### PromptTemplate：把话术做成模板

人设立住了，再看日常话术。客服话术天然带变量，真人团队的话术库就是这么写的：「亲，您的订单 {订单号} 已从 {仓库} 发出，预计 {日期} 送达」，固定句式加空槽，用时现填。代码里拿 f-string 也能拼，可 prompt 一多，你要的就不只是拼字符串了：模板得和业务逻辑分开存放，漏填变量当场就报错，同一份模板还能处处复用。`PromptTemplate` 干的就是这份差事，对话场景用它的消息版变体 `ChatPromptTemplate`：

![](<images/理论学习：LLM 接入与 Prompt 工程-16-prompt-template-slots.png>)

```python
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", SYSTEM_PROMPT),
    ("user", "用户问题：{question}\n\n可参考的资料：{context}"),
])
chain = prompt | llm
reply = chain.invoke({"question": "运费险怎么赔？", "context": policy_text})
```

`from_messages` 把 system、user 两段拼成一份完整的消息模板，花括号是留给变量的槽，`invoke` 时拿字典填进去；哪个槽忘了填，当场抛错，不会揣着空槽就把请求发出去。中间那根竖线是 LangChain 的组合语法，把模板和模型串成一条链，数据从左往右淌。



这里的 `"system"` 跟前面那份裸 JSON 里的 `system` 是同一个东西。LangChain 把各家的角色名对齐成了一套，模板里写 `system`，投给哪家模型都由它那层去适配。

![](<images/理论学习：LLM 接入与 Prompt 工程-17-langchain-chain-train.png>)

多说一句那个 `{context}` 槽。眼下你往里塞的是手工准备的商品说明、政策文本；等到了后面 RAG 章，检索回来的知识就是从这个槽灌给模型的。模板今天怎么写，那时候就怎么复用。

### 结构化输出：模型说人话，系统要字段

有些场合，你要的压根不是一段话。售后留言进来，系统想先把它整理成一条结构化记录：哪个商品、什么问题、用户急不急，好存库、派单、走后续流程。模型倒是乐意帮你归纳，可它吐的是自然语言：今天开头带句「好的，以下是提取结果」，明天给 JSON 裹一层 markdown 围栏，你的 `json.loads` 说崩就崩。

![](<images/理论学习：LLM 接入与 Prompt 工程-18-json-loads-fragile.png>)

这事前后两步都得稳：模型要按格式吐，吐出来的还要能校验。`llm.with_structured_output()` 直接把这两步焊进模型调用本身，你只管把想要的字段结构定义清楚：

![](<images/理论学习：LLM 接入与 Prompt 工程-19-structured-output-flow.png>)

```python
from pydantic import BaseModel, Field

class AftersaleNote(BaseModel):
    product: str = Field(description="商品名称")
    issue: str = Field(description="问题描述")
    urgent: bool = Field(description="用户是否着急")

structured_llm = llm.with_structured_output(AftersaleNote)
chain = prompt | structured_llm
```

先用 Pydantic 把想要的字段定义成数据模型，每个字段配上描述，这一步和平时定义数据结构没什么两样。`with_structured_output(AftersaleNote)` 拿着这份定义去配置模型调用：模型支持原生结构化输出的，比如 OpenAI、Claude，直接调用它们各自的原生能力，这条路最稳；换成不支持的模型，LangChain 会自动改用工具调用的方式，一样能拿到结构化结果。chain 里接的就是这个包过结构化输出能力的模型，`chain.invoke(...)` 出来的直接就是一个 `AftersaleNote` 对象，业务代码取字段就用。



老代码里常能碰到 `PydanticOutputParser` 这个类，效果类似，只是这些事全得自己干：格式说明要手动拼进 prompt，回来的文本也要自己解析校验。`with_structured_output` 把这两步收进了一步。



模型也有不听话的时候，字段类型对不上、必填字段漏填，pydantic 校验照样会报错。轻量场景加一层 `.with_retry()`，让它按原请求重试几次就够用；结构化输出在这套系统里以后到处都是，后面意图识别章让模型判断用户意图、强制吐 JSON，用的还是今天这招。

## 流式输出：别让用户盯着转圈

### 憋大招，用户等不起

拿政策类问题实测一把就有体感：一个退货政策的回答两三百字，模型要生成好几秒，接口攒到全文生成完才返回，用户那边就是好几秒的空白等待。搁在旺旺、微信这种聊天语境里，对面十几秒不吭声，用户的手指头已经摸到「转人工」按钮了。



有意思的是，模型明明是一个字一个字往外蹦的：它挑完一个 token 再挑下一个，天生就是边想边说；非流式接口只是把说完的话攒齐了才交货。「流式」要做的事说穿了就一句：别攒了，生成一个就递一个。用户看到的效果，就是聊天窗里文字逐字往外冒，跟真人客服那边显示「对方正在输入」一个感觉。



不过有一说一，流式没让模型算得更快，全文生成的总时长一分没省，省的只是「见到第一个字」的等待。别小看这省下的第一眼，人愿意看着字往外冒，不愿意对着空白转圈，体感差出一个档次。

![](<images/理论学习：LLM 接入与 Prompt 工程-20-streaming-vs-buffering.png>)

### 为什么是 SSE

模型到服务端这段好办，HTTP 分块传输原生就支持，`ChatOpenAI` 换个调用方法就能逐段收。服务端到浏览器这段怎么推，倒有三条路可选。



「轮询」，前端每隔半秒问一遍「有新字了吗」，请求满天飞、延迟还高，聊天场景基本不考虑。



「WebSocket」，全双工长连接，能推能收，游戏、协同编辑这类双向高频的场景是它的主场；



可咱们这个需求里数据方向是单向的，用户消息走普通 POST 上行，回答从服务端往下流，为一条单向流搭一套双向连接的架子，没必要websocket。



剩下的「SSE」（Server-Sent Events），是 HTTP 原生的单向推送：说穿了就是一条普通的 HTTP 响应，只是迟迟不关闭，服务端有一段写一段，浏览器还内置断线重连。

![](<images/理论学习：LLM 接入与 Prompt 工程-21-sse-vs-polling-websocket.png>)

单向流配单向推送，SSE 正合适。还有一层顺水推舟：OpenAI 协议和 Anthropic 协议自己的流式响应就是 SSE 格式，你从上游模型收到的、和你推给前端的，本来就是一路东西。真实字段藏得比较深：OpenAI 包在 `choices[0].delta.content` 里，Anthropic 走一串具名事件，靠 `event: content_block_delta` 标出每次增量。下面这份是简化示意，只留「一行一个 data:」的骨架：

```text
data: {"delta": "您"}

data: {"delta": "好"}

data: [DONE]
```

响应头标成 `text/event-stream`，正文就是一行行 `data:` 打头的消息、空行隔开，最后约定一个结束标记，前端读到就收工。格式简陋得有点可爱，但单向推字，够用了。

![](<images/理论学习：LLM 接入与 Prompt 工程-22-sse-data-conveyor.png>)

## 多轮对话：每次请求都是一位新客服

### 把聊天记录整份递过去

单轮问答到这里都顺了，连着聊立马露馅。用户问「这双鞋有 42 码吗」，答完接着问「那它多少钱」。它？模型一脸茫然。



前面协议那节埋过伏笔：Chat Completions 无状态，服务器不记对话。每次调用，你面对的都像一位刚接班的新客服，前面聊了什么他一概不知，除非你把聊天记录整份递到他手上。

![](<images/理论学习：LLM 接入与 Prompt 工程-23-new-agent-no-memory.png>)

「多轮对话」的真相就这么简单得有点意外：模型没有记忆，所谓上下文，全是调用方自己攒的。每次请求，把 system、历次的 user、历次的 assistant 按原顺序码进 `messages`，模型现场把整段通读一遍，才接得住那个「它」：

```json
[
  {"role": "system", "content": "你是喵购商城的智能客服小喵……"},
  {"role": "user", "content": "这双鞋有 42 码吗？"},
  {"role": "assistant", "content": "有的，42 码现货充足。"},
  {"role": "user", "content": "那它多少钱？"}
]
```

读到第四条时，前三条都在眼前，「它」指什么一目了然。开头留的那个疑问也顺势解开了：assistant 的话必须发回去，不发的话，模型连自己上一轮说了什么都不知道，谈何接话。工程上要做的就是把每轮问答存起来，下次请求前取出来拼数组；存哪里呢？这一步先存在内存里，进程活着就记得住，一重启就清空；更完整的管理方式，后面讲上下文管理时再细说。

### 记性不能无限长：裁剪与 token 预算

历史全量携带，聊到四五十轮会怎么样？两笔账马上找上门。



先是钱的账：每次请求都要重发全部历史，`prompt_tokens` 随轮次一路涨，聊得越久、单次越贵，费用曲线越聊越翘。



再是容量的账：模型的「上下文窗口」有硬上限，历史塞爆了，请求直接报错。何况历史里还混着大量噪声信息，垫得越厚，当前这个问题反而越容易被搅浑。

![](<images/理论学习：LLM 接入与 Prompt 工程-24-token-budget-pressure.png>)

最简的解法有两招。第一招按轮数裁：`system` 永远原样保留，历史只留最近若干轮，更早的直接扔。人设和红线可不能跟着历史一起被裁掉，前面说规矩必须立在 system 里，第二层用意就在这里兑现。



第二招按 token 预算裁：光数轮数不保险，有的轮就一句「好的」，有的轮用户贴来整页物流单，长短差得远。给历史设一个 token 预算，把各条消息的 token 数实际算一遍，超了预算就从最老的开始扔：

![](<images/理论学习：LLM 接入与 Prompt 工程-25-history-trimming.png>)

```python
def trim_history(messages: list, budget: int) -> list:
    system, history = messages[0], messages[1:]
    while history and count_tokens(system, *history) > budget:
        history = history[2:]   # 掐掉最老的一问一答
    return [system, *history]
```

这几行里有两处得留神。一是扔要成对扔，一问一答一起掐，留半截会打乱 user 和 assistant 的交替节奏，有的模型服务对消息顺序挑剔得很。二是数 token 要用模型配套的 tokenizer 实算，别拿字数瞎估，前面说过这两者换算不齐。



不过这版裁剪就是个「够用先跑」的版本，短板也要挑明：用户要是聊回二十轮之前的那个订单，被裁掉就是真忘了。更讲究的招数，滑动窗口的宽度怎么定、早期对话怎么压成摘要、怎么按当前问题去历史里做语义检索，是后面会话上下文管理的正题，到时候上下文还会挂进 LangGraph 的 State 里统一流转。本章的底线是「记得住近处的、账单不失控」，守住它就够了。

## 会聊了，然后呢

盘一盘这一章。OpenAI 协议把模型接了进来。调用、话术、结构化输出这几块，让 LangChain 三件套收拾得服服帖帖，模型想换就换，改两行配置的事。回答逐字蹦到用户眼前是 SSE 的功劳，聊上几十轮也不崩，靠的是历史裁剪兜底。一个能上岗聊天的 AI 客服，骨架算是立起来了。

![](<images/理论学习：LLM 接入与 Prompt 工程-26-chapter-summary-map.png>)

骨架归骨架，你拿真实客服问题一试，天花板立刻碰头：用户问「我昨天下的单到哪了」，它就傻眼或者乱编了。订单和物流状态在公司业务系统接口里，模型说得再漂亮，也拿不到这些数据。想让它拿到，就得教它使工具：告诉它手边有哪些工具、什么时候该开口调用哪个。这正是下一章 Function Calling 的戏份，顺带咱们还要把项目骨架和数据库真正搭起来。客服从「会聊天」到「能办事」，就差这一步了。
