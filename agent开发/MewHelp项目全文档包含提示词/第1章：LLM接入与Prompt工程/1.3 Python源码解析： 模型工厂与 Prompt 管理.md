## 配置加载

### Settings

`.env` 里的东西怎么进程序，用的是 pydantic-settings：

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    # 必填,故意不给默认值。模型名是跟着账号走的,给一个默认值等于替学员猜:猜错不会在
    # 启动时报错,而是在第一次调模型时抛一个看不懂的上游 401。没有默认值,缺了就在启动
    # 时报 chat_model Field required,直接指向 .env。调优常量(top_k、步数、阈值这些)
    # 是另一类,它们该留在代码里带默认值。
    chat_model: str
```

`env_file` 指定从哪读，`extra="ignore"` 让 `.env` 里多出来的键不至于炸掉启动，这一条很实用，因为学员的 `.env` 常常从别处抄来、带着一堆用不上的变量。

字段分两类，判据是「这东西跟着谁走」。跟着账号走的必填，不给默认值，缺了在启动那一刻就报 `Field required` 并指名道姓是哪一项。跟着代码走的调优常量给默认值，留在代码里。这个区分的价值在于把报错时机提前，配置缺失是启动时的确定性失败，而不是第一次调模型时冒出来的一个看不懂的 401。

文件末尾一行 `settings = Settings()` 做成模块级单例，全仓统一 `from app.config import settings`，不再各处重复构造。

## 模型工厂

### get\_chat\_model

```python
def get_chat_model(streaming: bool = False, model: str | None = None,
                   temperature: float | None = None) -> ChatOpenAI:
```

第 1 章真正需要的只有三样，模型名、地址、密钥，都从 `settings` 取，对应 `.env` 里 `CHAT_` 那一组。三组上游各配各的，这里只碰聊天那一组。

还有一处容易疑惑，函数返回的类型标着 `ChatOpenAI`，但实际构造的是它的一个子类。那是后面为了修正流式用量统计做的包装，跟本章无关。

## Prompt 管理

### 客服人设

System Prompt 分三段写，角色、职责范围、行为约束：

```python
CUSTOMER_SERVICE_SYSTEM = """你是「喵喵优选」电商平台的智能客服「小喵」。

## 角色
- 语气亲切专业,回答简洁,中文作答,适度使用礼貌用语,不卖萌刷屏。

## 职责范围
- 解答商品咨询、订单、物流、售后(退款/换货/维修/投诉)相关问题。
- 与购物无关的话题(写代码、闲聊时政等),礼貌说明职责范围并引导回购物相关问题。
```

值得留意的是行为约束那一段，每一条都是反着写的，说的是不许做什么。其中有一条专属于第 1 章：这时候系统还没有任何工具，模型手里没有查订单的能力，所以 prompt 里要明确写「本阶段没有查询订单/物流系统的权限」，还要拦住它张口就说「我帮您转交」。没有这句，模型会很自然地承诺一件它根本做不到的事。到第 2 章工具接上以后，这条约束就该跟着改。

### 模板拼装

```python
CUSTOMER_SERVICE_PROMPT = ChatPromptTemplate.from_messages(
    [
        ("system", CUSTOMER_SERVICE_SYSTEM),
        MessagesPlaceholder("history"),
    ]
)
```

`MessagesPlaceholder("history")` 是多轮对话的接口，调用时传一个消息列表进去，它整段展开成多条消息，而不是把历史拼成一个字符串塞进 system。这个差别在后面几章会一路发挥作用，因为工具调用、工具结果都是消息，只有保持消息结构才装得下。

角色名统一写 `system`，这是 LangChain 抽出来的统一叫法，各家协议的差异交给下面那层去对齐。

## 结构化提取

这是第 1 章保存得最完整的一条链路，从 schema 到接口几乎原封不动活到了现在。

### 目标形状

先用 pydantic 把你要的结果描述出来：

```python
class AfterSalesTicket(BaseModel):
    """从用户售后描述中提取的结构化工单。"""

    order_id: str | None = Field(
        default=None, description="订单号,原文未出现则为 null,禁止编造"
    )
    request_type: RequestType = Field(description="用户诉求类型")
    expected_solution: str = Field(description="用户期望的处理方案,一句话概括")
```

这里的 `description` 不是写给同事看的注释。它会被翻译成模型看到的 schema，跟 System Prompt 一样属于提示词的一部分，所以「禁止编造」这四个字是真的在对模型说话。诉求类型用 `RequestType` 枚举兜住，模型只能在五个值里选，答不上来落到「其他」。

### 占位符归一

```python
    @field_validator("order_id", mode="before")
    @classmethod
    def _normalize_missing_order_id(cls, v: object) -> object:
        # 模型偶尔把"没有订单号"表达成占位字符串而非省略参数,统一归一为 None
        if isinstance(v, str) and v.strip().lower() in {"", "null", "none", "n/a", "无"}:
            return None
        return v
```

这个 validator 挡的是一个具体的模型行为。原文里没有订单号时，正确做法是干脆不传这个参数，但模型偶尔会传一个字符串 `null` 或者 `无` 进来，字面上看它「填了」，实际是个占位符。`mode="before"` 让这段逻辑跑在 pydantic 校验之前，把这些写法统一归成 `None`。

同一个坑在提示词里也交代过一遍，`EXTRACT_SYSTEM` 里专门写了「千万不要传入字符串 null 或 无 这类占位文本」。两道防线一前一后，prompt 那道是劝，validator 这道是兜，模型不听话时仍然拿得到干净的结果。

### 接口装配

```python
def get_extractor() -> Runnable:
    model = get_chat_model()
    return EXTRACT_PROMPT | model.with_structured_output(AfterSalesTicket)
```

`with_structured_output` 把刚才那个 pydantic 模型变成对模型输出的约束，管道符把它和提示词模板串成一条可调用的链。

```python
@router.post("/api/extract", response_model=AfterSalesTicket)
async def extract(
    req: ExtractRequest, extractor: Runnable = Depends(get_extractor)
) -> AfterSalesTicket:
    try:
        return await extractor.ainvoke({"text": req.text})
    except Exception as exc:
        logger.exception("结构化提取失败")
        raise HTTPException(status_code=502, detail="上游模型暂时不可用,请稍后重试") from exc
```

`Depends(get_extractor)` 让这条链每次请求现建，代价是多了一点对象构造开销，好处是测试时能整条替换掉，不用打补丁。异常这里翻译成 502 加一句人话，原始异常只进日志不给用户看，因为上游的报错文本经常带着内部地址和模型名。

## SSE 流式响应

### 帧长什么样

```python
def _sse(payload: dict) -> str:
    return f"data: {json.dumps(payload, ensure_ascii=False)}\n\n"


def _sse_error(message: str) -> AsyncIterator[str]:
    yield "event: error\n"
    yield _sse({"message": message})
```

SSE 的格式很简单，每帧以 `data: ` 开头，两个换行结束。要标事件类型就在前面多发一行 `event: xxx`。`ensure_ascii=False` 不能少，否则中文全变成转义序列，前端拿到一堆看不懂的东西。

### 生成器变成响应

```python
@router.post("/api/chat")
async def chat(req: ChatRequest):
    async def event_stream() -> AsyncIterator[str]:
        try:
            async for ev in runtime.stream_turn(req.user_id, req.message, req.conversation_id):
```

内层定义一个异步生成器，最后交给 `StreamingResponse(event_stream(), media_type="text/event-stream")`。边生成边发的效果就是这么来的，函数没跑完，字已经在用户屏幕上蹦出来了。

### 出错了怎么办

```python
        except runtime.ConversationNotFound:
            for f in _sse_error("会话不存在"):
                yield f
            return
        except SQLAlchemyError:
            logger.exception("数据库错误 user_id=%s", req.user_id)
            for f in _sse_error("数据库暂时不可用,请稍后重试"):
                yield f
            return
```

三个分支各挡一类，会话找不到、数据库不可用、剩下的兜底当上游故障。这里有个流式接口特有的约束值得记住：**错误只能以帧的形式发出去，不能抛 HTTP 500**。响应头在第一帧发出去的那一刻就定了，之后再想改状态码已经来不及，所以前端得靠 `event: error` 这一帧知道出事了。

### 这层骨架没变，变的是喂给它的东西

第 1 章的版本是把模型的流式输出直接转成帧。现在这个 `async for` 消费的是第 5 章的图运行时，帧的种类也多了，`tool` 是工具轨迹、`citations` 是引用来源、`interrupt` 是需要用户点选时的中断、`actions` 是转人工建工单那些按钮。

但你对着上面几段代码看得出来，`_sse` 的写法、`StreamingResponse` 的用法、错误只能发帧这条约束，从第 1 章立起来就没动过。后面章节做的是往里塞更多种类的帧，不是重写这一层。

## 会话与历史裁剪

第 1 章还用不上数据库，会话就先存在进程内，`memory.py` 里那个 `SessionStore` 是当时的最简方案，按 `session_id` 存一个消息列表，重启就没。你在文件里还能看到它，但它现在已经没人调了，第 5 章之后会话落 MySQL、多轮状态交给 LangGraph State，这件事被接管了。留着是为了让你看得见这条演进，别照着它写新代码。

真正一路活下来的是裁剪这一段。

### trim\_history

```python
def trim_history(messages: list[BaseMessage], max_tokens: int) -> list[BaseMessage]:
    return trim_messages(
        messages,
        strategy="last",
        token_counter=count_tokens_approximately,
        max_tokens=max_tokens,
        start_on="human",
        allow_partial=False,
    )
```

四个参数值得逐个说。`strategy="last"` 是从后往前保留，因为最近几轮通常最相关。`token_counter` 用近似计数，省掉一次真实分词的开销，裁剪这种场景不需要精确到个位。`start_on="human"` 保证裁完之后窗口是从一条用户消息开头的，不会出现开局就是模型回话的怪结构。`allow_partial=False` 不切半条消息，宁可少留一轮也不留半句。

这个函数比它的邻居命长。第 7 章做分层上下文管理时，先按两个锚点把历史切成三段，切完仍然调它做 token 兜底，所以它是第 1 章留给后面章节的地基。

## 装配入口

`main.py` 大部分是路由注册这类样板，值得单独看的是开头那段日志配置：

```python
_applog = logging.getLogger("app")
if not _applog.handlers:
    _fmt = logging.Formatter("%(levelname)s:%(name)s:%(message)s")
    _h = logging.StreamHandler()
    _h.setFormatter(_fmt)
    _applog.addHandler(_h)
```

uvicorn 默认不给应用自己的记录器配 INFO handler，不手动加这一段，你在代码里写的 `logger.info` 一句都看不见。后面还有一行 `_applog.propagate = False`，作用是不让应用日志再往上冒到 root，免得跟 uvicorn 的 HTTP 访问日志混在一起，这样 `tail` 项目里那个日志文件时看到的全是业务决策，没有噪声。

文件里那个 `lifespan` 跟本章无关，它现在挂着三件后面章节的事：第 4 章的 Milvus 预热、第 8 章的内置工具扫描、第 5 章的图初始化。
