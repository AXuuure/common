


上一章收工的时候，我们手里已经有了一个能正经聊天的机器人：模型接通了，Prompt 模板立好了规矩，回答还能一个字一个字流式蹦到前端。看着像模像样，聊产品知识、扯几句闲天都不在话下。



那它现在能上岗当客服吗？你拿真实的客服问题一试就知道了，目前肯定还是很勉强的。这一章要给它装上手脚，让它从「会聊天」变成「能查数据、能办事」的客服。

## 会聊天，当不了客服

用户进线的第一句话，大概率是这种：

> 「我上周买的蓝牙耳机怎么还没到？」

这句话难住的可不止模型。你想啊，回答它得知道用户买了哪一单、订单发货没有、物流走到哪一站，这些信息全躺在你家数据库里。模型的知识是训练时固化进参数的，你家昨天的订单，它上哪知道去？



于是模型只剩两条路。诚实一点的，回一句「抱歉，我无法查询您的订单信息」，用户扭头就去找人工了；不诚实的更可怕，一本正经地编：「您的订单预计明天送达」，编得越流畅，客诉来得越快。

![](<images/理论学习：Function Calling 与工具定义-01-chatbot-without-tools.png>)

有同学可能会想：把订单数据塞进 Prompt 不就行了？上一章刚学过 System Prompt，把数据当背景知识喂进去嘛。



这条路只怕是走不通。订单是活数据，状态随时在变，你塞进去的那一刻它就开始过期。再说全库几十万条订单，上下文窗口塞得下吗？

![](<images/理论学习：Function Calling 与工具定义-02-context-window-overload.png>)

问题倒过来看就通了：数据别动，让模型开口「要」。它发现自己缺订单信息，就说一声「帮我查一下这个手机号的单」，我们的代码去把数据取回来，再把结果递回给它，它再组织语言回答用户。模型出的是大脑判断，代码出的是手脚。



这套机制就是「Function Calling」，也就是「工具调用」，本章的主角。

![](<images/理论学习：Function Calling 与工具定义-03-model-judges-code-acts.png>)

## Function Calling：模型只张嘴，不动手

先把最容易误会的一点说破：Function Calling 这名字起得有误导性，听着像模型会调用函数，其实模型从头到尾没有执行过任何代码。它做的唯一一件事，是输出一段结构化文本，内容是「我想调用某某工具，参数是某某」。真正拿这段文本去执行函数的，是我们自己写的程序。



想象一个新客服第一天上岗。他自己不会跑去仓库数货，工位上贴着一张内线清单：查订单打 8001，查物流打 8002，转工单打 8003。他的本事是听懂顾客想干嘛，然后判断该打哪个内线、报什么单号，拨号之后查库存翻订单的事，都是电话那头的后台系统在干。模型扮演的就是这个新客服，我们写的工具函数就是电话那头的系统。

![](<images/理论学习：Function Calling 与工具定义-04-new-agent-internal-lines.png>)

这么一拆，安全边界也顺带清楚了：模型能碰哪些数据、能做哪些操作，完全由我们递给它的工具清单说了算。没给它删库的工具，它说破天也删不了库。



整个流程走下来是四步。模型先从用户的话里识别出意图，比如这是要查订单；接着生成一个结构化的工具调用请求，带上函数名和参数；我们的代码执行这个函数，拿到真实数据；最后把执行结果「回灌」给模型，让它据此生成给用户的回答。四步里模型出场两次，一次点单，一次组稿，中间干体力活的那步交给我们的代码。

![](<images/理论学习：Function Calling 与工具定义-05-function-calling-four-steps.png>)

落到协议层面，这套流程无非是几条消息的往返。上一章我们读过 Chat Completions 的请求体，Function Calling 只是往里面多塞一个 `tools` 数组，数组里每个元素是一份工具的「说明书」：

```json
{
  "type": "function",
  "function": {
    "name": "query_order",
    "description": "根据订单号或下单手机号查询订单的状态、商品与金额",
    "parameters": {
      "type": "object",
      "properties": {
        "order_no": {"type": "string", "description": "订单号，形如 SO20260625001"},
        "phone": {"type": "string", "description": "下单时使用的 11 位手机号"}
      },
      "required": []
    }
  }
}
```

三个字段各管一块：`name` 是工具的名字，`description` 告诉模型这工具是干什么的、什么时候用，`parameters` 用 JSON Schema 描述参数长什么样。JSON Schema 你可以理解成参数的「格式合同」：`type` 定类型，每个参数自己的 `description` 说明取值含义，`required` 圈出必填项。

![](<images/理论学习：Function Calling 与工具定义-06-tool-manual-schema.png>)

其实这份说明书就是会随着塞进上下文的 Prompt，模型每次回答前都会先翻一遍，判断这次要不要用工具、用哪个。所以 `description` 写得好不好，直接决定模型会不会在该出手的时候出手，这一点到后面讲 `@tool` 装饰器时还会展开。



模型决定用工具时，回复长这样：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_7f3a",
    "type": "function",
    "function": {
      "name": "query_order",
      "arguments": "{\"phone\": \"13800001234\"}"
    }
  }]
}
```

注意两个细节。`content` 是空的，模型这一轮没说人话，只提交了一张「取数申请单」；`arguments` 的值是个字符串，字符串里面才是 JSON，拿到手得再解析一层，这是头一回对接时几乎人人踩的坑。

![](<images/理论学习：Function Calling 与工具定义-07-tool-call-request-card.png>)

我们执行完函数，把结果包成一条 `role` 为 `tool` 的消息，追加回对话：

```json
{
  "role": "tool",
  "tool_call_id": "call_7f3a",
  "content": "{\"order_no\": \"SO20260625001\", \"status\": \"已发货\", \"item\": \"蓝牙耳机\"}"
}
```

`tool_call_id` 要跟申请单上的 `id` 对得上，模型才知道这份结果是回应哪次调用的。带着这条消息再请求一次模型，它就能组织出「您的耳机已经发货，正在派送途中」这样的人话了。

![](<images/理论学习：Function Calling 与工具定义-08-tool-result-card.png>)

到这你应该看出来了，Function Calling 本质上是一种消息格式的约定，外加一轮额外的对话往返。拆开看无非三份 JSON：说明书、申请单、结果单。

![](<images/理论学习：Function Calling 与工具定义-09-manual-request-result-loop.png>)

## 打地基：项目骨架与四张表

工具是要查数据的，库里连表都没有，工具写出来查什么呢？动手定义工具之前，得先把项目和数据这层地基铺好。这一节只讲设计思路，真正把环境跑起来的操作，像用 Docker 起 MySQL、建库建表、灌测试数据，实战篇会一步步带着做。



先说项目骨架。Web 层用 FastAPI，数据层用 SQLAlchemy，都是 Python 生态的主流选择，异步支持好，跟这门课一路要用的 LangChain 也合得来。骨架本身没什么可炫技的，路由、数据模型、数据库连接、配置管理，标准分层。这门课的规矩是零手写代码，骨架也用 Claude Code 对话式生成：你描述清楚要什么结构，它来搭，你来验收，具体怎么描述、怎么把关。

![](<images/理论学习：Function Calling 与工具定义-10-fastapi-sqlalchemy-layers.png>)

重头戏是数据库设计。电商客服要伺候的场景，翻来覆去就那几类：问商品、查订单、催物流、问政策、搞不定了找人工。这里得先分个类：商品、订单、物流这三样，真实生产里都躺在公司电商系统、物流系统那边，客服系统只管调它们的 API 拿数据，自己并不存；本课程为了演示方便，干脆在对应工具内部随机生成，不接真实接口，也不建表。真正要自己落库的只剩四张，先混个脸熟：

| 表               | 存什么                             | 伺候谁             |
| --------------- | ------------------------------- | --------------- |
| `faq`           | 问答对：问题、答案、分类                    | `query_faq`     |
| `conversations` | 会话：谁在什么时候开启的一通对话、处理状态           | 对话服务            |
| `messages`      | 消息流水：会话里每条消息的角色与内容              | 对话服务            |
| `tickets`       | 人工工单：工单号、关联会话、问题描述、类型、处理状态、创建时间 | `create_ticket` |

![](<images/理论学习：Function Calling 与工具定义-11-customer-service-tables.png>)

商品、订单、物流这三样，真实生产里它们分别来自公司电商系统、物流系统的接口；课程项目这里为了方便演示，`query_product`、`query_order`、`query_logistics`的代码里会直接模拟数据



faq 表则是问题、答案、分类，三个业务字段。



conversations 和 messages 拆成两张，一对多，一通会话底下挂 N 条消息。为什么不合成一张？消息是流水，会话是流水的壳，用户的一次进线得有个统一的身份：谁来的、什么时候来的、处理完没有。往后做转人工、做工单都要引用「这通会话」，全捏在消息表里，就没有一个稳定的东西可指了。



messages 的角色字段得多说两句：它的取值跟 Chat Completions 协议的 `role` 对齐，`user`、`assistant` 之外还留了 `tool`。前面刚看过，工具调用的申请单和结果单也是消息，把它们原样落库，一通对话就能完整回放：模型什么时候决定查库、查到了什么、据此说了什么，全都有据可查。眼下这只是留档，等后面讲可观测性的章节，这些流水就是排查问题的第一手材料。



最后补一张 `tickets`，专给 `create_ticket` 落地。工单号当主键，挂着关联的会话 id、问题描述、工单类型、处理状态、创建时间。会话 id 让工单能倒查回当时具体聊了什么，处理状态从「待处理」流向「已处理」，后面真人客服接手时，就靠这个字段判断队列里还压着多少活。

![](<images/理论学习：Function Calling 与工具定义-12-faq-cards-into-database.png>)

## 客服的五件工具

地基有了，可以正经设计工具了。动笔之前有三条设计原则要立住，五个工具都按这套原则来。



第一条，一个工具只管一件事。「查订单」和「查物流」听着像亲戚，也别合成一个「查订单相关信息」的大工具，工具边界越清楚，模型选起来越不容易犯迷糊。



第二条是参数宁少勿多，每个参数都得让模型有地方取值，取值来源要么是用户的话、要么是上下文，模型凭空变不出参数来。



最后一条其实最容易被忽略：进出参都为「模型读得懂」服务。工具的使用者是模型，返回一堆裸 ID 和内部枚举码，它拿着也没法跟用户交代。

### query\_order：订单查询

职责一句话说完：根据订单号或手机号，查出订单的状态、商品和金额。



进参设计有个小门道：订单号和手机号都设成可选，但至少得给一个。为什么不干脆只收订单号？回忆一下你自己找客服的经历就明白了，有几个人背得出「SO20260625001」这种单号？多数用户开口是「用 138 那个手机号买的」。让工具同时认这两种问法，模型才能把用户的自然表达顺畅地翻译成调用。



出参按订单列表返回，哪怕按订单号查理论上只有一条。手机号底下常挂着好几个单，返回列表，模型看到多条结果就会自己追问「您问的是哪一单，耳机那单还是鞋子那单」，这层交互不用我们写一行分支逻辑，模型顺着数据就把它做了。

![](<images/理论学习：Function Calling 与工具定义-13-query-order-inputs.png>)

还有个容易做错的地方：查无此单时返回什么？返回空列表，再附一句明确的说明，比如「未查询到相关订单」，别丢个 null 或者空字符串回去。结果越含糊，模型越容易自由发挥，含糊就是给幻觉留门缝。

### query\_product：商品查询

用户问商品有两种典型问法，一种奔着具体商品来，「XX 降噪耳机有货吗」；一种按品类逛，「你们运动鞋都有什么」。所以进参给两个可选项，名称关键词和分类，正好接住用户问商品时最常给的两种线索。



出参是商品列表，带名称、价格、库存、规格。这里有个实际的取舍：命中太多怎么办？「鞋」一个字能扫出半个货架。查询内部要限条数，比如最多返回十条，超出就截断，并在结果里注明「还有更多商品，建议引导用户缩小范围」。把「数据太多」这个状态明明白白告诉模型，它就会顺势引导用户往细了问，而不是拿着十条硬编一份全店总结。

![](<images/理论学习：Function Calling 与工具定义-14-product-search-truncation.png>)

### query\_logistics：物流查询

这个工具的作用：按订单号返回一份物流状态，包括承运商、物流单号、当前进度和轨迹节点。



有了 query\_order 为什么还要它？订单查询答的是「买了什么、什么状态」，物流查询答的是「货现在到哪了」。



合成一个工具当然也能跑，拆开有两个好处：一是「到哪了」是电商客服的头号高频问题，单独成一个工具，模型选择的路径更短、带的参数更省；二是它俩的数据本就分属两个系统，订单来自电商系统、物流来自物流公司，真实生产里就是两个接口，拆开正好对得上真实情况。



课程项目这里为了方便演示，`query_product`、`query_order`、`query_logistics`的代码里会直接模拟数据

![](<images/理论学习：Function Calling 与工具定义-15-order-logistics-api-split.png>)

进参只收订单号一个。那用户报手机号催物流怎么办？直觉上模型该先拿手机号查出订单、再拿单号查物流，两步连着走。可本章的系统只让模型开一次单，这种组合拳它打不出来，只能先追问用户要单号。这个我们后面的章节会处理。

### query\_faq：政策与常见问题查询

前面三个工具查的是业务数据，都带着明确的主键或者关键词。这个工具查的是「知识」：退货政策怎么规定、发票怎么开、优惠券怎么叠加。



它的契约干脆到只有一进一出：进，用户的问题，一个字符串；出，答案文本。就这么多。



内部实现拿用户问题里的关键词，去 faq 表做 SQL LIKE 模糊匹配，命中了就把答案原样返回。


```sql
SELECT question, answer FROM faq
WHERE question LIKE CONCAT('%', :keyword, '%')
   OR answer LIKE CONCAT('%', :keyword, '%')
LIMIT 3;
```

关键词从哪来？可以偷懒到直接拿整句去匹配，也可以稍微认真一点，分词后挑出实词逐个去试。

### create\_ticket：转人工工单

前四个工具都是「读」，这一个是「写」：在系统里创建一张人工客服工单，把 AI 接不住的问题移交给人。



别小看这个兜底出口。智能客服的设计底线是搞不定就体面交接，而不是死扛着硬答。用户情绪上来了、问题超出能力范围、反复查不到想要的信息，都该有一条通往人工的路。没有这条路，AI 每一次答非所问都在消耗用户的耐心。

![](<images/理论学习：Function Calling 与工具定义-16-human-ticket-handoff.png>)

进参收拢移交所需的最小信息：关联的会话、问题描述、工单类型，写进 tickets 表时再补一个处理状态和创建时间。出参给工单号，再配一句能直接念给用户听的确认话术，「已为您创建工单 T20260701008，人工客服会在今天之内联系您」。

## `@tool` 装饰器：把函数亮给模型

五个工具的职责和进出参都设计完了，落到代码上，每个工具就是一个普通的 Python 函数。可光有函数不够，还记得前面那份 JSON 说明书吗？函数得配上名字、用途描述、参数 Schema，模型才认得它。



那份说明书谁来写？手写当然可以，裸调 OpenAI SDK 的项目就是这么干的：函数写一份，Schema 再写一份。麻烦倒是其次，真正的隐患是两份维护：哪天函数加了个参数，Schema 忘了同步，模型拿着旧说明书调新函数，错都不知道错在哪。



LangChain 给的解法是 `@tool` 装饰器，也是这门课在工具定义这条线上的正式选型。它的思路是一份代码、两份产出：你把函数写好、写规范，说明书从函数上自动抽出来。

![](<images/理论学习：Function Calling 与工具定义-17-tool-decorator-two-outputs.png>)

```python
from langchain.tools import tool
from typing import Annotated

@tool
def query_order(
    order_no: Annotated[str | None, "订单号，形如 SO20260625001"] = None,
    phone: Annotated[str | None, "下单时使用的 11 位手机号"] = None,
):
    """根据订单号或手机号查询订单，返回订单状态、商品与金额。

    订单号和手机号至少提供一个。用户报不出订单号时，用手机号查询。
    """
    ...
```

这段代码里藏着三个映射：函数名 `query_order` 成了工具名，docstring 成了工具的 `description`，参数的类型注解生成参数 Schema，`Annotated` 里那句中文说明会挂到对应参数的 `description` 上。装饰器在函数定义那一刻把这些信息抽出来，组装成模型要看的 JSON 说明书，跟函数本体永远同步。

![](<images/理论学习：Function Calling 与工具定义-18-tool-metadata-mapping.png>)

想看它抽出来的东西长什么样，打印一下就有：

```python
print(query_order.name)         # query_order
print(query_order.description)  # 根据订单号或手机号查询订单，返回订单状态……
print(query_order.args)
# {'order_no': {'description': '订单号，形如 SO20260625001', ...},
#  'phone': {'description': '下单时使用的 11 位手机号', ...}}
```

`query_order.args` 里就是前面协议部分见过的那份 JSON Schema。这套 Schema 的讲究不多，但每一处都影响模型的发挥：类型定准了，模型就不会把手机号传成数字；枚举型参数用 `enum` 定死可选值，比如工单类型只能在「售后、投诉、咨询」里选，模型就不会自己发明一个新类型出来；可选参数配上默认值，模型拿不准的时候有台阶下。



写 docstring 时要换一副心态：这段文字的读者是模型，它就是 Prompt 的一部分。「查询订单」四个字当注释合格，当工具描述不合格。什么时候该用这个工具、参数从哪取、有什么使用限制，都该写进去。上面那句「用户报不出订单号时，用手机号查询」写的就是使用时机，模型是会参考你这个说明来使用的。



工具定义好，挂到模型上只要一行：

```python
llm = ChatOpenAI(
    model="qwen-plus",
    base_url="https://xxx",
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    temperature=0,
)
tools = [query_order, query_product, query_logistics, query_faq, create_ticket]
llm_with_tools = llm.bind_tools(tools)
```

`bind_tools` 的作用是：把五份说明书转成协议里的 `tools` 数组，以后每次请求自动捎上。从此模型每次开口之前，都会先看拥有哪些工具。

![](<images/理论学习：Function Calling 与工具定义-19-bind-tools-cards.png>)

## 执行链：注册、分发与容错

模型点了单，轮到我们的代码接单了。执行这步听着琐碎，客服系统的「稳」几乎全押在这里。



先说注册。模型返回的 `tool_calls` 里只有工具名这个字符串，得有个地方能按名字找到工具本体，一行字典就够：`TOOL_REGISTRY = {t.name: t for t in tools}`。别嫌它简单，这个按名索骥的映射就是「工具注册表」的雏形。

![](<images/理论学习：Function Calling 与工具定义-20-tool-registry.png>)

分发执行交给 LangChain：把模型返回的 `tool_call` 整个递给 `tool.invoke`，它会把 `arguments` 那层「字符串里的 JSON」解析成字典、执行函数，再把返回值自动包成待回灌的 `ToolMessage`，连 `tool_call_id` 都替你对齐。



真正要花心思的是出岔子的时候。工具执行的失败分好几种，处理方式各不相同，一股脑 try 住往外抛异常，是最偷懒也最伤体验的做法。



第一种，参数不合法。模型偶尔会抽风，让查订单却一个参数都没给，或者手机号只传了 8 位。这类错误 Pydantic 校验会先拦住，拦下来之后，把校验错误的说明当成执行结果回灌给模型，它看到「订单号和手机号至少提供一个」，多半会回头追问用户，或者换个参数重新组织调用。



第二种，查询落空。订单号没查到、FAQ 没命中，这在业务上再正常不过，压根够不上「错误」那一档。落空就返回一句明确的「未查到」，让模型接着这个事实跟用户周旋：「没有查到这个单号，麻烦您核对一下」。把落空当异常抛，前端只能给用户看一句冷冰冰的「系统错误」，冤不冤。



第三种是故障：数据库连不上、查询报错。这类要捕获住，包成一条「工具暂时不可用」的结果回灌，模型会道歉、会建议稍后再试或者转人工。你看，坏消息在这套体系里也是有用的输入，模型拿到它一样能做出体面的应对，前提是你把坏消息如实告诉它，服务进程自己不能跟着倒。

![](<images/理论学习：Function Calling 与工具定义-21-tool-error-triage.png>)

上一章把流式输出接好了，用户此刻正盯着屏幕上的光标等回复呢，一个卡死的查询能把整条响应拖到天荒地老。所以每个工具执行都要包一层超时控制，异步实现用 `asyncio.wait_for` 这类机制设个上限，几秒等不来就掐断，掐断后同样包成失败结果回灌。对用户来说，「查询超时了，请稍后再试」远好过一个转了半分钟还在转的圈。

![](<images/理论学习：Function Calling 与工具定义-22-tool-timeout-cutoff.png>)

再说重试。重试只留给「再试一次可能就好」的暂时性故障，网络抖一下、连接偶尔闪断，这种重来一两次成本低收益高。业务性的落空千万别重试，订单号错了查一百遍还是查不到，白白搭上一百次查询。



最要小心的是 create\_ticket 这种写操作：网络超时未必代表工单没建成，可能只是响应丢在路上了，闷头重试就是两张重复工单。要么写操作不自动重试，失败了让模型如实告诉用户；要么请求里带上「幂等键」，同一个键重复提交只生效一次。课程项目选不自动重试这条，简单，语义也诚实。

## 结果回灌：把数据翻译给模型听

工具执行完，手里攥着的是 SQLAlchemy 的 ORM 对象。直接转成字符串扔回去行不行？模型大概率能看懂，可你把 token 的钱包和用户的隐私也一起扔出去了。回灌前的格式化，有三件事要做。



先挑字段。ORM 对象上什么都有，内部主键、成本价、库存预警线，这些跟回答用户没关系的字段一个都别带，只挑模型组织回答要用的：单号、状态、商品名、金额、时间。字段越少 token 越省，顺带把「模型说漏嘴」的风险也掐掉了，它没拿到成本价，就永远不会把成本价念给用户听。

![](<images/理论学习：Function Calling 与工具定义-23-filter-tool-result-fields.png>)

再翻译语义。数据库里的状态是给程序看的枚举码，`SHIPPED`、`REFUNDING`，直接给模型，它也能猜个八九不离十，但「猜」这个动作本身就不该存在。回灌前把枚举翻译成「已发货」「退款中」，模型拿到的每个字段都无歧义，回答才稳。

![](<images/理论学习：Function Calling 与工具定义-24-status-enum-translation.png>)

最后把结果序列化成 JSON 字符串。中文别转义成 `\u` 码，`json.dumps(data, ensure_ascii=False)`，省 token，人翻日志的时候也看得懂。空结果照前面立的规矩办，写成明确的「未查询到」，别让模型对着一个空数组自行想象。



格式化完的结果包进 `ToolMessage` 回灌。前面协议部分见过 `tool_call_id` 这个字段，这里补上它存在的理由：协议允许模型在一条回复里同时开出几张申请单，比如用户一句话又问订单又问发票，结果逐个回灌时全靠这个 id 对号入座，谁的结果是谁的，不能乱。LangChain 的 `tool.invoke(tool_call)` 已经替你把 id 对齐了，哪天自己手工构造 `ToolMessage`，这个字段千万别落下。

## 单轮调用：全流程串起来

零件全齐了：工具定义了、注册了，容错想清楚了，结果也知道怎么回灌了。串成一条完整的链，就是本章的最终形态：

```python
async def chat_once(messages: list):
    ai_msg = await llm_with_tools.ainvoke(messages)
    if not ai_msg.tool_calls:                # 不需要工具，直接回答
        return ai_msg

    messages.append(ai_msg)                  # 申请单入档
    for tool_call in ai_msg.tool_calls:
        tool = TOOL_REGISTRY[tool_call["name"]]
        tool_msg = await tool.ainvoke(tool_call)   # 执行，容错做在工具内部
        messages.append(tool_msg)            # 结果单入档

    return await llm_with_tools.ainvoke(messages)  # 拿着数据组织最终回答
```

十来行，就是 Function Calling 的全部骨架。走一遍时序：模型第一次被调用，翻了翻工具说明书，决定开申请单；我们按注册表找到工具、执行、把申请单和结果单一起追加进消息列表；模型第二次被调用，这回它手里有真数据了，组织出给用户的最终回答。两次模型调用，中间夹一次工具执行。

![](<images/理论学习：Function Calling 与工具定义-25-single-turn-sequence.png>)

多说一句那个 for 循环：它处理的是模型在同一条回复里开出几张申请单的情况，一句「帮我查下订单，顺便看看退货政策」可能同时唤起 query\_order 和 query\_faq。这仍然是一次决策、一批执行，跟「多轮」是两回事。



真正的边界在最后一行之后。模型拿到结果后的那次回复，万一还想再查一个呢？比如查完订单发现是售后单，想接着查退货进度。按本章的代码，它第二次回复就算带着新的 `tool_calls`，我们也不接了，流程到此为止。



有同学肯定要问：调完一次工具，要是还想接着调呢？很敏锐，这确实是的，而且后面你会发现，这就是 Agent 的本质。这个我们后面还会说的。

![](<images/理论学习：Function Calling 与工具定义-26-single-turn-boundary.png>)

## 章尾翻车现场：query\_faq 查了个空

链路跑通了，来验收。



faq 表里躺着这么一条数据：

| question | answer                              |
| -------- | ----------------------------------- |
| 运费怎么算    | 单笔订单满 99 元包邮，未满收取 10 元运费，偏远地区运费另计…… |

用户问的是：

> 「邮费是多少？」

按前面的实现，假如系统从问题里取词去 LIKE：`%邮费%`，落空；`%是多少%`，落空；整句去匹配，更没戏。faq 表里分明存着现成的答案，查询结果却是空的，模型只好老老实实告诉用户「没有查询到相关信息，建议您联系人工客服」。



答案就在表里，愣是没够着。



你多试几个问法，照样也是不行。「多少钱包邮」查不到，表里写的是「运费怎么算」；「快递费怎么收」照样落空；用户手滑打个错别字，就更别提了。反倒是恰好说出「运费」两个字的用户能拿到答案。一个客服系统，答不答得上来居然取决于用户会不会说精确标准的话，这就很荒唐。

![](<images/理论学习：Function Calling 与工具定义-27-faq-zero-word-overlap.png>)

病根不难看出来：LIKE 认的是字面。用户嘴里的「邮费」和表里的「运费」说的是同一件事，字面上却对不上。



那抢救一下呢？给「运费」配上「邮费、快递费」的同义词，给「包邮」挂上「免运费、满多少免邮」……补丁能打，用户的说法却是无穷的，词表补到最后，你维护的是一部《电商黑话大辞典》，还是补不完。

![](<images/理论学习：Function Calling 与工具定义-28-ecommerce-slang-dictionary.png>)

下一章 RAG 基础专门解决这个问题，到时候你会看到同样这句「邮费是多少」，从查空变成稳稳命中。

## 本章小结

这一章从「会聊天但查不了单」的窘境出发，把 Function Calling 的整套机制过了一遍：模型出判断、代码出腿，靠说明书、申请单、结果单三份 JSON 完成协作。地基上搭出了 FastAPI 加 SQLAlchemy 的骨架和四张表（商品、订单、物流走工具内部随机生成，不建表）；工具这层用 `@tool` 装饰器定义了五个业务工具；再往上，注册、分发、容错、回灌串成一条完整的「单轮调用链」，模型开一次单就收敛。



现在这个客服已经能查单、看物流、开工单了，唯独 query\_faq 在真实问法面前栽了跟头。下一章我们去看看要怎么解决这个问题。
