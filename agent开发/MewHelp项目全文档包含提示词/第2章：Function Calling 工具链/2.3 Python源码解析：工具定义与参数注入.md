## 先验一件事：模型到底会不会

### smoke\_toolcall.py

整章的方案都压在一个前提上，上游模型得能返回结构化的 `tool_calls`。这个前提要是不成立，后面写多少代码都白搭，所以第一步是花十几行把它验掉。

```python
@tool(args_schema=AddInput)
def add(a: int, b: int) -> int:
    """把两个整数相加。"""
    return a + b
```

```python
    model = get_chat_model()  # 非流式,直连 settings.chat_base_url
    bound = model.bind_tools([add])
    ai = await bound.ainvoke("请用工具计算 23 加 19 等于多少")
    print("content:", repr(ai.content))
    print("tool_calls:", ai.tool_calls)
```

这是全仓最干净的一段 Function Calling，没有数据库、没有编排、没有业务 Prompt，只剩协议本身。`bind_tools` 把工具的 schema 挂到这一次请求上，模型看完之后不返回文本，返回一份填好参数的调用申请，落在 `ai.tool_calls` 里。

脚本末尾判断的是选中的工具名对不对，对了打 GO，不对打 NO-GO 并且写明「停下来问用户，不自行换方案」。这句话是给 AI 看的，验不过就该停，别自作主张换个模型接着往下跑。

顺带说一下，`ai.content` 和 `ai.tool_calls` 可以同时有值，也可以只有一个。模型决定调工具时，正文常常是空的，这个细节等会讲建表的时候还会碰到。

## 一个工具最少要交代什么

### @tool

先看最干净的那个，`query_product`：

```python
@tool
async def query_product(
    product_name: Annotated[str, Field(description="商品名称或关键词,例如 猫粮")],
) -> dict:
    """查询商品的价格、库存和规格。用于用户咨询某商品是否有货、多少钱时。"""
    rng = random.Random(f"product:{product_name}")
    return {
        "product_name": product_name,
        "price": rng.randint(20, 999),
        "stock": rng.randint(0, 500),
        "spec": rng.choice(["标准装", "家庭装", "试用装"]),
    }
```

装饰器会从这个函数身上读走四样东西。函数名 `query_product` 成为工具名，docstring 成为工具的 `description`，类型注解 `str` 成为参数类型，`Field(description=...)` 成为参数说明。

这里最容易被当成注释掠过的是后两处描述。它们都会被序列化进模型看到的 schema，模型选哪个工具、往参数里填什么，判据就是这两句话。docstring 写得含糊，模型就会在几个工具之间反复挑错，这是提示词没写好，不是代码有 bug。

参数描述还有另一种等价写法，挂一个独立的 pydantic 模型上去。`query_faq` 用的就是这条路径：

```python
class FaqInput(BaseModel):
    keyword: str = Field(description="用户咨询的政策/规则/操作类问题(可用原话)")
    category: str | None = Field(default=None, description="可选:按品类过滤,如『运费』『退货』『商品手册』")
```

然后 `@tool(args_schema=FaqInput)`。参数多、需要复用、或者想给字段挂校验规则的时候用这种，参数就一两个的时候直接把 `Field` 写进注解更省事。仓库里两种都有，功能上没差别。

### 描述得写到什么份上

`query_order` 的 docstring 比上面那个长得多，多出来的部分正是工具描述真正吃力的地方：

```python
@tool
async def query_order(
    order_id: Annotated[str, Field(description="订单号,例如 1001")],
    user_id: Annotated[str, InjectedToolArg],
) -> dict:
    """查询订单的状态、金额、下单时间、商品名和物流单号(tracking_no)。用于用户询问某个订单情况时。
    要查物流轨迹,需先用本工具拿到订单的 tracking_no,再把它传给 query_logistics。
    发起人身份由系统注入,你不要传 user_id。"""
    if not owns_order(user_id, order_id):
        return dict(NOT_OWNED)
    return order_snapshot(order_id)
```

第一句交代返回值里有什么，还特意点名了 `tracking_no`。第二句交代跟别的工具怎么接力。用户问「我的快递到哪了」时，模型手上只有订单号，而 `query_logistics` 要的是物流单号，中间必须先调一次 `query_order`。这个先后关系没法写进任何一个工具的参数定义，只能写在描述里。

模型能不能连着调两个工具，很大程度上就取决于有没有人把这句话写进去。

## 模型看得见的参数和看不见的参数

上面那段签名里还有个别扭的地方，`user_id` 这个参数没有 description，取而代之的是 `InjectedToolArg`。

```python
    user_id: Annotated[str, InjectedToolArg],
```

它的效果是让这个参数留在 `args_schema` 里（函数照样得收到它），但不进 `tool_call_schema`。序列化给模型的是后面那份，所以模型压根不知道有这么个参数，也就没法填。真实的 `user_id` 由执行引擎在调用前从可信通道补进去，那套注入机制是第 8 章的东西，这里只要理解为什么签名里会出现一个模型看不见的参数。

判据很简单，凡是决定「这次调用代表谁」的参数，都不能让模型填。模型填的东西来自对话文本，而对话文本是用户可以随便写的。`create_ticket` 的会话号是同一个道理：

```python
@tool
async def create_ticket(
    description: str,
    ticket_type: Literal["售后", "投诉", "咨询"],
    conversation_id: Annotated[int, InjectedToolArg],
) -> dict:
```

这里也顺便看到 `Literal` 的用法，工单类型的三个取值会进 schema 变成枚举，模型只能从里面选。

### 一句话回两种情况

`query_order` 里那个归属分支返回的是一个常量：

```python
NOT_OWNED = {"error": "没有找到您的这笔订单", "code": "order_not_owned"}
```

订单不存在，回这句。订单存在但不是这个人的，也回这句。两种情况的回答必须一模一样，否则攻击者拿一串订单号挨个试，看回答的差异就能把平台上真实存在的订单号枚举出来。

归属判断收在 `owns_order` 这一个函数里，工具和后面章节的图节点都调它。判断逻辑散成两份、两边规则慢慢漂开，是这类校验最常见的失效方式。

## mock 数据源怎么做到可复现

`business.py` 现在只剩几个纯函数，不再定义任何工具。它管的是数据从哪来：

```python
def order_snapshot(order_id: str) -> dict:
    """订单快照(纯函数,随机种子固定 → 同 order_id 稳定)。query_order 工具与 fetch_order 节点同源。"""
    rng = random.Random(f"order:{order_id}")
    return {
        "order_id": order_id,
        "status": rng.choice(["待付款", "已付款", "已发货", "已签收"]),
        "amount": rng.randint(50, 2000),
        "created_at": f"2026-07-{rng.randint(1, 12):02d} 10:00",
        "product": rng.choice(["智能猫砂盆", "猫粮 5kg", "猫爬架", "自动饮水机"]),
        "tracking_no": f"SF{rng.randint(10**11, 10**12 - 1)}",
    }
```

关键是 `random.Random(f"order:{order_id}")` 这一行。随机数发生器的种子由入参决定，同一个订单号每次拿到的状态、金额、物流单号完全一样，重启进程也一样。

为什么非得稳定？后面每一章的验收脚本、单元测试、文档里的 curl 例子，全都拿 1001 举例。数据要是每次调用都变，断言就没法写，学员照着文档跑出来的结果也跟截图对不上。mock 数据可以假，不能飘。

同一个道理还体现在演示单上。`list_user_orders` 按 `user_id` 列出这个人名下的订单，用的也是入参当种子：

```python
    rng = random.Random(f"user_orders:{user_id}")
    ids = list(DEMO_ORDER_IDS)
    for _ in range(rng.randint(2, 4)):
        oid = str(rng.randint(1000, 9999))
        if oid not in ids:
            ids.append(oid)
```

`DEMO_ORDER_IDS` 是 1001 和 2002，每个账号名下都塞这两笔，文档里的例子换谁登录都跑得通。想看归属校验拦人，随便报一个别的号就行。

## 工具的说明书还有一份写在 System Prompt 里

单个工具怎么用，写在它自己的 docstring 里。工具之间怎么取舍、什么情况下压根不该调工具，这些没有归属，只能写进 system prompt。`prompts.py` 里的 `AGENT_SYSTEM` 就是这份说明书：

```text
## 工具使用原则
- 需要订单/商品/物流的具体信息时,调用对应工具查询(query_order / query_product / query_logistics),不要臆造数据。
...
- 只有用户明确要求建工单/要求人工跟进时,才发起 create_ticket;发起前先核对问题描述等必填信息,缺什么就先向用户追问,严禁编造或用占位文本充数。发起后系统会把工单预览交给用户确认;用户取消后不要擅自重试,除非用户再次明确要求。
- 工具清单可能动态变化(如物流轨迹、在保状态、退货进度等由外部服务提供),按各工具的用途描述选用;工具返回错误说明时,按说明修正参数或如实告知用户,不要编造结果。
- 能直接回答的闲聊或超出电商客服范围的问题,礼貌回应或引导回购物话题,不必调用工具。
...
```

`create_ticket` 那条写得最啰嗦，因为它是本章唯一的写操作，出错代价跟查询完全不是一个量级。它后半句提到的工单预览确认是第 8 章才加的，本章还没有。模型有个很稳定的坏习惯，参数缺了不会追问，会自己编一个看起来合理的填上，工单描述那一栏就变成了「用户反馈商品问题」这种谁看了都不知道在说什么的话。这条规则就是拿来堵这个的。

最后一条约束的是「什么都想调一下」的倾向。用户说句「你好」也要去查一遍 FAQ，纯属浪费一次往返。

「工具清单可能动态变化」那句是第 8 章接入 MCP 之后补的，让模型接受自己看到的工具清单不是固定的，别把没见过的工具当成异常。

## 落库：四张表和 messages 的形状

### 建表

```sql
CREATE TABLE conversations (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '会话主键',
  user_id     VARCHAR(64)     NOT NULL                COMMENT '用户标识',
  status      ENUM('进行中','已转人工','已结束') NOT NULL DEFAULT '进行中' COMMENT '处理状态',
  ...
  PRIMARY KEY (id),
  KEY idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='客服会话';
```

本章建四张表，会话、消息、FAQ、工单。商品、订单、物流都走工具内的 mock，一张表都不建，这是刻意的取舍，本章要讲的是工具怎么接进模型，不是电商系统怎么建模。

DDL 顶上那句 `SET NAMES utf8mb4` 别删。ENUM 的取值是中文，客户端连接如果按 latin1 解析，中文会被 double-encode，建出来的表里 ENUM 值直接是乱码，插入时报的错还完全指不到这里。

### messages

```python
class Message(Base):
    __tablename__ = "messages"

    id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True)
    conversation_id: Mapped[int] = mapped_column(
        BigInteger, ForeignKey("conversations.id")
    )
    role: Mapped[str] = mapped_column(Enum("user", "assistant", "tool"))
    content: Mapped[str | None] = mapped_column(Text, nullable=True)
    tool_calls: Mapped[list | None] = mapped_column(JSON, nullable=True)
    tool_call_id: Mapped[str | None] = mapped_column(String(64), nullable=True)
```

这张表基本是把协议原样存了下来。`role` 的三个取值对齐 Chat Completions，`tool_calls` 存 assistant 那条消息发出的调用申请，`tool_call_id` 记录一条 tool 消息回的是哪一次调用。一轮里模型同时申请了三个工具，回来的三条结果就靠这个字段各自认领各自的申请。

`content` 允许为空，对应的正是前面提过的那种情况：模型这一轮只发工具调用、不说话，正文本来就没有。要是把这个字段设成 NOT NULL，第一次跑通工具调用就会插入失败。

这张表的形状从第 2 章定下来就没再改过，中间编排层换了两遍也没牵动它。

### 一个 session 里做两件事

```python
async def create_ticket(conversation_id: int, description: str, ticket_type: str) -> str:
    ticket_no = _gen_ticket_no()
    async with db.async_session() as s:
        s.add(
            Ticket(
                ticket_no=ticket_no,
                ...
            )
        )
        conv = await s.get(Conversation, conversation_id)
        if conv is not None:
            conv.status = "已转人工"
        await s.commit()
    return ticket_no
```

建工单和把会话状态改成「已转人工」在同一个 `async with` 里，一次 `commit` 落地。要是拆成两次提交，中间挂掉就会留下一张工单配一个还显示「进行中」的会话，人工那边看到的状态是错的。

工单号由 `_gen_ticket_no` 生成，时间戳加一个进程内自增。单进程够用，多副本部署会重号，真上生产得换成数据库序列或者雪花 ID。

## 单轮那圈循环现在在哪

第 2 章还有两个文件，`app/core/agent.py` 管单轮编排，`app/tools/infra.py` 管超时重试。这两个在最终代码里都不存在了。编排被第 5 章的 `app/graph/` 取代，执行基础设施被第 8 章的 `app/tools/engine.py` 取代，当年那份二十来行的注册表也被第 8 章的注册中心重写了。

它们干的事值得用一段话交代清楚。绑上工具调一次模型，拿到 `tool_calls` 之后并发执行，把每个工具的返回值包成一条 tool 消息回灌进对话，然后第二次调用模型，这次故意不绑工具，逼它必须用文字收敛。第二次不绑这个细节挺关键，绑着的话模型很容易再申请一轮工具，一步接一步停不下来。

代码没了，但它定下的消息协议还在，而且还在被依赖：

```python
def _views_from_state(state):
    """从终态 messages 重建工具调用/结果轨迹(供评估/单测看模型选了什么工具)。"""
    calls, results = [], []
    for m in state.get("messages", []):
        if isinstance(m, AIMessage) and m.tool_calls:
            for tc in m.tool_calls:
                calls.append(ToolCallView(id=tc["id"], name=tc["name"], args=tc["args"]))
        elif isinstance(m, ToolMessage):
            results.append(ToolResultView(
                tool_call_id=m.tool_call_id, name=m.name or "", ok=(m.status != "error"),
                content=m.content))
    return calls, results
```

这个函数从图跑完的终态消息里，把 `AIMessage` 上挂的 `tool_calls` 和所有 `ToolMessage` 挑出来，重建成一条「模型申请了什么、工具回了什么」的轨迹，给评估脚本和单测看。

它能这么写，恰恰因为消息还是那三种角色、那几个字段。编排从一圈手写循环换成了状态图，遍历消息的逻辑一个字没动。

接口对外的形状也留着当年的痕迹：

```python
class AgentResponse(BaseModel):
    conversation_id: int
    answer: str
    tool_calls: list[ToolCallView]
    tool_results: list[ToolResultView]
    suggested_actions: list = Field(default_factory=list)
```

前四项是第 2 章定的，`suggested_actions` 是第 5 章接图时加的，`interrupt` 是第 6 章做退款子流程时加的。
