这一章的核心是「意思相近」到底怎么算出来的，先花几分钟看这条视频建立直觉：

[RAG 视频：检索怎么算出「意思相近」.mp4]()

上一章收尾时，query\_faq 当场翻车了。faq 表里明明放着一条现成答案：「运费怎么算」对应「单笔订单满 99 元包邮，未满收取 10 元运费，偏远地区运费另计……」，用户问的是「邮费是多少？」，查询结果却是空。问题不在数据本身，问题出在查法：LIKE 认的是字面，用户嘴里的「邮费」，在「运费怎么算」里根本找不到，字面对不上就查空。



这一章要做的，是把 query\_faq 内部那套查法换掉，让它能听懂「邮费」和「运费」说的是同一件事。

![](<images/理论学习：RAG 原理与知识库构建-01-literal-vs-semantic-match.png>)

## 字面对得上是运气，对不上是常态

既然对不上才是常态，第一反应多半是给它补一张同义词表：给「运费」配上「邮费、快递费」，给「包邮」挂上「免运费、满多少免邮」。补是能补，可用户的说法无穷无尽，词表补到最后，维护的是一本谁也编不完的黑话词典。



词表这条路补不完，真正该换的是查找的方式本身。人理解「邮费是多少」，靠的是这几个字背后的意思，不是这几个字本身；要让机器也做到这一步，得先把「意思」这个抽象的东西变成机器能算的东西。这个思路早有名字，叫「向量化」，围着它搭起来的整套查、答机制，就是这一章的主角，「RAG」（Retrieval-Augmented Generation，检索增强生成）。

![](<images/理论学习：RAG 原理与知识库构建-02-synonym-table-never-ending.png>)

## RAG：先查资料，再张嘴回答

向量化本身只是把文字变成一串数字，这串数字就叫「向量」，让意思相近的内容在数字上也挨得近，具体怎么训练出这种效果，后面讲 Embedding 时再细说。这里先说下：为什么要费这么大功夫搭这一整套 RAG。



模型的知识来源于在训练那一刻的参数里，之后再没更新过。你上周刚改的退货政策，它不知道；你家新出的一款蓝牙耳机什么参数，它更不知道，压根没学过这些。碰到不知道的，模型不会老实说「我不知道」，它的天性是把下一个最像话的词接着往下编，编得越看着很对，错得越理直气壮。



RAG 就是用来解决这些问题的，你可以这样子想：给模型一个外挂的库，每次要回答问题，先去库里现查，查到什么就照着什么答，库里没有就老实说没有。库里的内容随时能更新，退货政策改了，换一份文档就行，不用重新训练模型。去库里捞相关的那几段，把捞回来的内容拼进模型这次要看的材料，让模型照着这些材料组织回答，RAG 这个名字拆开看就是这三步。



模型本身没变聪明一分，或者说这些问题的重点不是智商，而是需要数据。

![](<images/理论学习：RAG 原理与知识库构建-03-rag-read-before-answer.png>)

## 电商客服的知识库里该放什么

库要建，先得想清楚往里面放什么。第一反应可能是把历史客服对话存进去，这个想法得先纠正。原始对话记录本身东一句西一句，夹着寒暄和废话，信息噪声太多，不适合直接拿去检索，这个怎么用，下一节细说。



真正要放进知识库的，是权威、结构清楚的文档：退款退货政策、商品 FAQ（规格、功能、使用方法）、售后服务手册（保修条件、换货流程）、支付和发票 FAQ、促销活动规则，还有账号安全、评价规则。这几类文档有个共同点，内容相对稳定，但会更新。

![](<images/理论学习：RAG 原理与知识库构建-04-ecommerce-knowledge-base.png>)

## 知识从哪来：写文档的人，和聊过天的人

知识库这几类文档，总得有人先写出来、录进系统。其实 RAG 说到底干的是数据工程，知识的质量直接决定效果的上限，库里是垃圾，查出来的也是垃圾，模型再强也救不回来。往下讲的两条知识来源，人工整理和历史对话挖掘，缺一不可，这也是为什么单靠一条来源永远补不齐覆盖面。

![](<images/理论学习：RAG 原理与知识库构建-05-garbage-in-garbage-out.png>)

第一条来源是人工整理。退货政策、售后手册这类文档，由懂业务的人写成结构化的 Markdown，一级标题、二级标题、正文段落，层次分明。这么写是有讲究的，好处放到下一节讲切分时细说，这里先记住一句：每一块内容都要能独立说清一件事，不能东一句西一句掺在一起。



第二条来源是历史客服对话。聊天记录里全是真实用户会问的问题，这是一座金矿，但挖出来的只是原始矿石，得靠模型帮着炼成问答对。做法是拿出一批会话，喂给 LLM，让它从聊天里抽取出「用户问了什么、客服怎么答的」这样的问答对，写进一张暂存表，等所有批次都抽完，再整体过一遍去重，才是最终能用的问答对。



举个具体的，一段聊天里用户说「上次买的连衣裙偏大，想换小一码」，客服回「可以，签收后 7 天内都能申请换货，运费我们出」，模型抽出来就成了一条干净的问答对：问的是「买的衣服尺码不合适能不能换货」，答的是「支持签收后 7 天内换货，运费商家承担」。原话里的寒暄、口语和上下文依赖都被摘掉，只留下能直接入库检索的那一问一答。

![](<images/理论学习：RAG 原理与知识库构建-06-knowledge-sources-funnel.png>)

这里有个容易被忽略的细节：为什么要分批喂，不能一股脑把几千个会话全塞给模型？两个原因。第一个好懂，模型的上下文有硬性 token 上限，成千上万的会话的文字量塞不进去。第二个原因更值得说道：就算真塞得下，数据一多，抽取质量反而会往下掉。



一是幻觉变多。上下文又长又杂，模型会分心，把不同会话的内容串味，硬凑出一条压根没出现过的问答对，这个现象有个说法叫「上下文焦虑」，材料越堆越多，模型越读越不专心。



另一点是准确率往下掉，这跟一个叫「Lost in the Middle」的现象有关系：喂给模型的材料排成一长条，开头结尾模型看得认真，塞在中间那部分反倒容易被一带而过，该抽的问答对没抽出来。再加上原始对话本身噪音就大，寒暄、跑题、答非所问都掺在里头，喂得越多，信噪比只会越差。



分批就是把这两个问题一起摁下去，一批只放几十个会话，模型读得过来，也不容易串味。实际做法是每批导出一份会话记录文件，批量跑完写进暂存表，等所有批次跑完，再把暂存表里的内容整体拿给模型去重一遍，形成最终干净的问答对，这才收尾入库。

![](<images/理论学习：RAG 原理与知识库构建-07-batch-extraction-focus.png>)

## 两条流水线：离线建库，在线问答

知识来源理清楚了，该看整套 RAG 是怎么运转的了，拆开看其实就两条流水线。



一条叫「离线建库」，做的是把文档变成能查的库：解析、切分、向量化、存起来。这条线不用等用户提问，提前跑，跑一次或者定期更新一次就够，用户完全感知不到。



另一条叫「在线问答」，用户每问一句，都要走一遍：把问题变成向量、去库里查、把查到的内容交给模型生成回答，这条线上的每一步都被用户的等待盯着，跑一次就要交一次答卷。



两条线各干各的，接口却只有一个，「向量库」。离线那条线辛辛苦苦建好的库，就是在线问答要查的那个库，库建得好不好，直接决定在线这条线查不查得着。



这一章接下来按这两条线的顺序走，先走离线建库，从文档解析一路讲到怎么把切好的知识存进库里；再走在线问答，不过这一章只跑通「向量检索」这一条路径，让 query\_faq 先能查着，更精细的检索优化留到下一章。

![](<images/理论学习：RAG 原理与知识库构建-08-offline-online-rag-pipelines.png>)

## 解析：文档读错，后面全白搭

文档到手，第一步是先把它读对，不是急着切。读错一个字，后面切分、检索、生成再强也救不回来。离线建库这第一步要处理的，是商品规格表、价格表、政策文档、售后手册这些原始文件，把它们变成干净的文本。可轮到电商场景的文档，有几个坑躲不开。



最要命的一个是无边框表格。商品规格表、SKU 价格表，很多时候就是靠空格对齐撑出来的表格，连一根边框线都没有。解析器认不出行列关系，读出来的字段就可能对错了行。想象一张五十行的价格表，某个型号搭配某个价格这一行，解析器把价格那一列错位对到了下一行的型号上，用户拿这个错报价去下单，退款投诉全跟着来。碰到这类无边框表格，得靠更强的表格识别能力去补，普通的文本抽取顶不住。

![](<images/理论学习：RAG 原理与知识库构建-09-borderless-table-misalignment.png>)

多栏排版倒是不用太操心。政策文档、促销规则这类，多数是单栏往下写，顶多加个目录，解析时按顺序读下来基本不会乱。



还有一类情况会遇到，但出现得不算多：印章遮挡和扫描件模糊。商家资质证明、品牌授权书、盖章合同，这些本来就是扫描件，盖的章有时候正好压在关键文字上，扫描分辨率低时字迹也会发虚。这类文档归到重型解析通道处理，先把印章层和文字层分开，文字层单独做 OCR，模糊的先做一遍图像增强再识别。这块本课程点到为止，交给现成的解析工具去做就行，不深挖。



这几种坑处理思路不一样，工程上不能一刀切都上最贵最慢的解析方案。常见做法是先加一层分类判断，识别这份文档是不是无边框表格、是不是模糊扫描件，只有判定为难啃的那一小撮，才送进重型通道，剩下大多数走轻量通道，平均下来解析速度和准确率都能兼顾。

![](<images/理论学习：RAG 原理与知识库构建-10-document-parser-routing.png>)

解析完还有一件小事顺手做，建一份电商领域的术语词库。SKU、满减、花呗分期、运费险，这些词在通用语料里不一定有，或者不一定是最准确最符合我们业务的描述，清洗文本、后面切分识别文档结构时，有这份词库垫底，程序能更准地认出这些术语。

## 切分是隐形地基：切歪一寸，模型就敢乱答

文档解析干净了，下一步是「切分」，把一篇长文档剪成一个个小块，方便检索时按需去取。这步听着更简单，不就是拿把刀切吗？可切在哪一刀呢，这可是决定模型将来能不能看到完整的信息。



拿前面那条退货政策展开写细一点，可能就是这样一句：「支持 7 天无理由退货，商品需保持完好，以下情况除外：定制商品、已拆封的个人护理类商品、赠品需与商品一并退回」。



要是切分的时候不管三七二十一，数够字数就切一刀，正好切在「以下情况除外」这几个字后面，前半句单独成一块，「支持 7 天无理由退货，商品需保持完好」，后面那串例外情况被扔进了下一块。



用户问「定制款的杯子能退吗」，检索命中的偏偏是前半块，模型看到的是一句「支持 7 天无理由退货，商品需保持完好」，读不出后面还有例外，大大方方回一句「可以退」。定制商品明明是不退的，这就出问题了。



因为这个切分导致的模型乱答，也不能怪模型，是切分先把信息切没了。这就是为什么切分被称作 RAG 的地基，地基歪一寸，上层的检索、生成再强也救不回来。

![](<images/理论学习：RAG 原理与知识库构建-11-bad-chunking-policy-exception.png>)

这里我们按三代演进来讲，一代代往前推，每一代都是被上一代的毛病逼出来的。



第一代最直接，按固定长度切，比如每 500 字砍一刀，实现起来一行代码的事。毛病也在这，它完全不管内容，句子被从中间砍断的概率不低，前面那个退货条款的例子就是这么翻车的。切出来这块的正文就剩前半句：

```json
{ "answer": "支持 7 天无理由退货，商品需保持完好" }
```

第二代改成按句子边界切，再加上相邻块之间留一段重叠，防止关键信息刚好卡在边界上被漏掉。这一代解决了句子被砍断的问题，却漏了另一层，章节的层级关系。用户想精确落到某一节，比如指名要看「退货政策」里「无理由退货」是怎么规定的，句子级切分只保证每块是完整的句子，块和块之间不带章节归属，模型拿到一段话却不知道它挂在文档的哪一节底下，这类按章节定位、要溯源的问题，照样接不住。例外条款这下完整留在了一块里，可字段里还是没有它出自哪一节：

```json
{ "answer": "支持 7 天无理由退货，商品需保持完好，以下情况除外：定制商品、已拆封的个人护理类商品、赠品需与商品一并退回。" }
```

第三代才是现在站得住脚的方案，「结构感知切分」，按 Markdown 的标题层级去切，一级标题、二级标题各自成一层，每一块不仅语义独立完整，还带着自己在文档里的层级路径。前面提过，人工整理知识时要求按标题分层，道理就在这，结构感知切分靠的正是这份结构。这代切出来的块，除了完整正文，还多挂一个 section\_path 记着它的层级：

```json
{
  "answer": "支持 7 天无理由退货，商品需保持完好，以下情况除外：定制商品、已拆封的个人护理类商品、赠品需与商品一并退回。",
  "section_path": "退货政策 > 无理由退货"
}
```
这一块知道自己出自「退货政策」的「无理由退货」这一节，按章节定位、给答案标引用溯源，靠的都是这条 section\_path。



结构感知最吃本项目这套规整 Markdown 的红利，但它不是切分的唯一方式。碰上没有清晰标题层级的长文本，按相邻句子向量相似度找断点的「语义切分」更合适；还有一种做法是每块切好后先补一段交代它在全文里位置和角色的上下文，再连着上下文一起向量化，非结构化材料上召回能拉高不少。按文档形态挑着用就行。

![](<images/理论学习：RAG 原理与知识库构建-12-chunking-strategy-evolution.png>)

还有一些技巧或者细节注意。



文档超长的章节，先按小节切，小节还长再按段落切，段落还长才落到句子，一级级往下让，优先保住更大的语义单元。



重叠也不是简单地固定截一段字数，得裁到最近的一个句号，别把半截话带过去，带半句进来非但不补信息，反而添噪音。



规格表、价格表这类大表格按行切时，还有一个容易漏的细节，每一块都要把表头复制一份带过去，不然模型拿到的只是表格中间几行数字，压根分不清哪一列是尺码、哪一列是库存，价格又藏在哪一列，回答不了某个型号多少钱。

![](<images/理论学习：RAG 原理与知识库构建-13-table-header-per-chunk.png>)

## 从文字到向量：Embedding 怎么选

文档切好了，接下来要把每一块变成向量，这一步叫「Embedding」，前面已经点过它的作用：把文字变成一串数字，让意思相近的内容在数字上也挨得近。具体怎么训练出一个模型出这种效果，不是这门课要深挖的东西，这里要解决的是应用层的，更实际的问题，选哪个模型。



电商客服这个场景，一般都是企业级的，数据不能泄漏出去，私有化部署是硬要求；有时候还需要拿自家语料给它做点微调，得选一个开源、能自己微调的；中文英文的客服问题都可能出现，两边都得顶得住。这三条一列出来，闭源的商用 API 直接出局，不管它效果多好，数据出不去、进不了私有环境，想在自己这边接着微调也就无从谈起。不过这只是企业级实际落地时的情况，我们学习和课程演示用云端的就行，避免本地部署太重。



商用的 OpenAI text-embedding、Voyage、Cohere，效果确实不差，可前面立的那几条硬门槛它们迈不过去；再加上高频调用按 token 计费，账单越滚越大，本项目只拿它们当个对照基准，不选。

![](<images/理论学习：RAG 原理与知识库构建-14-embedding-model-requirements.png>)

排除商用 API 之后，剩下的是开源多语言模型这条主线，几个候选摆在这：BGE-M3、Qwen3-Embedding、gte-multilingual-base、jina-embeddings-v3。



BGE-M3 体量不大，支持 100 多种语言，能处理长达 8192 token 的文本，中英文的语义检索能力都稳，还方便后续做领域微调。



Qwen3-Embedding 走的是同一条路，多语言表现更强一档，同样开源可微调，不过它的强项在 4B、8B 这种大参数档，也提供 0.6B 的轻量档。



gte-multilingual-base 用的是 Apache 2.0 许可，商用没障碍，编码器架构小巧、跑得快，长文本和中英文检索也都撑得住，能力够用；只是放在 BGE-M3 边上没什么非它不可的亮点，生产落地的案例和踩坑资料也薄一些，就往后排了。



jina-embeddings-v3 卡在许可上，它开源出来的权重是 CC BY-NC 非商用协议，真要商用得另找 Jina 谈授权，跟我们这套要商用、要私有化的场景对不上，能力再全也只能放备选。



所以主要是看BGE-M3和Qwen3-Embedding。



这里插一句容易被误解的事：是不是模型参数越大，检索效果就一定越好？未必。



真实情况是，检索质量的瓶颈很少卡在 Embedding 的参数规模上，更多卡在切分切得好不好、检索是不是只用了单一路径、有没有做重排、要不要针对领域微调这几步。



一个轻量模型配好后面这几步，召回精度也同样足够。电商客服这个场景又刚好在几个维度上都吃这套轻量路线的红利，用户问题通常不长，知识范围也有限，就是自家商品加自家政策，不是一个开放域的百科全书。真要上到 4B、8B 这种大档模型，是给语料特别庞杂、跨语种细微差异特别多的场景准备的，所以我们暂时选型为0.6B。

![](<images/理论学习：RAG 原理与知识库构建-15-light-model-with-retrieval-stack.png>)

同样是轻量档，BGE-M3 和 Qwen3-Embedding-0.6B 怎么选？



BGE-M3 中英文双语都顶得住，支持长文本，也支持微调，生产环境用得多，各家向量库把它当一等公民对待，踩过的坑网上一搜一大把，这些工程上的便利，是选型时不能忽略的加分项。所以本项目默认选它，想换的话 Qwen3-Embedding-0.6B 随时能接上。



选型的优先级排下来是这样：数据合规放在最前面，过了这一关才看中英文表现和能不能微调，再往后是向量维度带来的存储成本，最后才轮到自己部署要花多少算力。



向量维度越高，表达力强一些，但存储和检索的成本也跟着涨。BGE-M3 输出的是固定 1024 维，想砍维度省成本得换模型：有一类用「MRL」训练的模型，把重要信息压在靠前的维度里，截短了用精度损失不大，本章备选的 Qwen3-Embedding 就支持这么按需设定维度，OpenAI 的 text-embedding-3 也是这么做的，预算紧的时候是个退路。



另外还有个细节，有些模型会给 query 端单独加一段检索指令或前缀，跟 document 端区别对待，能再抬一点检索效果，像 E5 的 `query:`、Qwen3-Embedding 的 query 指令都是这么干的；BGE-M3 默认不用加这层指令，query 和 document 一视同仁。

![](<images/理论学习：RAG 原理与知识库构建-16-mrl-vector-truncation.png>)

最终结论，默认用 BGE-M3，当然也可以换成同档的 Qwen3-Embedding-0.6B，谁更适合本项目，还是得拿自己的电商评估集跑一遍。

## 向量放哪里：向量库怎么选

向量算出来了，得有个地方存，还要能在几十万甚至上百万条向量里，几十毫秒内找出最相似的那几个，这件事交给向量库。



向量库主流的有：FAISS、ChromaDB、pgvector、Milvus 和 Qdrant。



FAISS 严格说只是个检索库，不带服务层，只管存向量和一个数字 ID，连原文都不存，连按字段过滤都做不到，要另外配一个地方存原文，demo 阶段、单进程跑跑还行。



ChromaDB 走的是开箱即用路线，嵌入式部署，开发阶段用起来省心，但撑不住生产环境的并发规模。



pgvector 是给 PostgreSQL 装了个向量检索的插件，复用现成的数据库，SQL 过滤和事务这些能力天生就有，中小规模够用。



Milvus 和 Qdrant 是专门为向量检索设计的分布式系统，索引种类丰富，原生支持按标量字段过滤，扛得住大规模、高并发。

![](<images/理论学习：RAG 原理与知识库构建-17-vector-database-options.png>)

本项目选 Milvus。电商客服这套系统要扛的向量规模会持续涨，按品类、按店铺过滤这种标量查询也少不了，Milvus 这两条都占。它还有个面向未来的好处，2.5 版本起自带了 BM25 全文检索能力，dense 向量和 BM25 能同库共存，方便下一章说的混合检索。当然，嫌 Milvus 部署起来重，然后项目是属于个人开发级别的，ChromaDB 可以当轻量替代先跑起来。



存进 Milvus 靠的是一种叫「ANN」的检索方式，近似最近邻。「近似」这两个字说的是，它不保证每次都找到数学意义上绝对最相似的那一条，而是拿一点点精度换来数量级的速度提升。要是真按逐条比对的笨办法去算相似度，几十万条向量，一次查询都够用户等到不耐烦。



常见的索引方式有两种，「HNSW」建的是一张多层的图，从稀疏的顶层入口往下钻，顺着邻居一路走到最相似的点附近，查得快、召回也高，代价是建图占内存、写入慢一些，适合读多写少的场景。



「IVF」先把向量聚成一堆堆的簇，查询来了只在最近的几个簇里精算，跳过其余，建库快、省内存，召回效果跟着要查几个簇这个参数走，规模越大越划算。



两种各有取舍，规模不大、追求低延迟选 HNSW，规模特别大、能接受调参换召回选 IVF。

![](<images/理论学习：RAG 原理与知识库构建-18-hnsw-vs-ivf-indexes.png>)

## 向量库和业务库，为什么要分家

向量库能查了，原文放哪？顺手把原文也塞进 Milvus 不就完了？这一步得慢下来想清楚。



向量是从原文算出来的派生品，这层计算有损，工程上不会拿着一串数字去反推原文。既然是派生的，它有个特点，随时能重算，原文没变，重新跑一遍 Embedding 就能拿到一份一模一样的向量。反过来，要是把原文也弄丢了，是真的补不回来，原文这份事实来源必须留一份权威落点。



再往下想，后面微调 Embedding、调整切分策略、换向量维度，这些改动都要求把向量全量重生成一遍，原文要是稳当留在别处，重新生成就是重新跑一遍脚本的事。而且向量库专精的是按相似度查找，业务上还可能对原文进行关系型查询，真要它兼顾事务、SQL 过滤、被好几个服务同时读，硬塞给它并不合适，这些交给关系型数据库做得更顺手。

![](<images/理论学习：RAG 原理与知识库构建-19-vector-not-source-of-truth.png>)

原文放哪、跟向量库怎么搭，有几种方案。



最轻的是 FAISS 配一个 sidecar，拿 pickle 或者 SQLite 存原文，FAISS 里只留一个整数 ID 对应过去，零额外服务，单进程跑 demo 够用。



再往上一档，FAISS 加 MySQL，靠一个 vectorId 字段关联，业务字段多起来、要 SQL 过滤、好几个服务要共读原文，这时候升级到关系库就划算了。



第三种是 Milvus 或者 Qdrant 干脆做成一体，原文和各种元数据直接进向量库自带的存储，原生支持标量过滤，代价是多运维一套分布式系统。



第四种是本项目的选法，把第二、第三档的长处并到一起。正文连同检索要用的元数据直接进 Milvus，它既能按相似度召回，下一章还能在同一份正文上开原生 BM25；MySQL 则当权威事实源和业务底座，原文在这里留一份权威落点，会话、工单、飞轮待审这些要事务、要 SQL 过滤、要被多个服务共读的数据也都搁这，靠 vectorId 跟 Milvus 那条记录对上。检索时直接从 Milvus 取回正文和元数据就够用，要补全整条业务上下文，再拿主键回 MySQL 捞。

![](<images/理论学习：RAG 原理与知识库构建-20-storage-layout-options.png>)

## 建库怎么落地：双写和一个状态位

存储方案定了，落到具体流程上，一个知识块从切好到能被检索到，要走一趟「双写」。



先把切好的这块内容存进 MySQL，这时候它还没变成向量，状态标成「待向量化」，vectorId 那一列先留空。接着拿它去调用 Embedding 模型算出向量，把向量连同正文、检索用的元数据一起写进 Milvus，Milvus 会给这条记录分配一个 ID。最后一步是回写，把这个 vectorId 补回 MySQL 对应的那条记录，状态改成「已向量化」。



多记这一个状态位，成本很低，一个布尔值的事，换来的好处却不小：随时能扫一遍 MySQL，揪出还卡在「待向量化」的那些记录，说明它们上一次向量化中途失败了，直接拿这批记录重跑一遍就行，不用整库推倒重来。落库按 chunk 的主键做幂等 upsert，同一条记录重复写入不会出现两份。



这一整套双写眼下是同步走的，切完一块就立刻跑完这四步。等哪天离线建库的数据量非常大，一条条同步建向量太慢，就可以换成异步队列：先把切好的块全写进 MySQL 落库、标成「待向量化」，后台再顺着这批「待向量化」记录去异步建向量，建完一条改一条状态。

![](<images/理论学习：RAG 原理与知识库构建-21-vectorization-double-write.png>)

## 一条 chunk 长什么样：不止是正文

每一条知识落库时，不只是一段光秃秃的正文，还挂着好几个字段，拼成一个结构化的 JSON。这里先说清楚一件容易搞混的事：这坨 JSON 本身不会整个拿去做向量化，真正送进 Embedding 模型的，只是把 JSON 里几个正文相关的字段拼接起来的那一段文本，其余字段是给检索和溯源用的元信息，不进向量。



不管哪一类内容，送进向量的都是 category（分类）、questions（问题）、answer（答案）三格拼起来的文本，区别只在 questions 这格从哪里来。商品 FAQ、从历史对话里挖出来的问答对，本身就带着真实问题，questions 填 FAQ 标题或者用户的真实问法。政策文档、售后手册这类纯文档没有天然问题，就用它所在的章节标题来当 questions，比如「例外情况」，category 填上级标题路径，正文落进 answer，照样凑齐这三格。



除了拼进向量化文本的那几个字段，每条 chunk 还带四类元数据，它们都不进向量。



section\_path 记录这块内容在文档里的章节路径，答案要溯源到原文时靠它定位。



content\_type 标出这块内容是文字、表格还是图片。



is\_key\_clause 标记这块是不是退货、售后这类关键条款，留作检索排序时的一个加权信号。



prev\_chunk\_id 和 next\_chunk\_id 记住相邻的块是谁，遇到语义不完整的情况能自动拉前后块补全。



is\_key\_clause 这个字段正好接上前面切分那节的反例。那条被切断的退货条款，要是当时就标成关键条款，入库前就得保证它完整成一块，不能被随手一刀切开，这个坑从源头上就不会出现。section\_path 则是一条贯穿全流程的暗线，切分时把它存进去，检索时带着它一起走，后面生成答案要做引用溯源，靠的也是这条路径，把答案里的编号映射回原文。



把上面这些字段落到实处，一条 chunk 大致就长这样。先看带问题的这类，商品 FAQ、从对话里挖出来的问答对都归它：

```json
{
  "category": "退换货",
  "questions": ["买的鞋子能不能退", "七天无理由适用哪些商品"],
  "answer": "支持 7 天无理由退货，商品需保持完好，定制类商品除外。",
  "section_path": "退货政策 > 无理由退货",
  "content_type": "text",
  "is_key_clause": true,
  "prev_chunk_id": "kb_00417",
  "next_chunk_id": "kb_00419"
}
```

送进 Embedding 的，是 category、questions、answer 这三格拼起来的一段文本，下面那几格不进向量，留给检索过滤和溯源。



再看没有天然问题的纯文档，政策条款、售后手册归它，questions 那格填的是它所在的章节标题，正文落在 answer 里：

```json
{
  "category": "退货政策-无理由退货",
  "questions": ["例外情况"],
  "answer": "以下情况不支持无理由退货：定制商品、已拆封的个人护理类商品、赠品需与商品一并退回。",
  "section_path": "退货政策 > 无理由退货 > 例外情况",
  "content_type": "text",
  "is_key_clause": true,
  "prev_chunk_id": "kb_00418",
  "next_chunk_id": "kb_00420"
}
```
这类照样是 category、questions、answer 三格向量化，questions 填本节标题、category 填上级标题路径，章节上下文就这么进了向量，让模型知道这段话挂在文档的哪一节底下。section\_path 只留在元数据里管溯源，不跟着进向量。两类内容共用同一套字段和同一种拼法，差别只在 questions 是天然问题还是章节标题。

![](<images/理论学习：RAG 原理与知识库构建-22-chunk-storage-structure.png>)

## 在线问答：这一章先跑通向量这一路

离线那条线走完了，文档解析、切分、向量化、落库，一条完整的知识生产线搭起来了。该在线问答这条线跑起来了，用户一句「邮费是多少」进来，该怎么查？



流程不复杂：把这句话送进同一个 Embedding 模型，编码成一条向量，拿这条向量去 Milvus 里按相似度检索，取排名最靠前的 Top-K 条，一并交给模型。这一章先只走这一路，向量检索单路召回，更完整的检索链路留到下一章。



LangChain 把这套组合封装了，三个组件拼起来就是一条检索链，Embeddings 管向量化，向量库管存和查，Retriever 把这两者包成一个统一的检索接口。代码大致是这样：

```python
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_milvus import Milvus

embeddings = HuggingFaceEmbeddings(model_name="BAAI/bge-m3")
vector_store = Milvus(
    embedding_function=embeddings,
    connection_args={"uri": "http://localhost:19530"},
    collection_name="ecommerce_kb",
)
retriever = vector_store.as_retriever(search_kwargs={"k": 10})

docs = retriever.invoke("邮费是多少")
```

`HuggingFaceEmbeddings` 包一层 BGE-M3，负责把文字变向量；`Milvus` 这个向量库对象接好连接信息和集合名，建库时往这里写，查询时也从这里查；`as_retriever` 把向量库包成一个「拿问题换文档」的检索器，`k=10` 是每次查询取多少条候选。最后一行 `retriever.invoke` 一次调用，内部干的就是编码问题、去 Milvus 查相似度、把命中的 chunk 连着它的元数据一起吐出来。



query\_faq 内部实现从这一刻起就换掉了，里面连着这套检索链，对外还是原来那份「进一个问题，出一段答案」的契约，调用方一行都不用改。

![](<images/理论学习：RAG 原理与知识库构建-23-vector-search-hit-policy.png>)

## 回到那句「邮费是多少」

回到最初那句话，这次再问一遍「邮费是多少」，向量检索不看字面重不重合，看的是语义挨不挨得近。「邮费」和「运费」在向量空间里离得很近，检索稳稳命中，query\_faq 终于能给出正经答案。之前补不完的同义词词典，现在也用不上了，「快递费怎么收」「多少钱包邮」，这些问法向量检索都能查到。



不过这条链路眼下只跑通了向量单路，还有一类问题它不擅长应付。用户报出一串 SKU 编号、或者报个具体型号，这类查询看重的是字面对得上，向量检索认的是语义相近，反而容易把结果晃到几个长得像但答非所问的商品或文档上。这个缺口留到下一章再补。

![](<images/理论学习：RAG 原理与知识库构建-24-rag-faq-final-hit.png>)
