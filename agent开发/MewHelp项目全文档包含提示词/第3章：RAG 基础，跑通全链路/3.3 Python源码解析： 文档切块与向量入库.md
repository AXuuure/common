## 嵌入客户端

### embeddings.py

```python
def _client() -> AsyncOpenAI:
    """直连嵌入上游(硅基流动的 bge-m3,OpenAI 兼容)。
    进程内单例:复用同一 httpx 连接池,避免每次 embed 新建客户端累积连接/fd。"""
    global _CLIENT
    if _CLIENT is None:
        _CLIENT = AsyncOpenAI(base_url=settings.embed_base_url, api_key=settings.embed_api_key)
    return _CLIENT


async def embed_texts(texts: list[str]) -> list[list[float]]:
    resp = await _client().embeddings.create(model=settings.embed_model, input=texts)
    return [d.embedding for d in resp.data]


async def embed_query(text: str) -> list[float]:
    return (await embed_texts([text]))[0]
```

整个文件就这么点东西。单例挡的是连接泄漏，每次 embed 都新建一个 `AsyncOpenAI` 的话，底下的 httpx 连接池和文件描述符会一路累积，建库那种成百上千次调用很快就撑爆。

两个口子分工明确。建库时一批几十条走 `embed_texts`，在线检索一次就一条走 `embed_query`，后者直接套前者，不重复写一遍请求逻辑。

嵌入上游和聊天上游是 `.env` 里分开的两组配置。这两件事的模型选型完全不相干，聊天要的是推理能力，嵌入要的是中文语义表示，供应商也常常不是同一家。

## 切块

### split\_sections 与 recursive\_split

切分分两级。先按 Markdown 的标题层级切成小节，小节还超长的再按字符递归切下去。

```python
HEADERS = [("#", "h1"), ("##", "h2"), ("###", "h3"), ("####", "h4")]
# 中文无词边界,分隔符优先段落/换行,再句末标点,最后逐字
CJK_SEPARATORS = ["\n\n", "\n", "。", "！", "？", "；", "!", "?", ";", "，", " ", ""]


def split_sections(md: str) -> list[Document]:
    splitter = MarkdownHeaderTextSplitter(headers_to_split_on=HEADERS, strip_headers=True)
    return splitter.split_text(md)
```

`CJK_SEPARATORS` 这张表得自己写。库里默认那套是给英文准备的，段落、换行之后就是空格，靠空格找词边界。中文没有词边界，默认表落到中文文档上等于只有段落和换行两级能用，再切不动就直接逐字硬切，一句话被拦腰截断是常事。

自己排的这一版在换行之后插了一层句末标点，句号、感叹号、问号、分号，再往后才是逗号和空格，最后才是逐字。切下来至少能落在句子或者分句的边界上。

```python
def recursive_split(text: str, chunk_size: int, chunk_overlap: int = 0) -> list[str]:
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size, chunk_overlap=chunk_overlap,
        separators=CJK_SEPARATORS, is_separator_regex=False, length_function=len,
    )
    return splitter.split_text(text)
```

注意 `strip_headers=True`，标题从正文里被摘掉了。标题不是丢了，它在 `sec.metadata` 里，等会装配的时候另有用处。

### apply\_sentence\_overlap

`recursive_split` 自带 `chunk_overlap` 参数，为什么不直接用？因为它按字符数取重叠。前一块末尾数三十个字接到后一块开头，接过来的多半是半截话，「非质量问题的换货运」，读的人和模型都拼不出后面是什么。

这里另起一层，按整句取：

```python
def _trailing_sentences(text: str, max_chars: int) -> str:
    """取 text 结尾若干**完整句**作为重叠,总长尽量不超过 max_chars;
    单句超长则整句保留(优先「不留半截话」)。"""
    out: list[str] = []
    total = 0
    for s in reversed(_split_sentences(text)):
        if out and total + len(s) > max_chars:
            break
        out.insert(0, s)
        total += len(s)
    return "".join(out)
```

从文本末尾倒着一句一句凑，凑到快超 `max_chars` 就停。`if out and` 那个 `out and` 是关键，它保证第一句无论多长都会被收进来。宁可这一块的重叠超一点，也不给下一块接一个半截句子。

```python
def apply_sentence_overlap(chunks: list[str], overlap: int) -> list[str]:
    if not chunks:
        return []
    out = [chunks[0]]
    for i in range(1, len(chunks)):
        ov = _trailing_sentences(chunks[i - 1], overlap)
        out.append(ov + chunks[i] if ov else chunks[i])
    return out
```

既然重叠这件事整个交给了这一层，调用 `recursive_split` 时就传 `chunk_overlap=0`，让它老老实实只管切。

### split\_table\_rows

表格是另一种切法。按字符切表格的后果很直观，除了第一块，后面每一块都没有表头，「7 天」这个格子孤零零躺在那里，谁也不知道它是哪一列的值。

先得认出表格在哪：

```python
def _find_table_header(lines: list[str]) -> int:
    """返回表头行下标(其后紧跟 --- 分隔行);无表格返回 -1。
    允许表格前有若干散文行(不再要求首行即表头)。"""
    for i in range(len(lines) - 1):
        if (lines[i].lstrip().startswith("|")
                and _TABLE_SEP_RE.match(lines[i + 1]) and "-" in lines[i + 1]):
            return i
    return -1
```

判据是「这行以竖线开头，下一行是分隔行」。允许表格前面有几行散文说明，真实文档里表格上面常常先有一段导语。

```python
def split_table_rows(table_md: str, max_rows: int) -> list[str]:
    ...
    lines = [ln for ln in table_md.strip().splitlines() if ln.strip()]
    idx = _find_table_header(lines)
    if idx == -1:
        return [table_md.strip()]
    preamble, header, sep, rows = lines[:idx], lines[idx], lines[idx + 1], lines[idx + 2:]
    if len(rows) <= max_rows:
        return [table_md.strip()]
    out: list[str] = []
    for j, i in enumerate(range(0, len(rows), max_rows)):
        group = rows[i:i + max_rows]
        block = [*preamble, header, sep, *group] if j == 0 else [header, sep, *group]
        out.append("\n".join(block))
    return out
```

每一块都重贴表头行和分隔行，切出来的每块都是一张完整的小表。`preamble` 那段散文只跟着首块走，重复到每一块只会稀释语义。行数本来就不多的表格直接整块返回，不做无谓切分。

### build\_chunks

上面那几个原语在这里接成一条线：


这个字段映射有点绕，但它对应的是一个现实问题。政策文档、售后手册这类东西没有天然的「问题」，只有章节标题。硬要给每个块编一个问句，编出来的多半跟用户真实问法对不上，倒不如就用标题，把「运费怎么算」这类真实问法留给 FAQ 类文档和后面挖出来的知识。

关键条款单独打个标：

只看标题加正文前四十个字，因为关键词出现在开头才说明这一块讲的就是这件事。整块搜的话，一段讲商品介绍的正文里顺带提了句「运费另计」也会被标成关键条款，标记就没有区分度了。

## 落库与向量库

### 两个库各存什么

```sql
-- 本章新建:knowledge_chunks(知识库原文权威源)
-- 向量落 Milvus 集合 knowledge(非 MySQL,DDL 不含);MySQL 存原文 + 双写状态
-- category + questions + answer 三格拼成向量化文本;其余字段是元数据,只存不进向量
```

分工写在建表 DDL 的注释里。MySQL 是权威源，存原文和双写状态。Milvus 只存向量和检索时要用的那几个字段。要改知识、要审核、要看历史，都在 MySQL 这边，Milvus 随时可以整个删掉重建。

`vectorize_status` 这个 ENUM 只有 `pending` 和 `done` 两个值，整条双写幂等的支点就在它身上。

### ensure\_collection

```python
    if client is _CLIENT and collection in _ensured:
        return
    if client.has_collection(collection):
        client.load_collection(collection)
    else:
        schema = client.create_schema(auto_id=False)
        schema.add_field("id", DataType.INT64, is_primary=True)
        schema.add_field("dense", DataType.FLOAT_VECTOR, dim=DIM)
```

最重要的是 `auto_id=False`。主键不让 Milvus 自己生成，直接用 MySQL 那边 `knowledge_chunks.id` 的值，两个库共享同一个身份。这一个决定换来的是天然幂等，重跑向量化时按 id 做 upsert，同一条覆盖过去，不会插出第二份。

```python
        index_params = client.prepare_index_params()
        index_params.add_index(field_name="dense", index_type="AUTOINDEX", metric_type="COSINE")
```

建集合这件事在每次写入和检索前都会调一遍，所以得幂等。`_ensured` 那个集合缓存挡的是重复的 `has_collection` 网络往返，只对进程内单例生效，测试传进来的临时客户端各自 ensure 各自的。

函数体里还有 `text` 字段、`sparse` 字段和那个 BM25 Function，连同 `section_path` 这些标量字段，都是第 4 章做混合检索时加的，本章用不到。同理 `hybrid_search`、`bm25_search` 和文件顶上那个单线程执行器 `acall` 也归第 4 章。`acall` 治的问题倒是本章埋下的，同步 pymilvus 客户端在 async 服务里跨线程共享会间歇性返回空结果，那时候还没暴露出来。

### write\_pending

```python
async def write_pending(chunks: list[Chunk]) -> list[int]:
    """按顺序把一份文档的 chunks 写入 MySQL(status=pending),并在同文档内连 prev/next 指针。"""
    ids: list[int] = []
    for c in chunks:
        cid = await repository.insert_knowledge_chunk(
            c.category, c.questions, c.answer,
            section_path=c.section_path, content_type=c.content_type,
            is_key_clause=c.is_key_clause,
        )
        ids.append(cid)
    for i, cid in enumerate(ids):
        prev_id = ids[i - 1] if i > 0 else None
        next_id = ids[i + 1] if i < len(ids) - 1 else None
        await repository.set_chunk_neighbors(cid, prev_id, next_id)
    return ids
```

两趟循环，不是写复杂了。第一趟插入才能拿到自增 id，邻居的 id 那时候还不存在，只能等全插完再回头把 `prev` 和 `next` 连上。

这一步写进去的全是 `pending`，向量化是另一个独立动作。

### vectorize\_pending


拼向量化文本用的正是 DDL 注释里说的那三格，`category`、`questions`、`answer` 换行拼起来。别的字段不进向量，它们是溯源和过滤用的元数据。

```python
            await repository.mark_chunk_vectorized(r.id, str(r.id))
```

幂等就成立在这两句上。upsert 按 MySQL 的 id 覆盖同一条向量，回填之后状态变 `done`，下次 `list_pending_chunks` 就取不到它了。跑到一半断电也不怕，已经处理完的那几批是 `done`，重跑从剩下的接着做，不会重复也不会漏。

## 从对话里挖知识

文档是一个来源，历史对话是另一个。客服跟用户来回聊的那些内容里藏着不少可复用的问答，`mining.py` 干的就是把它们抽出来。

### QaExtraction

```python
class QaExtraction(BaseModel):
    """LLM 结构化输出 schema:用两个并列标量数组一一对应。
    实测 glm-5.2 的 anthropic 兼容上游对嵌套对象数组(list[对象])的工具 schema 会 502,
    标量 list[str] 正常,故不用 list[QaPair],改并列数组规避。"""

    questions: list[str] = Field(
        default_factory=list, description="问法列表,与 answers 一一对应;无可复用问答则为空"
    )
```

按直觉这里该写 `list[QaPair]`，一个问题配一个答案，结构清清楚楚。实测下来上游对这种嵌套对象数组的工具 schema 直接返回 502，换成两个并列的标量数组就正常。

这类坑绕过去比死磕划算，但代价得自己扛：两个数组的对齐关系从此没人替你保证了。

```python
    qs, ans = result.questions, result.answers
    if len(qs) != len(ans):
        # 并列数组本应一一对应;长度不一致(模型偶发)按较短对齐,记警告不静默错位
        logger.warning("挖知识并列数组长度不一致 questions=%d answers=%d,按较短对齐", len(qs), len(ans))
    n = min(len(qs), len(ans))
    return [QaPair(question=qs[i], answer=ans[i]) for i in range(n)]
```

按较短的那个截断，多出来的丢掉，同时记一条警告。少抽两条知识没什么，问题错配到别人的答案上会直接污染知识库，而且很难查出来。

### dedupe

```python
_STRIP_RE = re.compile(r"[\s\W_]+", re.UNICODE)  # \W 不含中文(中文属 \w),故只去空白/标点


def normalize_question(q: str) -> str:
    return _STRIP_RE.sub("", q.strip().lower())
```

那句注释很关键。`\W` 匹配的是非单词字符，而中文汉字在 Python 的 Unicode 模式下属于 `\w`，所以这个正则只会去掉空白和标点，不会把中文吃掉。「运费怎么算？」和「运费怎么算」归一化之后是同一个键。

```python
    seen = {normalize_question(q) for q in existing_questions}
    kept, discarded = [], []
    for item in items:
        key = normalize_question(item.question)
        if not key or key in seen:
            discarded.append(item)
        else:
            seen.add(key)
            kept.append(item)
```

`seen` 一开始就装进了库里已有的全部问法，所以这一次遍历同时挡住两种重复，本批内部撞车的和跟存量撞车的。

### mine

```python
    staged = [s for s in await repository.list_staging_by_status("extracted") if s.batch_no == batch_no]
    existing = await repository.list_all_questions()
    kept, discarded = dedup.dedupe(staged, existing)
    await repository.set_staging_status([s.id for s in kept], "kept")
    await repository.set_staging_status([s.id for s in discarded], "discarded")
```

抽出来的东西不直接进知识库，先落 `qa_extraction_staging` 这张暂存表，状态是 `extracted`。去重之后分别标成 `kept` 和 `discarded`。

`batch_no` 那个过滤条件是踩过一次坑之后加的。上一次挖到一半崩了的话，暂存表里会留下一批状态还是 `extracted` 的残骸，不圈定批次就会把它们一起卷进这次去重，结果既不对也不好查。

到这里 `mine` 就收工了。`kept` 的意思是等人看一眼，还没进库。

为什么不让它自己写进去？本章开头那句话在这里要兑现，库里是垃圾，查出来的也是垃圾。挖出来的问答对是模型从聊天记录里归纳的，客服当时那句回答，可能只对那一单成立，可能带着具体的订单号和收货地址，也可能就是一句「稍等我帮您看看」被当成了答案。这种东西一旦进库，之后每次检索都可能把它捞出来当依据。

所以入库口只留一个，`app/api/kb.py` 里的 `/staging/approve`。人在录入页那张「对话挖知识」的卡片上逐条过，点采纳才走 `write_pending` 真的写库。点弃用的标成 `rejected`，行留着不删，将来要能回答这条当初谁挖的、为什么没要。

这个端点只认 `kept` 状态的行。页面上手快点两下，或者拿已经弃用的行再来入库，都会在这一步被 409 挡回去。

采纳进去的块 `content_type` 标成 `mined`，`questions` 存的是用户的真实问法，跟从文档切出来的块能分得开。哪些知识是人写的、哪些是从对话里长出来的，后面几章都要用到这个区分。

## 在线检索

### search\_knowledge

本章的检索路径就一条，问题向量化，拿向量去 Milvus 取 Top-K：

```python
    if strategy == "vector":
        vec = await embeddings.embed_query(query)

        def work():
            c = client or milvus_client.get_client()
            milvus_client.ensure_collection(c, collection=collection)
            return milvus_client.dense_search(c, vec, top_k, category, collection)
        return await milvus_client.acall(work)
```

这个函数在 HEAD 上有六十多行，本章占的就是这一个分支。开头的子句拆分、后面的 hybrid 和 rerank 两个分支，还有 `arrange_head_tail` 那个首尾组装，全是第 4 章的东西。`def work()` 包一层再交给 `acall` 的写法也归第 4 章的线程纪律，本章那版就是直接同步调。

### query\_faq 换内脏不换签名

第 2 章的 `query_faq` 拿关键词去 `faq` 表做 LIKE 查询，本章把函数体换成了一句 `await retrieval.search_knowledge(keyword)`，参数还是那一个 `keyword`，装饰器还是那个 `@tool`。

调用方不知道底下换过，system prompt 里那条「用 query\_faq 按关键词检索」不用改，模型看到的 schema 一个字节都没变。这就是第 2 章那张工具去向表想说明的事，这一章把它兑现了一次。

现在 HEAD 上的 `query_faq` 又长了不少，多出来的重排、自评和证据编号是第 4 章加的。那次改动动了返回值的形状，代价比这一次大。
