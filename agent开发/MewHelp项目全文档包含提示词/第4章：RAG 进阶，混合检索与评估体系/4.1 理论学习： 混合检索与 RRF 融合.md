用户在客服框里敲了一句「BE200 支持快充吗」。知识库里其实躺着两份规格文档，一份是 BE200 的参数表，另一份是上一代 BE100 的参数表，两份文档八成的字句一模一样，型号那几个字符是唯一的差别。向量检索依据的是整段话的意思，两份文档意思都差不多，型号编号这种没什么语义的东西反而排不上号。检索结果里，上一代的参数表堂而皇之地排到了前面，回答里也就跟着把快充功率报错了。



这就是向量检索的问题：拿不准这类要求一字不差的东西。退一步说，就算两份文档都被捞回来了，谁排在前面同样没准。这一章要解决的，正是这件事。

![](<images/理论学习：混合检索与 RRF 融合-01-vector-model-confusion.png>)

## 给向量加一条路径：BM25 怎么打分

把刚才那道题换个查法试试：不看意思，只看这几个字符有没有原样出现在文档里。型号编号这种东西，认字面反而比认语义靠谱。这条查法有个现成的名字，叫「BM25」，是关键词检索的标准打分算法，信息检索领域用了几十年，搜索引擎、Elasticsearch 这些全文检索基建也都建在它上面。



BM25 打分的逻辑并不复杂：query 里的词在某份文档里命中得越多、命中的词越稀有，这份文档分就越高。「的」「是」这种到处都是的字会没那么重要，「花呗分期」这种少见的词命中一次，几乎就能锁定答案。这个思路更老的算法「TF-IDF」也有，BM25 在它基础上又补了两处修正。



第一处是「词频饱和」。一段促销规则里反复出现「满减」这个词十次，不代表它跟用户问题的相关度是只出现一次时的十倍，出现到一定次数之后，再往上加分应该慢下来，不然堆词的文档就占了便宜。

![](<images/理论学习：混合检索与 RRF 融合-02-bm25-term-frequency-saturation.png>)

第二处是「文档长度归一化」。一份长的售后手册就是会比一份短的 FAQ 包含更多字，不能因为它长就更容易命中，得按文档长度打个折扣，让长短文档站在同一条起跑线上比。这两处修正各有一个参数控制，工程上有约定俗成的默认取值，照着默认值起步，再拿评估集微调就够用，不用从零摸索。

![](<images/理论学习：混合检索与 RRF 融合-03-bm25-length-normalization.png>)

BM25 也有认不出来的地方。它靠字面命中，「退货」和「退款」在它眼里是两个毫不相干的词，压根不知道这俩说的其实是一件事，这正好是向量检索的强项。两条路径的短板刚好相反，谁也替不了谁，从此并存着走，不是拿一条换掉另一条。

![](<images/理论学习：混合检索与 RRF 融合-04-bm25-vector-complement.png>)

## 这条路径落在哪：还是回到 Milvus

上一章选向量库的时候提过一句，Milvus 从 2.5 版本起自带 BM25 全文检索。



建库时给存正文的字段挂一个 BM25 函数，Milvus 会自动帮它生成一份稀疏向量，中文分词走内置的 `chinese` 分析器，底层用的是 jieba 分词，不用自己接一套分词逻辑。dense 向量字段和这份稀疏向量字段在同一张集合里并排存着。

![](<images/理论学习：混合检索与 RRF 融合-05-milvus-dense-sparse-fields.png>)

查询时也不用挨个调用两个不同的系统，一次 `hybrid_search` 就能把两路结果一起要回来。这里直接落到 Milvus 底层的 `pymilvus`，把两路召回和融合都摆到明面上看得更清楚；上一章在线检索用的 LangChain 那层其实也能做混合检索，只是细节被封装起来了，这里讲原理就下沉一层：

```python
from pymilvus import MilvusClient, AnnSearchRequest, RRFRanker

client = MilvusClient(uri="http://localhost:19530")
dense_req = AnnSearchRequest(
    data=[query_vector], anns_field="dense_vector",
    param={"metric_type": "COSINE"}, limit=50,
)
sparse_req = AnnSearchRequest(
    data=[query_text], anns_field="sparse_vector",
    param={"metric_type": "BM25"}, limit=50,
)
results = client.hybrid_search(
    "ecommerce_kb", reqs=[dense_req, sparse_req],
    ranker=RRFRanker(k=60), limit=50,
)
```

`dense_req` 和 `sparse_req` 分别是两条召回请求，各自先要回 50 条候选；



`hybrid_search` 把这两批一起送进 `RRFRanker` 融合，吐出一份融合排好序的候选池，也就是下面要讲的粗排，后面精排再把它收窄到十条左右送去生成，所以这里 `limit=50` 给的是粗排池大小、不是最终条数。融合具体怎么算，下一节细说。



业界另一条常见路线是把 BM25 单独交给 Elasticsearch 处理，全文检索这块的基建和中文分词更老到，适合已经有 ES 集群、或者要独立扩展全文检索能力的团队，两边打分原理相通，面试提一句即可。而我们这里直接一套库搞定，省下另起一套 Elasticsearch 集群的运维成本，数据一致性也不用在两个系统之间对齐。

![](<images/理论学习：混合检索与 RRF 融合-06-milvus-vs-elasticsearch.png>)

## 三阶段流水线：先捞得全，再排得准

接下来该怎么把结果合到一起？得分三段来走。



头一段是「召回」，向量和 BM25 各自独立跑一遍，各要回一批候选，常见的做法是每条路先捞 50 条，宁可多捞一点，也不要在这一步就漏了正确答案。紧接着是「融合」，把两条路径的结果合成一个候选池，这一步产出的排序还比较粗糙，业内管这一层叫「粗排」。最后一段才轮到「精排」，用更准但更慢的模型把这批候选重新细排一次，只把排到最前面的十条左右交给生成模型。整套流程的字面意思就是「找得全」交给召回，「排得准」交给精排，粗排在中间打个底稿。

![](<images/理论学习：混合检索与 RRF 融合-07-three-stage-retrieval-pipeline.png>)

召回阶段还有一个过程：按元数据先筛一遍。用户问的商品要是已经带着品类、店铺这类信息，检索前先按这些标签把候选范围圈小，再去算相似度和词命中，候选池干净了，精度通常能提，检索多数时候也更快；只是过滤条件卡得太窄时，带过滤的向量检索反而可能变慢。



融合这一步，权重可以按 query 类型来定。标准化程度高的电商用词，比如具体型号、优惠券代码，BM25 更值得信任；问法模糊、带口语色彩的语义型提问，更该偏向量。

![](<images/理论学习：混合检索与 RRF 融合-08-query-type-dynamic-weighting.png>)

## 两套分数怎么合：加权还是拼排名

向量检索给出的是余弦相似度，取值范围是 -1 到 1（Milvus 的 COSINE 度量也是 \[-1,1]，电商语料的检索结果绝大多数落在正区间）；BM25 给出的打分数值范围完全是另一回事，可能是几分，也可能是十几分。两套分数量纲不同，直接相加没有道理，谁分高不代表谁真的更相关。



一类做法是「分数级融合」，先把两套分各自拉到同一个区间，比如都归一化到 0 到 1 之间，再按权重加起来，权重固定不动是最简单的版本，比如各占一半，效果能用但不够灵活，这类做法可控，代价是权重得逐场景手调。



另一类做法叫「RRF」，倒数排名融合，思路反过来了：干脆不比分数，只比排名。每份文档在每条排序里贡献 1/(k+排名) 这么一点分，两条路径的排名加起来，两边都靠前的文档自然冒头，k 这个参数通常取 60。



RRF 完全绕开了分数量纲不统一这个麻烦，工程实现也简单，是眼下最常见、最省心的融合方式，开箱就能用；分数级加权更可控，但要花时间逐场景调权重。上一节代码里那行 `RRFRanker(k=60)`，接的正是这套逻辑。前面说的按 query 类型定权重，靠的就是分数级加权这套做法。

![](<images/理论学习：混合检索与 RRF 融合-09-rrf-ranking-fusion.png>)

## 粗排也会看走眼：精排登场

用户问「退货运费谁承担」，知识库里两条相关条款都被捞回来了。一条是「退货规则：七天无理由退货，未拆封商品可退」，字面上「退货」两个字出现了不止一次；另一条是「运费险：若未购买运费险，退货产生的运费由买家自行承担」，才真正回答了用户问的问题，但字面命中次数反而没那么高。粗排只会数字面命中，前一条被排到了更靠前的位置，交给生成模型的候选顺序一乱，回答很可能只顺着退货流程说了一堆，压根没提到运费该谁出。

![](<images/理论学习：混合检索与 RRF 融合-10-rerank-shipping-fee-answer.png>)

召回已经把两条都捞回来了，卡壳的地方在排序。向量和 BM25 打分时都是各自独立看 query 和某份文档像不像，读不懂这两份文档之间谁才真正回答了运费问题，这就是粗排的天花板。



精排要解决的正是这层关系。干精排这件事的模型，业内叫「reranker」，重排器；它用的结构叫「Cross-Encoder」，交叉编码，做法是把 query 和文档拼成一条输入送进模型，让两边的每个词充分交互，读出「运费该谁出」这种更深的语义关联，而不是各查各的自说自话。



跟它相对的是双塔结构「Bi-Encoder」，query 和文档各自独立编码成向量，最后才拿两个向量去比相似度，好处是文档向量能提前算好存起来，检索起来极快，代价是两边编码时互不知道对方在问什么，精度有个上限。



前面选 Embedding 模型那一节讲的 BGE-M3，用的正是这套双塔结构。双塔跑得快但精度有限，交叉编码精度高但跑不动大规模，一个负责在海量候选里快速筛一遍，一个负责在一小把候选里挑出最准的那个，正是各司其职。

![](<images/理论学习：混合检索与 RRF 融合-11-bi-encoder-vs-cross-encoder.png>)

reranker 模型的选型思路跟 Embedding 类似，中文和中英混合场景，本项目默认用 bge-reranker-v2-m3，跟前面选定的 BGE-M3 属于同一系列、同一个底座，BGE-M3 中英双强的底子它直接继承，中英文榜单表现都稳，生产上踩过的坑也多，资料好查。不过这只是企业级实际落地时的情况，我们学习和课程演示用云端的就行，避免本地部署太重。



要更强的对照，可以拿 Qwen3-Reranker 这类更新的模型上自己的评估集比一比，按数据定夺。还有一个容易被忽略的细节，reranker 能吃下的最大输入长度得跟 chunk 的大小对齐，chunk 比它能处理的还长，尾部会被悄悄截断，精排等于白做。

![](<images/理论学习：混合检索与 RRF 融合-12-reranker-max-length-truncation.png>)

排好序还没完。LLM 读长上下文时，对塞在中间位置的内容利用率最低，之前也说过这个现象叫 Lost in the Middle。就算精排把最相关的那条捞出来了，如果它被埋在候选列表中间才交给生成模型，模型很可能视而不见。所以精排的价值不只是把对的排进候选池，更是要把最相关的几条摆到最前面和最后面，刻意避开中间这块注意力盲区。

![](<images/理论学习：混合检索与 RRF 融合-13-lost-in-the-middle.png>)

精排慢，工程上有三招能压一压延迟：先把候选数量本身缩小，只精排真正需要的那一批，候选数直接决定要跑多少次模型；再上「批量推理」，把几十对 query 和文档打包成一个批次一次性送进模型，而不是写个循环一条条来；最后还有「模型量化」，用 INT8 这类低精度格式配合专门的推理引擎，精度损失不大，速度提升明显。三招叠加通常能把精排延迟压到可接受的范围。

![](<images/理论学习：混合检索与 RRF 融合-14-batch-reranker-inference.png>)

## 为什么不能一步到位，直接精排扫全库

精排明明更准，那能不能干脆跳过召回和粗排，直接拿精排模型扫一遍全库？问题卡在精排模型的算法本身，上一节刚讲过，Cross-Encoder 得把 query 和每一份文档拼在一起现算一遍，几十万条文档跑一遍，慢到用户等不起，才要先用快的方法把候选池收窄，精排只在这个小候选集上发力，把算力花在真正重要的地方。



候选池的大小也不是随便定的，它是召回率的上限。正确的那份文档如果压根没进候选池，后面精排再准也救不回来，候选池宁可先调大一些保住召回，精度交给精排去收拾。



最终交给生成模型的条数同样有讲究，太少容易漏掉有用信息，太多又会把噪音一起塞进去，既拖慢生成又可能干扰它的判断，常见做法是先摸出一个大致区间，再拿评估集找到刚好够用的那个数。



三段各管一段职责：召回图快图全，粗排把多路结果拢成一个候选池，精排图准，在小范围里把顺序定死。少了任何一段，要么慢得离谱，要么准头不够。

![](<images/理论学习：混合检索与 RRF 融合-15-rerank-whole-corpus-vs-candidates.png>)

## 问题问得好，检索才有戏：Query 理解

前面几节一直在优化怎么查，这一节转到另一个角度，看看送进去查的那句话本身有没有问题。



用户「这个是不是能便宜点买」这种问法，知识库里大概率没有一模一样的字眼，得先把它改写成更贴近知识库表达的说法，比如「是否支持优惠或满减」，这叫「Query 改写」，目的是求准。



另一种做法是「扩写」，给问题加上同义词、相关词，变成好几条查询一起去检索，比如同时拿「优惠」「满减」「折扣」都查一遍，目的是求全，哪怕知识库里写的是另一个说法，也能被兜到。改写和扩写这两件事目标维度不一样，一个求准，一个求全，别混着用同一套逻辑去衡量。

![](<images/理论学习：混合检索与 RRF 融合-16-query-rewrite-vs-expansion.png>)

给 BM25 补同义词，成本很低：不必多开一条查询，只在原查询里多塞几个近义词，就给 BM25 多开几个命中入口，很划算；至于向量本身已经能理解近义表达，扩写对它的边际收益要小得多。



还有一招，叫「HyDE」，先让模型编一段「可能的答案」，把这段假答案向量化，拿它去检索真实文档，而不是直接拿用户的原始问题去检索。这个假答案哪怕内容是编的也没关系，用的是它的语义丰满度，一段完整的答案自带一堆相关术语，向量比原始的一句简短提问更接近真正答案文档的向量，短查询的召回效果因此能提上来。



代价是多了一次模型调用，延迟和成本都要算进去，强 Embedding 模型下这一招不一定划算，甚至可能是负优化，要不要用得拿自己的评估集实测过再定。

![](<images/理论学习：混合检索与 RRF 融合-17-hyde-answer-vector.png>)

这里要提醒一个容易踩的坑，如果建库时把一条知识用大模型泛化成好几个问法，再按一问一答的结构把这几个问法分别存成好几条记录，看着是提升了召回入口，实际效果适得其反：同一条知识产生了好几条彼此高度相似的向量，一个 query 进来，Top-K 的名额很容易被这同一条知识的几个变体全部占满，真正该被捞出来的别的知识反而挤不进候选池。

![](<images/理论学习：混合检索与 RRF 融合-18-duplicate-question-variants-topk.png>)

这个坑告诉我们，扩召回这件事该放在检索侧做 Query 扩写，库里每条知识只存一份，查询时才临时扩几条，用完就丢，不会占着名额，别在入库时就把一份知识拆成好几份分别存着。真要在入库侧增强召回，走的是给每块补一段上下文再嵌入那条路（RAG 基础章切分那节提过），而不是把一份拆成好几份。至于检索侧具体怎么把一句问题扩写成好几条查询，后面意图识别那一章会展开讲；多轮对话里「它」「这个」这类指代要先补全才能拿去检索，同样归在那一章处理，这一章不展开。

## 查到了不等于答对了：生成前后的几道闸

检索、排序都做对了，最后一步是把这些资料交给大模型生成一段回答，这一步还有两个坑没堵上。



头一个坑，模型即便是有的数据仍有可能会编。资料明明检索不到，或者检索到的东西压根答不了这个问题，模型的天性还是想把话说圆，硬凑一个听起来像模像样的答案。



有两个方式去尽量避免。生成前先用一段 system prompt 立规矩，把身份、硬约束、红线一次交代清楚：

```plain&#x20;text
# 角色
你是电商客服助手，只依据下面的【知识片段】回答，判断不了就转人工。

# 铁律
1. 只用【知识片段】里的信息作答，片段没提到就直说没查到，绝不自行编造
2. 每条结论后标来源编号 [1][2]，对应片段序号，方便回原文核对
3. 红线，一律不承诺：具体到货时间、第三方物流时效、退款金额的最终裁定

# 知识片段
[1] {chunk_1}
[2] {chunk_2}

# 用户问题
{query}
```

这段 prompt 里最重要的是「铁律」头一条，只依据资料回答、没有就说没有，一句话既给答案的可信度打了底，也提前挡住一部分凭空发挥。第二条要求每个结论标编号，是给下面的溯源打底。第三条那几条不许承诺的红线，就是「负面清单」，本节末尾还会拎出来细说。知识片段带着 `[1][2]` 的序号一起喂进去，模型引用时才对得上号。



光靠这句约束还不够，模型偶尔还是会自信地越界，生成后还要再补一道验证，做一条事实验证链去拦截漏网的幻觉，并且给答案标上出处，这就是「溯源标注」。答案里的每个结论标一个编号，编号映射回这段内容在 chunk 里存的 `section_path`，编号就能跳到原文核对。

![](<images/理论学习：混合检索与 RRF 融合-19-pre-post-generation-guards.png>)

怎么让编号标出来，工程上有两条路线。一条是直接在 prompt 里让模型边答边标 `[编号]`，最简单，一个 prompt 就搞定，缺点是模型会有一部分漏标，标错编号的情况也不是没有。



另一条是回答生成之后再做后处理，把答案拆成一句一句，对每一句去查检索到的原文能不能支撑它，支撑得住的补上出处，支撑不住的这句大概率就是编的，这套技术在自然语言处理里有个名字叫「NLI」，自然语言推理。



第二条路线更可靠，代价是多跑一趟模型去Review，速度慢一些，成本也会增加。生产里两条路线通常一起上，先让模型生成时顺手标一遍，再用后处理逐句校验补漏。我们课程这里就不做了。



标出来大致是这样，模型吐一段带编号的回答，另挂一份编号到出处的映射：

```json
{
  "answer": "支持 7 天无理由退货，定制类商品除外 [1]；未买运费险时，退货运费由买家承担 [2]。",
  "citations": [
    { "mark": "[1]", "section_path": "退货政策 > 无理由退货" },
    { "mark": "[2]", "section_path": "运费险 > 退货运费" }
  ]
}
```

`answer` 里每个结论都挂着编号，`citations` 把编号对到 chunk 的 `section_path`，就能跳回「退货政策 > 无理由退货」那一节核对原文。

![](<images/理论学习：混合检索与 RRF 融合-20-citation-to-source.png>)

另一个坑，模型该拒答的时候不拒答。检索不到相关内容，或者检索到的置信度太低，该做的是老老实实说没查到，转人工，而不是硬答一个。



这一步可以再往前挪一点，让模型在生成之前先自己判断一下，检索回来的这些知识够不够回答用户这个问题，够就正常生成，标成 `useful=true`；不够就直接拒答，标成 `useful=false`，同时给一句兜底话术。这条低置信度的记录会自动落进一个问题池，等着后面处理，具体怎么处理，留给后面数据飞轮那一章接着讲。



具体做法是回到前面那段 system prompt，给它接一段输出要求，把这层判断也一并交给模型：

```plain&#x20;text
# 输出要求
先判断【知识片段】够不够回答，再按 JSON 返回，别输出多余内容：
- 够答：useful=true，依据片段作答，每条结论标来源编号
- 不够：useful=false，reply 给一句转人工的兜底话，reason 写清缺什么
```

判断结果用一份 JSON 落下来，拒答的时候就是下面这副样子：

```json
{
  "useful": false,
  "reply": "这个问题暂时没查到明确依据，已经为你转接人工客服",
  "reason": "检索资料只覆盖站内支付方式，没提到跨境订单的退款到账周期",
  "route": "human_handoff"
}
```

这份判断结果里，`useful` 是这批知识能不能支撑回答的总判断；`reply` 是真正回给用户的兜底话术；`reason` 记下判不能的原因，留作复盘；`route` 指明这条该往哪走，`human_handoff` 就是转人工。



几个字段拆开存，系统能按 `useful` 和 `route` 自动分流，`useful=false` 的那批自动沉进问题池，复盘时也有线索可循。这里先只靠 `useful` 判一条问题该不该进池，等后面数据飞轮那一章，还会再加一道从检索侧算出来的分，把这道闸做得更稳。`useful=true` 的情况就不走这套兜底，改带上前面那份 `citations` 正常作答。

![](<images/理论学习：混合检索与 RRF 融合-21-refusal-vs-forced-answer.png>)

再回到 system prompt 里那几条不许承诺的红线，单独说说这份负面清单为什么非写死不可。到货时间、物流时效、退款金额裁定这类话，一旦被模型顺口答出去，客服系统实际上就替公司做了承诺，用户真照着它来主张权益，出了问题没法收场。这种红线宁可列得啰嗦，也别给模型留松口的余地。

![](<images/理论学习：混合检索与 RRF 融合-22-negative-red-line-list.png>)

## 有没有变好，得拿数据验证：RAG 评估体系

这一章讲了这么多招，混合检索、动态权重、精排、Query 改写，每一招上线之前，怎么知道它真的有用，而不是团队里几个人「感觉」有用？答案是得先有一套能量化的指标，不然改了 A 觉得不错，改了 B 也觉得不错，谁也说不清哪个真管用，调参就成了拍脑袋的事。验证靠的就是「评估集」，一批事先标好标准答案的测试题。



评估分层来看，先看检索、再看生成。检索段看的是「该找的找到没有」，生成段是看「生成后的情况」。



检索段评估常用两个指标：「Recall@k」，正确的那份资料有没有出现在前 k 个检索结果里；「MRR」，全称平均倒数排名，正确资料排第一得 1 分，排第二得 0.5 分，如果压根没召回就记 0 分，所有测试题取平均数，总的来说就是看的不只是找没找到，还要看排得靠不靠前。



检索和生成之间，还架起一层「证据覆盖度」当桥梁：把每道题的标准答案拆成几个要点，数一数检索回来的这批资料里字面盖住了几个。它不调大模型、纯字符串匹配、可复现，检索排得越靠前、捞得越全，这个数就越高，等于提前预告了生成段答得全不全。



生成段看的是「答得好不好」。我们这里用第一个角度是「LLM-as-Judge」，就是拿另一个模型当裁判照着标准打分，我们让它看看客服答案正确覆盖了几个标准要点，得出「答案覆盖度」，还让四种检索策略各生成一遍答案分别判定，就能看清检索质量怎么一路传导到最终回答。



另一个角度是「Faithfulness」，衡量答案有几成能在检索原文里找到依据，专抓「资料里没有、模型自己编」的幻觉，这一项只在最终上线的那条混合重排链路上测，因为毕竟真正的跨策略对比信号本来就在答案覆盖度上。



这几个指标社区有 RAGAS 这类现成框架，大家可以自己去直接使用，不过我选择自己动手搭一套，理由有两条：一是想把 Recall@k、MRR、证据覆盖度这几个指标更具体体现；二是我们要的是四种检索策略摆一起横向比、按桶（政策 / 型号 / 口语 / 该拒答）拆开看、再算机械证据覆盖度和拒答率。其实就是想自己定制化一下。

![](<images/理论学习：混合检索与 RRF 融合-23-recall-mrr-evaluation.png>)

接下来看看评估集，评估集不是随便几道题就能用，得讲究几件事。先得给每道题标好「ground-truth」，写清楚正确答案该落在知识库的哪一节、要点有哪些。



题目还得按类型分好桶，覆盖到不同的考法：规矩政策类的日常提问、带着型号编号这类要求精确匹配的刁钻提问、口语化、说法模糊的问法，甚至知识库压根没有、该拒答的问题，都得有，不能全是好答的题。



最后还得抽一部分出来人工校验，确认标注的要点真的能在原文里对上。



一道标好的评估题，落到 JSON 上差不多是这么个结构：


```json
{
  "id": "B1",
  "bucket": "B_model",
  "query": "MH-LP100 的废砂盒多久倒一次",
  "expect_section": ["MH-LP100"],
  "expect_points": ["5 至 7 天", "7 天(单猫)"],
  "should_refuse": false
}
```

`bucket` 给题目分桶，`B_model` 就是型号精确匹配这一类；`expect_section` 是这道题的 ground-truth，写清正确答案该来自哪一节，检索段就看召回结果的 `section_path` 命中了没有、排第几，用于前面的 Recall@k 和 MRR；`expect_points` 是标准答案拆出来的要点，证据覆盖度和答案覆盖度都拿它来数盖住了几个；`should_refuse` 标记这道题该不该拒答，知识库里没有的问题填 `true`（这类题的 `expect_section` 和 `expect_points` 就都留空）。跑评估时按 `bucket` 分桶，就能看出哪一类题倒在哪一步。

![](<images/理论学习：混合检索与 RRF 融合-24-ground-truth-evaluation-set.png>)

有了分层的指标，排查问题也有了思路。



回答不理想，先看检索段的数字。如果 Recall 本身就低，说明该找的压根没找到，问题出在切分或者检索这一步，后面生成环节再怎么调 prompt 也没用；



Recall 高但证据覆盖度上不去，多半是排序不对、真正答题的那条被挤在后面，该在精排上下功夫；如果检索这几个数都很漂亮，生成还是不尽如人意，问题就落到 prompt 设计或者模型本身，该去调的是前面「查到了不等于答对了」那节讲的那几种情况。

![](<images/理论学习：混合检索与 RRF 融合-25-rag-diagnosis-flow.png>)

不过准不准只是评估的一个方向。一个真要顶在客服台前的 RAG，光答得对还不够。前面几层指标量的是「准确」和「可信」——准确看检索排名和覆盖度，可信靠 Faithfulness，看答案有几成能在原文里找到依据。



这之外还得专门弄个维度「该拒则拒」：知识库里没有的问题，模型有没有老实说没查到、转人工，而不是硬编一个。评估集里那批 `should_refuse=true` 的题就是干这个的，跑一遍看拒答率高不高。



还有即便这样子肯定也不是完全够的，我们还可以做个用户反馈功能，生成答案后可以让用户打个满意度来评估。

![](<images/理论学习：混合检索与 RRF 融合-26-rag-evaluation-dashboard.png>)

## 拿数据说话：四种策略摆一起比

道理讲了一整章，到底谁强谁弱，得拿数据出来看。造一份带难度梯度的评估集，一类是标准化术语的提问，比如型号、优惠券代码这类要求精确匹配的说法，另一类是语义模糊的提问，比如口语化、模糊的说法，四种检索策略各跑一遍：纯向量、纯 BM25、混合 RRF、混合加精排，从检索排名一路比到证据覆盖度、答案覆盖度，看每一层各自拉开多少差距。



跑完之后再按 query 类型分桶看，标准化术语类的提问，哪条路径更占优；语义模糊类的提问，又是哪条更占优，这正好回应前面融合那一节，动态权重该往哪边偏，答案就在这张分桶表里。



一个反直觉的结论大概率会出现：电商客服里用户的问法看着随意，但涉及型号、优惠券、SKU 这类内容时，用词其实相当标准化，这种场景下 BM25 未必输给向量，甚至可能反超。这条结论提醒一件事，不能一概而论地说向量检索一定比 BM25 强，具体谁强谁弱，得看这批 query 本身的特征，谁的说法越标准化，字面匹配那条路径越占上风。

![](<images/理论学习：混合检索与 RRF 融合-27-retrieval-strategy-comparison.png>)

数据里还有一个更反直觉的地方：口语类问题上，纯向量单独检索是满分，一融合 BM25 反而掉了下来，跨文档类也隐约看得出同样的方向。混合检索不是「多一路信号总归更稳」，RRF 融合按排名位置算分，不看两路谁更可信，BM25 在这两类问题上本来就弱，融合进来的噪声会把向量已经排对的答案往后挤。真正把这个坑填回来的是精排，它不看排名位置，是把两路召回的候选内容重新读一遍、重新打分，口语类冲回满分，双双反超纯向量。这条结论比「四策略里谁最强」更值钱：混合检索要兑现收益，精排这一步不能省。



这些结论建立在 300 道自建评估题、51 个知识库小节上，规模不算大，图的是能在课程环境里秒级建库、秒级验证，把几种策略的相对差距讲清楚。知识库真到了成百上千个类目、上万条记录，检索会难得多，这里的结论该怎么变，得回到自己的数据上重新跑一遍评估，不能直接套用。

## 本章小结

这一章从向量检索认不出型号编号这道题讲起，把 BM25 这条关键词路径接了进来，落地在同一个 Milvus 里；接着走了一遍召回、融合、精排的三阶段流水线，讲清了 RRF 怎么合分数、粗排为什么会看走眼、精排怎么把顺序纠正回来；再往后看了 Query 理解怎么把问题本身先改好，生成阶段又加了拒答和溯源这几道闸挡住幻觉；最后靠一套评估体系把这些招数的效果量化成看得见的数字。



知识检索这条线，从最初关键词漏检开始，一路走到能查、能排，验证和评估也跟上了，这一路算是立住了脚跟。接下来要看的是这些能力怎么被整个客服系统调度起来，那是另一件事了。
