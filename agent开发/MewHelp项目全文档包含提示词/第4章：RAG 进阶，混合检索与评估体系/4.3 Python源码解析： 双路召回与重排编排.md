## 集合重建：一份数据两种索引

### text 字段与 BM25 Function

第 3 章的集合只有一个稠密向量字段。本章要做混合检索，得再挂一路稀疏索引：

```python
        # text = category+questions+answer 拼接,恒长于 answer(8192);放宽到 16384 防长块 upsert 溢出
        schema.add_field("text", DataType.VARCHAR, max_length=16384,
                         enable_analyzer=True, analyzer_params={"type": "chinese"})
        schema.add_field("sparse", DataType.SPARSE_FLOAT_VECTOR)
```

```python
        schema.add_function(Function(
            name="text_bm25", input_field_names=["text"],
            output_field_names=["sparse"], function_type=FunctionType.BM25,
        ))
```

这个 Function 是 Milvus 提供的一层便利：给它一个文本输入字段和一个稀疏输出字段，写入时它自己分词、算 BM25 权重、填进 `sparse`。应用侧只管往 `text` 里塞字符串，倒排那套完全不用碰。

`enable_analyzer=True` 和 `analyzer_params={"type": "chinese"}` 这两个参数缺一不可。分析器默认按空白和标点切词，中文进去基本切不动，BM25 算出来的权重也就没有意义。

那句注释讲的是一次真实的溢出。`text` 存的是 `category`、`questions`、`answer` 三格拼接的结果，它一定比 `answer` 单字段长，可 `answer` 设的是 8192，照抄过来长块 upsert 就报错。放宽到 16384 才装得下。

两套索引挂在同一个集合上，稠密走 COSINE，稀疏走 `SPARSE_INVERTED_INDEX` 加 BM25 度量。同一条数据，两种召回方式。

### hybrid\_search

```python
def hybrid_search(client, vector, text, top_k, recall=50, category=None, collection=COLLECTION) -> list[dict]:
    expr = _cat_expr(category)
    dense_req = AnnSearchRequest(data=[vector], anns_field="dense",
                                 param={"metric_type": "COSINE"}, limit=recall, expr=expr)
    sparse_req = AnnSearchRequest(data=[text], anns_field="sparse",
                                  param={"metric_type": "BM25"}, limit=recall, expr=expr)
    res = client.hybrid_search(collection, reqs=[dense_req, sparse_req], ranker=RRFRanker(),
                               limit=top_k, output_fields=_OUTPUT)
    return [_hit(h) for h in res[0]]
```

两个请求各打各的字段，`RRFRanker` 把两份排名融成一份。

RRF 融合的依据是名次，不是分数。这一点很关键：余弦相似度是 0 到 1 的一个数，BM25 分是个没有上界的实数，两者量纲完全不可比，加权求和这条路走不通。改成看名次就绕开了，一条结果在稠密路排第 3、在 BM25 路排第 8，融合分就由这两个名次算出来。

`limit=recall` 是每一路各自召回的深度，默认 50，外层的 `limit=top_k` 是融合之后截取的条数。先各捞五十条再融，比各捞十条融出来的池子厚得多。

### \_cat\_expr

```python
def _cat_expr(category: str | None) -> str:
    return f'category == "{category}"' if category else ""
```

品类过滤拼成 Milvus 的布尔表达式，跟着检索请求一起下推。检索引擎在索引层面就把不匹配的排除掉，而不是全捞回来再在 Python 里筛。捞回来再筛的话，top\_k 会被过滤掉的那些占着名额，实际拿到手的可能只剩两三条。

### acall

这是本章集成阶段踩得最深的一个坑：

```python
_EXECUTOR = ThreadPoolExecutor(max_workers=1, thread_name_prefix="milvus")


async def acall(fn, *args, **kwargs):
    """在专用单线程上执行同步 pymilvus 调用(供 async 在线路径用)。"""
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(_EXECUTOR, functools.partial(fn, *args, **kwargs))
```

pymilvus 是同步库，底下是 gRPC。在 async 服务里想调它，直觉做法是丢进 `to_thread`，让默认线程池随便挑个线程跑。问题是同一个客户端对象就这么被多个线程共享了，而它在这种用法下会间歇性返回空结果。不抛异常，不报错，就是查出来是空的，下一次又正常。

这种故障最难查，因为它不稳定复现，日志里也看不出任何异常。

解法是把所有 Milvus 调用固定到一个专用线程上，`max_workers=1` 意味着这个池里永远只有那一个线程。客户端也在这个线程里惰性创建，两件事必须配套，只把调用挪进来、客户端还在主线程建的话，共享问题原样存在。

代价是所有 Milvus 调用被串行化了。但比起重建客户端连带重建连接池的开销，这点损失可以接受，而且检索本来就不是这条链路的瓶颈。

### \_rerank\_url

```python
def _rerank_url() -> str:
    """把配置里的上游地址拼成 /rerank 端点。每次现算,改配置不用重启。

    地址带不带版本段都收:硅基流动和 Jina 的 rerank 在 /v1 下,Cohere 在 /v2 下,而
    「上游地址」按字面理解很容易只填到域名。少了版本段会打成 https://host/rerank,
    上游回 404,而且只在查询时以 hybrid_rerank 失败的形式冒出来,排障要绕一圈。"""
    base = settings.rerank_base_url.rstrip("/")
    if not _VERSION_SEG.search(base):
        base += "/v1"
    return base + "/rerank"
```

各家的版本段不统一，而学员照着「上游地址」这四个字填，十有八九只填到域名。这个错误的隐蔽之处在于它不在启动时暴露，服务照常起来，一直到有人问了个政策问题、走到重排那一步才 404，排障得从「回答质量不对」一路倒推回配置。

### \_post

```python
async def _post(url, json, headers, timeout):
    """带退避重试:子句拆分之后一个问题要打好几次 /rerank,上游按秒限流,
    突发流量会撞 429。这是瞬时限流不是坏请求,退一步再试就过去了;
    连试几次还不行才抛出去(评估脚本会把这一轮记成失败,不会静默算低分)。"""
    last = None
    for i in range(_RETRIES + 1):
        async with httpx.AsyncClient() as c:
            resp = await c.post(url, json=json, headers=headers, timeout=timeout)
        if resp.status_code not in _RETRY_STATUS:
            return resp
        last = resp
        if i < _RETRIES:
            await asyncio.sleep(_BACKOFF * (2 ** i))
    return last
```

`_RETRY_STATUS` 里只有 429 和几个 5xx。4xx 里的参数错误不进这个集合，那是请求本身有毛病，重试一百次结果也一样。

最后那句「不会静默算低分」值得留意。评估跑一轮要打两千多次上游，其中一次因为限流失败，如果代码悄悄吞掉返回个空列表，这道题就会被记成召回失败，最后算出来的分比真实水平低，而且没人知道为什么低。让它抛出去，评估脚本记成错误，至少这个分数是可疑的这件事是明确的。

## Query 理解

### understand

```python
async def understand(query: str) -> dict:
    """口语→标准问法 + 同义词扩展。扁平字段(list[str],非嵌套对象),避开 glm-5.2 502。"""
    model = llm.structured(_Rewrite)
    r: _Rewrite = await (QUERY_REWRITE_PROMPT | model).ainvoke({"query": query})
    return {"standard": r.standard or query, "expanded": list(r.expanded or [])}
```

两个产物分工不同。`standard` 是去掉口语和情绪的标准问法，「我买的这破玩意儿到底啥时候能到啊」变成「订单配送时效是多久」。`expanded` 是三到六个同义词，邮费和运费、多久到和时效这种。

`r.standard or query` 这个兜底不能省。改写这一步是整条检索链的入口，模型偶尔返回空串，兜不住就是整条链断在第一步。

结构化输出这里又用了扁平字段，跟上一章挖知识那处同源，都是绕开上游对嵌套结构的 502。

同文件里还有个 `expand_queries`，那是第 6 章退款子流程用的，本章不涉及。

## 检索编排

### 四个策略

`search_knowledge` 支持 `vector`、`bm25`、`hybrid`、`hybrid_rerank` 四种走法，线上只用最后一种。

前三种留着是因为评估要用。它们是四根对照柱，没有对照就说不清「加了重排到底提升了多少」，也没法在换了嵌入模型之后重新量一遍。这几十行代码换来的是随时能复现的横向比较。

`hybrid` 和 `hybrid_rerank` 共用前半段的混合召回，只在末尾分岔，一个直接截断返回，一个再过一遍精排。

### split\_clauses

```python
def split_clauses(query: str) -> list[str]:
    """把一问多意图的问题按标点拆成子句;拆不出两条就原样返回一条。

    「我在新疆下单 80 块钱,运费怎么算,会员的免运费能不能抵」这种一句话问三件事的,
    整句去检索时向量会被主语义带跑,只有一个意图能挤进前排。拆开各查一遍再轮转合并,
    每个意图都能占到名额。注意这招得配精排:子句各自的第一名要够准,合并才有意义,
    没有精排的单路检索拆完反而更吵(评估集实测:重排 +0.02、其余三路 -0.04 到 -0.06)。
    """
    parts = [p.strip() for p in _CLAUSE.split(query) if len(p.strip()) >= _MIN_CLAUSE]
    return parts if len(parts) >= 2 else [query]
```

一句话问三件事，整句向量化之后语义重心只能落在其中一个意图上，另外两个连前十都进不去。拆开各查一遍，每个意图都有自己的名额。

`_MIN_CLAUSE = 4` 挡的是拆出来的碎片。「怎么办」三个字单独拿去检索毫无信息量，只会引进噪声。

docstring 最后那句实测数据是本章的方法论缩影：这招在有精排的路径上提升 0.02，在其余三条路径上反而掉 0.04 到 0.06。原因也说清了，子句拆开之后每一路的第一名都得够准，合并才有意义，没有精排把关，拆完只是把噪声乘以三。

每一处优化都带着适用条件，不是加上去就一定更好。这句话本章会反复兑现。

### \_merge\_round\_robin

```python
def _merge_round_robin(lists: list[list[dict]]) -> list[dict]:
    """各子句轮流出一条,按 chunk id 去重;同一小节只留最靠前的那条,重复的挪到后面。"""
    out, seen_id, seen_sec, tail = [], set(), set(), []
    for i in range(max((len(x) for x in lists), default=0)):
        for lst in lists:
            if i >= len(lst):
                continue
            h = lst[i]
            key = h.get("id") or (h.get("section_path", ""), h.get("question", ""))
            if key in seen_id:
                continue
            seen_id.add(key)
```

轮转合并的规则是各子句轮流出一条，保证每个意图在前排都有位置，不会被某一个意图的连续几条挤掉。

同一小节的处理有个细节：命中 `seen_sec` 的会挪进 `tail` 排到最后，而不是直接丢掉。多个子句都指向同一小节，说明那一节确实相关，扔掉可惜，但让它连着占三个名额又会挤掉别的意图。放到后面是个折中。

### arrange\_head\_tail

```python
def arrange_head_tail(items: list) -> list:
    """最相关放首、次相关放尾,其余按序居中(缓解 lost-in-the-middle)。"""
    if len(items) <= 2:
        return items
    return [items[0], *items[2:], items[1]]
```

长上下文里模型对开头和结尾的注意力高于中段，业界管这个叫 lost-in-the-middle。既然中段容易被忽略，就把最相关的两条放在首尾两个位置上。

三行代码，改的是喂进 prompt 的顺序，不改内容。

## 两道证据闸

检索完了不等于能答。`query_faq` 在生成之前设了两道闸，任何一道不过就直接拒答。

### 机械闸

```python
    # 机械闸:无召回 or 最高分低于阈值

    if not hits or top < settings.rerank_min_score:

```

判据是重排的最高分，阈值定在 0.3：

```python
    recall_top_k: int = 50        # dense/BM25 各召回 Top-50
    rerank_top_k: int = 10        # 精排出 Top-10
    subquery_split: bool = True   # 一问多意图时按子句拆开各检索一遍再轮转合并(见 retrieval)
    rerank_min_score: float = 0.3 # 重排最高分低于此 → 检索证据低,拒答
```

返回的形状是 `sufficient=False` 加 `source` 加 `reason`，`citations` 给空列表。`source` 这个字段后面要用，它区分是检索这一步就没召回到，还是召回了但自评说不够，两种失败对应的补救动作完全不同。

### 语义闸

```python
    # 语义闸:生成前自评证据够不够
    ev_texts = [f"{h['question']} {h['answer']}" for h in hits]
    chk = await selfcheck.check_sufficient(query, ev_texts)
    if not chk["useful"]:
        return {"sufficient": False, "source": "self_check",
                "reason": chk["reason"], "citations": []}
```

分数高不代表答得了。检索分衡量的是相似度，一个讲「退货运费」的块跟「换货运费谁承担」的问题相似度可以很高，但它答不了这个问题。这道闸让模型自己看一眼证据，判断够不够。

```python
async def check_sufficient(query: str, evidence_texts: list[str]) -> dict:
    """生成前证据充分性自评。扁平字段 useful/reason(避开 glm-5.2 嵌套数组 502)。"""
    evidence = "\n".join(f"[{i+1}] {t}" for i, t in enumerate(evidence_texts)) or "(无证据)"
    r: _Check = await _chain().ainvoke({"query": query, "evidence": evidence})
    return {"useful": bool(r.useful), "reason": r.reason or ""}
```

闸设在生成之前，判不能就直接拒答，省掉一次生成调用。生成完再判的话，那次生成的钱已经花了，而且已经生成出来的答案很容易被舍不得，最后变成「勉强用一下」。

prompt 里那句「严格只看证据是否够答，不要脑补证据外的知识」是必须写的，自评模型天然倾向拿自己的常识去补全，一补就把这道闸架空了。

### 品类过滤要能退回来

```python
    # 品类过滤稳健性:category 由模型自由填写,常猜错入库值(如「商品手册」≠ 实存「商品规格手册」),
    # 精确过滤会把结果清空致误拒答。过滤后为空/全弱则回退到不过滤重试(过滤是优化、非硬约束)。
    if category and (not hits or hits[0]["rerank_score"] < settings.rerank_min_score):
        hits = await retrieval.search_knowledge(
            query, strategy="hybrid_rerank", category=None, bm25_text=bm25_text)
```

`category` 是模型自己填的，它会填「商品手册」，而库里实存的值是「商品规格手册」。精确匹配一过滤，结果直接清空，前面那道机械闸紧跟着判拒答，用户看到的是「暂时没查到」，可知识明明在库里。

改法是把过滤的定位说清楚：它是优化，不是硬约束。滤完为空或者最高分还是过不了阈值，就退回去不带过滤重查一次。宁可多打一次检索，也别因为一个模型猜错的字符串误拒答。

    citations = [
        {"n": i + 1, "id": h["id"], "section_path": h["section_path"],

### 指标口径

```python
def _hit_rank(hits, expect_section):
    """这一组证据里任意一个小节命中的最靠前名次;一条都没召回回 0。"""
    for i, h in enumerate(hits):
        sp = h.get("section_path", "") or ""
        if any(w in sp for w in expect_section):
            return i + 1
    return 0
```

```python
def _recall_at(ranks: list[int], k: int) -> float:
    """Recall@k:这题需要的几块证据,有几成在前 k 条里。
    单证据题就是老口径(0 或 1);跨文档题按组给部分分,凑齐才是 1.00。"""
    return _mean([1.0 if 0 < r <= k else 0.0 for r in ranks])
```

跨文档题为什么要按组给部分分？因为一道题需要三块知识，全有全无的口径下，召回到两块和一块都没召回是同一个分数，那这个指标就没法指导优化。

MRR 那个口径更值得看一眼：

```python
def _rr(ranks: list[int]) -> float:
    """MRR:单证据题就是命中名次的倒数;跨文档题按「每块证据各自的名次倒数」取平均,
    漏掉的那块记 0。不用「最后一块到位」的名次算,那样两块证据的题上限只有 0.5,
    和单证据桶放进同一张图会被误读成检索变差了。"""
    return _mean([(1.0 / r if r else 0.0) for r in ranks])
```

按「最后一块到位的名次」算 MRR 听起来很自然，但两块证据的题最好情况是第 1、第 2 条都命中，最后一块的名次是 2，倒数只有 0.5。这个上限是口径带来的，跟检索质量无关。跨文档桶的 MRR 天生比单证据桶低一半，画在同一张图里，读图的人会得出「跨文档场景检索变差了」的结论。

评估脚本自己也会出错，而且指标口径定歪了比没有指标更危险，因为错误的结论会被当成事实继续往下传。

### 评估里的生成端为什么要固定

`RAG_ANSWER_PROMPT` 这套引用规则只被评估脚本引用，线上的生成规则挂在 `AGENT_SYSTEM` 的「query\_faq 结果处理」那一节里。

两边不共用是刻意的。评估要量的是检索策略这一个变量，四个策略必须共用同一个生成器，答案的差异才算得到检索身上。生成端跟着一起变的话，分数变了也说不清是哪一边的功劳。

### faith\_cases

忠实度裁判判出来的每一条编造，除了写进报告，还单独进一张表：

```sql
  eval_id       VARCHAR(16)     NOT NULL                COMMENT '评估集题号,如 A43;一题一行',
  ...
  seen_count    INT UNSIGNED    NOT NULL DEFAULT 1      COMMENT '被判编造的累计次数(跨轮)',
```

报告是产物，重跑一次就被覆盖，上一轮判出的个案连同它的处置状态一起没了。而这些个案的价值恰恰在跨轮追溯，同一道题反复被判编造，说明库里那一格一直没补对。

`uk_eval_id` 保证一题一行，再次被判编造不新增行，只更新快照并且 `seen_count` 加一。已经标了「已解决」的题又被判出来，状态会自动退回「未解决」，那是复发不是新问题，得让它重新出现在待处理列表里。

`citations` 存的是当轮喂给模型的证据全集，不只是被引用的那几条。裁判说「证据里没有」，追溯时得看得到当时手里到底有哪几条、实际只引了哪几条，没被引用的那些同样是判断依据。
