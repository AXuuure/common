用户报一个手机号说要查物流，模型先拿手机号查一遍订单，从订单里翻出物流单号，再拿这个单号去查一次物流状态。可当时的系统只许模型开一次工具调用，走完查订单这一步就没了下文，只能用户再继续推进询问。



其实解决也简单，往工具调用外面套一个循环，让模型想查多久就查多久。但光把循环套上还不够，还得想明白一件更重要的事：客服系统真把主动权整个交出去，让模型自己想干嘛就干嘛，捅出来的乱子，比查不到一次物流严重得多。



这一章要交代清楚的，正是这个循环该配在哪、怎么配，才既接得住「手机号查物流」这种活，又不至于放出去就收不回来。

![](<images/理论学习：Workflow 编排与 ReAct 循环-01-phone-logistics-chain-break.png>)

## 先说清这一章怎么读：骨架先搭，细节后面再展开

读这一章之前，有件事先说清楚：后面会点到几个名字，这一章只注重骨架，每个节点的施工图留给对应章节去画。一句话里的「它」「这个」怎么补全、用户到底想干嘛怎么判断，这些留给后面意图识别那一章。



外部工具怎么用 MCP 协议接进来，是后面工具系统那一章的事。



答不上来的问题怎么进数据飞轮，则要等到可观测性与数据飞轮那一章。这几块这一章都会露个脸，认出它是干什么用的就够。



这一章真正要交代清楚的，是骨架本身长什么样、每个节点各管一段什么职责。

![](<images/理论学习：Workflow 编排与 ReAct 循环-02-chapter-route-map.png>)

## 两个主角：Workflow 是什么，Agent 又是什么

回到手机号查物流这件事：模型能不能自己拿主意先查订单再查物流，取决于系统给它的是 Workflow 的活法还是 Agent 的活法，先把这两个词的意思搞清楚。



「Workflow」说的是开发者把整条处理流程写死在代码里，第一步做什么、第二步做什么、遇到什么条件走哪个分支，全在写代码的时候就定好，运行时严格照着这条路径走，不会节外生枝。



「Agent」反过来，把「下一步该干嘛」这个决定权交给了大模型，它自己判断要不要调用工具、调哪一个、调完看到结果要不要再调一次，整个过程运行时才现场决定，没人提前写死。



这两个词的差别，落在控制权交给谁：Workflow 交给写代码的人，Agent 交给运行时的模型。想清楚这层区别，后面聊「为什么要把两者拼在一起用」才有的放矢。

![](<images/理论学习：Workflow 编排与 ReAct 循环-05-workflow-vs-agent.png>)

## 客服请求走一圈：六个节点怎么接力

先来看看整体的流程，用户发一句消息进来，头一步是「指代消解」，把「它多少钱」这种依赖上下文才看得懂的话，补全成「蓝牙耳机多少钱」这种独立成立的问题，不然模型不知道「它」到底指的是啥。



紧接着是「意图识别」，识别用户到底想干嘛，是问物流、查订单、问商品、要退款退货、要售后、投诉，还是单纯闲聊。



第三步开始按意图「分流」，遇到知识类问题，比如政策、商品 FAQ，流程强制先走一趟检索，把资料先捞出来当上下文；



碰到物流、订单、售后这些业务数据类的问题，直接交给下一步处理；



纯粹闲聊搭话的，既不检索也不进后面的执行环节，直接回一句写死的话术把话题引回产品咨询；



判成投诉的，先回一句安抚的话，再把「转人工」和「建工单」两个选项交给用户自己点，想找真人还是想留个工单都由他定，接着往下聊也行；这条分支同样不进后面的执行环节。

![](<images/理论学习：Workflow 编排与 ReAct 循环-06-intent-routing-funnel.png>)

走到第四步，是这一章要花最多篇幅讲的「Agent」。不过知识类这条分支在进 Agent 之前，还先经过一道置信度闸。



这道置信度闸判的是检索到的证据够不够回答这个问题：够，才把证据连同问题一起交给 Agent 作答；不够，就直接走兜底话术，同时把这个问题记下来，留给后面的数据飞轮处理。它特意卡在 Agent 之前——Agent 的答复是逐字流式吐给用户的，等答完再判证据就晚了，弱证据凑出来的答案早已经发出去。业务数据类分支没有检索证据，不走这道闸，分流后直接进 Agent。



最后一步是记录日志，把这一路上模型想了什么、调了哪些工具、花了多少 token 全部留痕，这是后面讲可观测性那一章的地基。



这几个节点里，指代消解、意图识别、分流、以及知识类进 Agent 前的证据闸，走的都是 Workflow 那条确定性路径；只有主力 Agent 是运行时的临场判断；最后记日志又回到确定性的代码逻辑。

![](<images/理论学习：Workflow 编排与 ReAct 循环-03-six-node-relay.png>)

## 主力 Agent 的引擎：ReAct 循环

前面一直说主力 Agent 会自己判断该调哪个工具、按什么顺序调，那么Agent到底是什么，是怎么运作的，是时候拆开看了。



主流的做法叫「ReAct」，Reasoning 加 Acting 拼起来的名字，中文可以念成「推理加行动」。它跑的是一个三步循环：先让模型想一句现在该干嘛，这一步叫「Thought」；想清楚了就据此调用一个工具，这一步叫「Action」；工具执行完，结果递回去给模型看，这个环节的名字是「Observation」。拿到 Observation 之后不算完，循环回到第一步，模型拿着这个新结果重新想一次下一步该干嘛，如此往复，直到它判断信息已经够了，才收敛出最终答复。

![](<images/理论学习：Workflow 编排与 ReAct 循环-07-react-loop.png>)

这套循环的精髓，就藏在「每拿到一个 Observation 就重新想一次」这句话里。模型走一步看一步，中间结果会影响下一步该干嘛，不是提前把整条路径规划好再一口气执行完。回到手机号查物流那个例子：物流单号得先从订单里取，所以模型先用手机号查订单，拿到结果看到订单已发货、带着物流单号，才据此决定下一步去查这个单号的物流。下一步查什么，是盯着上一步的结果临场定的，这正是 ReAct 跟事先写死的分支流程最本质的差别。

![](<images/理论学习：Workflow 编排与 ReAct 循环-08-phone-logistics-react-loop.png>)

也正是这套循环，让主力 Agent 自己就能应付难易不同的意图。查个订单状态这种简单意图，模型走一步，看到订单结果就够回答用户了，直接收敛；跨订单加物流加售后综合判断的复杂意图，走完一步发现信息还不够，接着想、接着查，多走几步才收敛。更省事的是知识类提问，资料前面已经检索好、随问题一起递进来，模型第一步就发现手上的上下文够用，连工具都不用调，直接组织语言作答，跟裸 LLM 调用一次没什么两样。



换句话说，Agent 是纯 LLM 能力的超集：简单场景它退化成一次普通调用，不多花一分成本；真到了要取数、要多步判断的场景，它才会展开成好几轮循环，也就不用在它前面再加一层「这事简单还是复杂」的判断，各种分支全都被Agent吸收进去了。

![](<images/理论学习：Workflow 编排与 ReAct 循环-09-agent-simple-complex.png>)

## 祛魅：循环这东西，你自己也写得出来

Agent 听着像个挺玄乎的概念，实际拆开看一眼骨架，没那么神秘。



模型调一次，看它有没有要求调工具；有就执行、把结果塞回对话历史；没有就说明它想清楚了，直接把这句话当最终答案收工。这套逻辑用一个 `for` 循环就能写出来：

```python
async def run_agent(query: str, max_turns: int = 6):
    messages = [HumanMessage(query)]
    for _ in range(max_turns):
        ai_msg = await llm_with_tools.ainvoke(messages)
        messages.append(ai_msg)
        if not ai_msg.tool_calls:
            return ai_msg                      # 想清楚了，收敛
        for tool_call in ai_msg.tool_calls:
            tool = TOOL_REGISTRY[tool_call["name"]]
            tool_msg = await tool.ainvoke(tool_call)
            messages.append(tool_msg)          # 结果塞回去，下一圈接着想
    return messages[-1]                # max_turns 用尽仍没收敛，这里拿到的是工具结果不是答复，生产得改走兜底话术
```

跟第二章那段只跑一轮的代码放在一起看，改动其实不大：那时候模型第二次回复带着新的工具调用也不再接了，这里换成外面套一圈 `for`，模型只要还想接着查，就让它接着查，直到 `max_turns` 封顶，或者它自己说不用再查了为止。当初留的那个问号，答案就是这十来行代码。



这里顺便把 `max_turns` 这道闸说清楚，它管的是「模型钻牛角尖出不来」。工具描述写得含糊、两个工具用途重叠，模型看完结果一转身又调同一个，能这么耗下去。步数封顶就是给它一个硬上限：一步一次模型调用，数得清、好解释。各家 Agent SDK 给的也是同一件东西，LangChain 的 `max_iterations` 默认 15，Claude Agent SDK 叫 `max_turns`。我们这个客服场景一轮最多两三步能查完，封到 6 步够用还留了余量。



这里要提醒一句常见的误会：**token 花销不该拿来当停止条件**。它防的不是打转，是烧钱和撑爆上下文。ReAct 每走一步都要把工具结果追加进上下文再整段重喂一遍，所以花销是滚着涨的，该管，但该在别处管：阈值得按真实用量分布标定，标得偏一点就会掐在模型已经决定调工具、结果还没拿到的那一刻，用户看到的是半句「好的，我来查一下」然后没了下文。这条线怎么划、按 token 还是按钱算，放到第 9 章跟成本统计一起讲，那时候有真实数据可依。

![步数封顶和成本控制防的是两件事](<images/理论学习：Workflow 编排与 ReAct 循环-18-stop-conditions-turns-vs-cost.png>)





祛魅的意义不在这段代码本身，而在提醒一件事：Agent 说到底是给大模型配一个能反复调用工具的循环，外加一份工具清单，不是某个框架变出来的魔法。这一章后面要讲的 LangGraph，做的也是同一件事，只是把这个循环放进一个更大的图里管理，方便和别的确定性节点摆在一起编排，没有重新发明什么。

![](<images/理论学习：Workflow 编排与 ReAct 循环-10-agent-loop-demystified.png>)

## Workflow 里那个 AI 节点，为什么裸 LLM 和写死分支都不够用

循环是看明白了，可主力节点这一步为什么非得是 Agent 不可？还是拿手机号查物流说事，看看另外两条路走不走得通。



第一条路，让 LLM 裸着上，不给它配任何工具。它没办法凭空知道这个手机号名下的订单状态和物流进度，这些数据得去查数据库或者调用业务系统的API，模型的训练语料里压根没有。



第二条路，学知识类分支的样子，先让流程把数据查好、再请模型开口：把「先查订单再查物流」这条步骤写死在Workflow里。这条路能用，可惜走不远。业务数据这边不一样，拆循环的时候已经看到，往下走哪一步常常依赖上一步查出来的结果，订单状态不一样，接下来该查什么完全不同。每冒出一种新组合就加一条新分支，代码很快就爆炸，改一次分支就得测一遍所有旧分支有没有被牵连，维护成本比业务本身还重。



这两条路都走不通，兜了一圈还是得把「先查什么、再查什么」这个决定权交出去，让模型运行时自己判断该调哪个工具、按什么顺序调，也就是前面说的 Agent 的活法。它跟裸 LLM 的区别在于手里多了工具，跟写死分支的区别在于不需要开发者提前替它想好每一种排列组合。

![](<images/理论学习：Workflow 编排与 ReAct 循环-11-llm-workflow-agent-choice.png>)

## 全交给 Agent 会怎样

主力节点该配 Agent，这件事定了。那能不能干脆再往前走一步，前面指代消解、意图识别、分流这几步也一并交给 Agent，让它从用户开口那一刻起自己全权处理，整套系统只剩一个巨大的 Agent 循环？



客服这类要担责任的场景，工程团队做架构决策时，本能都会先求稳：宁可流程写得笨一点，也要出了问题能一步步查到是哪个环节的锅。全交给 Agent ，灵活是真灵活，代价也摆在明面上。决定权交给模型之后，它也会带来流程上的不确定性，会带来三个问题。



第一个是排查问题。同一句用户提问，跑两次 Agent，中间的思考路径可能都不一样，这一次先查订单再查物流，下一次说不定先查了商品信息，排查问题的时候很难指着某一步说「就是它错了」，调试和监控的难度比确定性流程高出一大截。

![](<images/理论学习：Workflow 编排与 ReAct 循环-12-agent-debug-nondeterminism.png>)

第二个是漏了流程：模型会自己「忘事」。知识类问题本该先去检索一遍资料再作答，可全权交给 Agent 之后，它有时候漏调工具去检索资料，凭自己记的那点训练语料直接给答案，答案听着挺像那么回事，其实资料里根本没这一条，纯属编的。低置信度的时候本该老实说没查到、走兜底话术，可 Agent 一旦学「聪明」了，也可能硬凑一个听起来说得过去的回答糊弄过去。这两条都是业务上碰不得的硬约束，一旦被绕过，用户拿到的是一个自信满满的错误答案，比「暂时回答不了」更麻烦。

![](<images/理论学习：Workflow 编排与 ReAct 循环-13-agent-skips-retrieval.png>)

第三个是响应太慢。对于智能客服来说，大量用户只会问几句问题，我们必须正确地对用户的首句问题或前几句问题迅速准确回答，所以不能依赖于 Agent 自己去探索和使用 RAG，时间不可控，稳定性也是。

## Workflow 把硬约束焊进轨道

跳过检索硬答、该拒答不拒答，能不能靠 Workflow 补回来？能，而且这正是 Workflow 最拿手的地方。



前面讲六步接力的时候提过，指代消解、意图识别、按意图分流这几步走的是确定性路径。放着这几步不交给 Agent 自己判断，好处正是这里：知识类问题该不该先检索，写死成一条规矩，凡是判定成知识类的意图，一律先走一趟检索，检索结果作为上下文一并交给主力 Agent，不用每次都让模型临场决定。写死在流程里，模型就没有「忘记检索」这一说。



写死成规矩之后，幻觉率明显能压下去，而且检索这一步本身很快，相比模型推理和生成的耗时，多这一趟查询几乎不增加多少成本，用一点点确定性成本换稳定性和可控性，这个ROI收益是可以的。



同样的思路也用在置信度兜底上：证据不够的时候，流程强制回一句兜底话术，不让模型自己硬编一个听着像样的答案糊弄过去。



Workflow 在这里干的事，是把几条不容商量的硬约束，从「希望模型别出错」这种一厢情愿，变成「代码逻辑上模型压根绕不过去」这种硬性保证。可观测性也是跟着这条路径一起来的，每个节点各管一段职责，出了问题能顺着路径一步步查是哪个节点的锅，这一点后面讲可观测性那一章会再展开。

![](<images/理论学习：Workflow 编排与 ReAct 循环-14-workflow-guardrails-track.png>)

## 骨架归 Workflow，脑子归主力 Agent

两条路各自的短板和长处摆出来之后，答案已经不难猜：生产环境里几乎不存在非此即彼的选择，Workflow 和 Agent 往往合在一起用，谁也离不开谁。



具体怎么合：用 Workflow 编排出一条确定性骨架，把意图识别、分流这些硬约束嵌入在路径节点上，保证系统整体行为可控、可观测、可调试；再把最需要临场判断的那部分工作，交给主力 Agent 这一个执行节点去干，让它在骨架划定的范围内自由发挥，进行组合多变、依赖中间结果的业务逻辑。骨架管稳定，主力 Agent 管灵活，两者各司其职。

![](<images/理论学习：Workflow 编排与 ReAct 循环-15-workflow-agent-train.png>)

## 编排层为什么选 LangGraph

骨架和脑子的分工定下来了，接下来用什么把这些节点串起来呢？



前面几章一直在用的 LangChain，组织方式是链式的，用一个 `|` 符号把几个 Runnable 首尾接起来，跑起来就像一条流水线，上一步的输出直接喂给下一步。这套写法处理「从头到尾一条直线」的流程很顺手，第一章接 LLM、做流式输出用的就是这套。



客服这条完整流程不是一条直线，意图识别完要分流，分出去的几条支线还要在主力 Agent 那里重新汇合，状态还得从最开始的用户消息一路带到最后的日志记录。链式结构对于这种「分流再汇合」这种图状的走法不适合，硬拿链去拼，要么拼得七扭八歪，要么干脆拼不出来。

![](<images/理论学习：Workflow 编排与 ReAct 循环-16-langchain-vs-langgraph.png>)

LangGraph 换了一套模型，把每一步都做成图上的一个命名「节点」，节点之间用「边」连起来，边上可以挂条件，决定走哪条分支；一份共享的「State」顺着图走完全程，每个节点都能读它、改它。指代消解是一个节点，意图识别是一个节点，主力 Agent 也只是众多节点里的一个，各管一段职责，谁跟谁连、什么条件下往哪条边走，一目了然：

```python
graph = StateGraph(ConversationState)
graph.add_node("resolve_reference", resolve_reference_node)    # 指代消解
graph.add_node("classify_intent", classify_intent_node)        # 意图识别
graph.add_node("retrieve_knowledge", retrieve_knowledge_node)  # 知识检索
graph.add_node("main_agent", main_agent_node)                  # 主力 Agent
graph.add_node("confidence_check", confidence_check_node)      # 置信度判断
graph.add_node("fallback_reply", fallback_reply_node)          # 兜底话术

graph.add_edge("resolve_reference", "classify_intent")         # 直连边：消解完必进意图识别
graph.add_conditional_edges("classify_intent", route_by_intent, {  # 条件边：按意图分流
    "knowledge": "retrieve_knowledge",   # 知识类，先走一趟检索
    "business": "main_agent",            # 业务数据类，直进主力 Agent
    # 闲聊、投诉两条出口略去，先看清骨架
})
graph.add_edge("retrieve_knowledge", "confidence_check")       # 知识类：检索完先过证据闸
graph.add_conditional_edges("confidence_check", confidence_gate, {  # 生成前证据闸：进 Agent 前先判证据够不够
    "strong": "main_agent",              # 证据够 → 交给主力 Agent 作答
    "weak": "fallback_reply",            # 证据弱 → 直接兜底话术，不进 Agent
})

```

`add_node` 用于定义节点，`add_edge` 是给节点之间加直连边，`add_conditional_edges` 接一条按判断走不同分支的边，`route_by_intent` 这个函数返回什么，就往哪条边走。



前面六步流程里「知识类走检索、业务类直接进 Agent」这条分流规则，落到代码里就是这么一行条件边，就是计算机数据结构里的图结构。

![](<images/理论学习：Workflow 编排与 ReAct 循环-04-langgraph-stategraph.png>)

迁移也很方便，前面几章接 LLM 用的 `ChatOpenAI`、写 Prompt 用的模板、做流式输出的流程，放进 LangGraph 的节点里照样能用，一个都不用换掉。而且图的状态自带「checkpoint」持久化能力，中断了能接着跑，再往后配 Langfuse 做可观测，也是顺着这张图天然对齐每个节点。



可能有的同学会问：为什么不干脆用 Dify、Coze 这类智能体低代码平台把这套骨架拖拽出来，省得自己写代码接节点？低代码平台确实能省掉不少体力活，但换来的是链路被封在平台里，出了问题很难看清楚某一步具体在做什么，也没法按自己的业务逻辑精细控制每个节点；真要接自己的数据库和鉴权体系，平台照样得写代码对接，并不是拖拖拽拽就零成本上线。



这门课要教的，正是怎么用 AI 工程化地把这套系统一行行写出来。

## 本章小结

这一章从「手机号查物流」讲起，先把 Workflow 和 Agent 这两个词的意思搞清楚，再顺着电商客服完整的六步流程，看清楚哪几步该在路径上、哪一步该交给模型临场判断。



纯 Agent 守不住业务硬约束，纯 Workflow 又接不住组合多变的业务逻辑，答案是两者拼起来用：Workflow 搭一条确定性骨架，主力 Agent 站在骨架中心，靠 ReAct 循环自己判断该调哪个工具、走几步才收敛。



这套循环拆开看不过是一段带工具清单的 `for` 循环，真正让它管用的，是外面这张 LangGraph 图，把它和前后那些确定性节点安置进同一套编排里，各管一段职责。



骨架这一章算是搭完了，图上还留着几个先点名没细讲的节点，从下一章开始，逐个把它们的内部打开来看。
