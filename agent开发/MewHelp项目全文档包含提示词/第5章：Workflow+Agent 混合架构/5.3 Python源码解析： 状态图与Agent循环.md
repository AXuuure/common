## 祛魅：Agent 就是个带工具清单的 for 循环

### bare\_agent\_loop.py

在引入任何框架之前，先看看不用框架长什么样：

```python
async def run_agent(query: str, max_turns: int = 6):
    specs = {s.name: s for s in await registry.get_all_specs()}   # ch08:内置+MCP 现拉
    model = get_chat_model().bind_tools([s.tool for s in specs.values()])
    messages = [SystemMessage(AGENT_SYSTEM), HumanMessage(query)]
    for step in range(1, max_turns + 1):
        ai = await model.ainvoke(messages)
        messages.append(ai)
        if not ai.tool_calls:
            print(f"[第{step}步] 无工具调用 → 收敛")
            return ai.content
        for tc in ai.tool_calls:
            print(f"[第{step}步] 调用工具 {tc['name']} args={tc['args']}")
            run = await engine.execute_tool_call(tc, 0, specs)
            messages.append(run.tool_message)
```

绑上工具调模型，模型要是申请了工具就执行、把结果回灌进消息列表，没申请就收敛返回。外面套一个 `for`。

跟第 2 章那圈单轮编排比，差别只有这个 `for`。当时讲完工具调用有个问题没往下说，调完一次还想接着调怎么办，答案就在这里。所谓 Agent，本质上就是把「调模型、执行工具、回灌」这三步放进循环，让模型自己决定什么时候停。

```python
    print(f"[封顶] max_turns={max_turns} 用尽仍未收敛,生产环境此处应走兜底话术")
```

再加一个步数封顶。模型不一定会收敛，可能一直申请工具，也可能在两个工具之间来回，所以循环必须有上限，上限用尽还得有兜底。

那么问题来了：核心就这么点东西，为什么还要引入 LangGraph？

答案是这个裸循环只解决了「多步」，没解决「不是每个问题都该进循环」。用户说句「你好」也丢进 ReAct 环里，模型得先思考一遍要不要调工具。退款这种有固定流程的场景，也没理由让模型每次现想一遍步骤。本章要做的就是把确定的部分固化成边，把不确定的部分留给循环。

## State：图里流的是什么

### ConversationState

```python
class ConversationState(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]  # 跨轮历史,checkpointer 续接
    ...
    intent: str            # 九类之一(ch08 增「人工」)
    resolved_query: str    # 指代消解+改写后的完整问句(下游检索/判意图都用它)
    intent_confidence: float  # 意图 JSON 的 confidence(0-1)
    ...
    steps: int             # ReAct 步数(停止条件)
    tokens_used: int       # token 预算累加
    suggested_actions: list  # [{"type": "transfer_human"} | {"type": "create_ticket", "draft": {...}}]
    trace: Annotated[dict, merge_dict]  # 留痕
```

`total=False` 让所有字段都变成可选的，于是节点只需要返回自己改动的那几个键，不用每次构造一份完整 State。

真正值得看的是 `Annotated` 这层包装。带 `Annotated` 的字段是「有 reducer 的通道」，节点返回 `{"messages": [ai]}` 时，`add_messages` 会把这一条追加到已有列表后面，而不是把整个列表换掉。没有 `Annotated` 的就是普通标量，后写的直接覆盖先写的。

这个区分后面会反复咬人，先记住。

字段上的章节注释是全课的状态总账。`summary` 那几个字段是第 7 章分层上下文的摘要与锚点，`evidence_confidence` 和 `retrieved_snapshot` 是第 9 章的置信度与快照，`order_id` / `order_data` 是第 6 章退款流程的。本章立的是 `messages`、`intent`、`route`、`steps`、`tokens_used`、`trace` 这几样。

### merge\_dict

```python
def merge_dict(a: dict | None, b: dict | None) -> dict:
    """trace 累加 reducer:后写覆盖同键,其余合并;b 为 None 是重置哨兵。
    入口(_graph_input)每轮传 trace=None 清零本轮 trace——merge 通道塞 {} 清不掉
    (merge(旧,{})=旧),故用 None 触发重置,杜绝上一轮条件键(如 retrieve_policy)跨轮残留。
    图内各节点写 trace 恒为真 dict(从不传 None),故 None 专属入口重置,不误伤累加。"""
    if b is None:
        return {}
    return {**(a or {}), **b}
```

`trace` 是留痕通道，每个节点往里写自己那部分，图跑完拼成一份完整记录。合并逻辑本身没什么，有意思的是那个 `None`。

State 按会话持久化，下一轮进来时 `trace` 里还留着上一轮的内容。想在入口清零，直觉是传个空字典，但这是 merge 通道，空字典合并进去等于什么都没做。清不掉。

于是约定一个哨兵：传 `None` 表示重置。这个约定能成立，前提是图里的节点从不传 `None`，只有入口会传。前提写在了 docstring 里，这种约定必须写下来，不然下一个人在节点里返回 `{"trace": None}` 就会把整份留痕清空。

LangGraph 的用法就两件事，注册节点和连边。节点是个函数，吃 State 返回一个字典。

`fetch_order` 和 `retrieve_policy` 是第 6 章退款子流程的两个节点，本章还没有。

### 连边

```python
    # 骨架:消解 → 意图 → 分流
    b.add_edge(START, "resolve_reference")
    b.add_edge("resolve_reference", "classify_intent")
    b.add_conditional_edges("classify_intent", route_by_intent, {
        "escalate": "complaint_reply",
        "fallback_script": "script_reply",
        "knowledge": "retrieve_knowledge",
        "refund_flow": "fetch_order",
        "business": "main_agent",
    })
```

固定的路径用 `add_edge`，一条直线。要分岔的用 `add_conditional_edges`，给一个路由函数和一张映射表：函数返回什么字符串，就走映射表里对应的那个节点。

`route_by_intent` 返回 `"knowledge"`，图就走到 `retrieve_knowledge`。函数返回值和映射表的键必须对得上，这是本章一个隐性的耦合点，等会讲分流规则时还会提到。

```python
    # 主力 Agent ReAct 环
    b.add_conditional_edges("main_agent", should_continue, {
        "continue": "agent_tools",
        "stop": "log",
    })
    b.add_edge("agent_tools", "main_agent")
    # 确定性出口 → 日志 → END
    b.add_edge("complaint_reply", "log")
    b.add_edge("script_reply", "log")
    b.add_edge("fallback_reply", "log")
    b.add_edge("log", END)
```

ReAct 环就是这么表达的。`main_agent` 的条件边接到 `agent_tools`，`agent_tools` 再无条件连回 `main_agent`，环就闭上了。刚才那个裸循环的 `for`，在图里就是这两条边。

所有出口最后都汇到 `log`。留痕和落库这两件事不能指望每个节点自觉，收到一个点上，只要图跑完就一定发生。

### confidence\_check 为什么是个实体节点

```python
async def confidence_check(state) -> dict:
    """置信度兜底(生成前证据闸)的实体节点:留痕门控决策供可观测;
    强/弱的实际分流在其后的条件边 confidence_gate(读 evidence_strong)。"""
    decision = "strong" if state.get("evidence_strong") else "weak"
    return {"trace": {"confidence": decision}}
```

这个节点什么都不改，只往 `trace` 里写一句判断结果，真正的分流在它后面的条件边上。看着像脱裤子放屁。

理由是条件边在 LangGraph 里是纯函数，不进执行记录，图跑完之后你看不到它当时判了什么。而「证据够不够、放不放行」是这条链上最需要被观测的决策点，出了问题第一个要查的就是它。所以单开一个节点，专门为了让这个判断在记录里留下痕迹。

## 分流：写死的那部分

### INTENT\_TO\_ROUTE

```python
INTENT_TO_ROUTE: dict[str, str] = {
    "投诉": "escalate",
    "闲聊": "fallback_script",
    "其他": "fallback_script",
    "商品咨询": "knowledge",
    "退款退货": "refund_flow",
    "售后": "refund_flow",
    "人工": "business",   # ch08:明确要求建工单/转人工 → 主力 Agent 走 create_ticket 确认流
    "物流": "business",
    "订单": "business",
}


def route_by_intent(state) -> str:
    """按意图分流;未知意图保守归 business(让 Agent 自己应对)。"""
    return INTENT_TO_ROUTE.get(state.get("intent", ""), "business")
```

意图由模型判，映射到哪个出口由这张表定死。模型只负责回答「这句话属于哪一类」，至于「投诉类该怎么处理」，代码说了算。

这张表的值就是上面条件边映射表的键。两处必须一致，写在一个地方才不会漂，所以注释里专门写了「单一来源不漂移」。真要在别处再抄一份，改的时候漏掉一处，症状是某类意图静默走到错误的出口，日志上还看不出异常。

未知意图归 `business` 是保守选择。归到兜底话术的话，模型判飞一次用户就被打发走了。归给主力 Agent，它至少还有机会调工具去查。

### classify

```python
class _Intent(BaseModel):
    intent: Literal["物流", "订单", "商品咨询", "退款退货", "售后", "投诉", "人工", "闲聊", "其他"] = Field(
        description="九类意图之一")
    confidence: float = Field(default=0.5, ge=0.0, le=1.0, description="判断把握 0-1")
```

`Literal` 进 schema 之后变成枚举，模型只能从这九个值里选一个。比让它自由输出字符串、再在代码里做字符串匹配可靠得多，后者要处理「物流查询」「物流类」「物流相关」这类近似值，处理不完。

```python
    model = llm.structured(_Intent, model=settings.intent_model or None)
    try:

    return {"intent": intent, "confidence": float(r.confidence)}
```

schema 约束了，不代表模型一定守约，所以还有一道 `in INTENTS` 的二次校验。整个调用包在 `try` 里，任何异常都归「其他」并把 `confidence` 记 0，让下游能看出这是个兜底而不是真判断。

`settings.intent_model or None` 这个回落留了个口子：意图分类可以单独指定模型，不配就跟着聊天模型走。留这个口子的取向是求准，宁可配个更够格的大模型也别在分流上判飞。这一步每轮都跑，判错一次，后面整条路都跑偏，影响面比省那点钱大得多。

## ReAct 什么时候停

```python
def should_continue(state) -> str:
    """ReAct 停止条件:无 tool_calls 就收敛,步数封顶则强停,否则继续。

    只用步数封顶,不在这里卡 token。防打转靠的是步数:一步一次模型调用,数得清、好解释,
    各家 Agent SDK 给的也是 max_turns / max_iterations 这类步数上限。
    token 花销是另一件事——它管的是烧钱和撑爆上下文,不是死循环,阈值要按真实用量分布标定,
    归第 9 章的成本控制一起讲。混在这里卡,一次估偏就把工具链整条掐断,而且掐在模型
    已经决定调工具之后,用户只看到半句「我这就去查」。"""
    last = state["messages"][-1]
    has_tool_calls = isinstance(last, AIMessage) and bool(last.tool_calls)
    if not has_tool_calls:
        return "stop"
    if state.get("steps", 0) >= settings.max_agent_steps:
        return "stop"
    return "continue"
```

判断顺序是先看模型自己收没收敛，最后一条消息没有 `tool_calls` 就说明它已经在组织答案了，直接停。有 `tool_calls` 才看步数封顶。

这个函数最值得读的是 docstring 那段。停止条件里要不要加一个 token 上限，是个看起来很自然的想法，实际上是两件事混在了一起。

步数管的是死循环。一步对应一次模型调用，数得清、好解释，出了问题看日志「第几步」一目了然，各家 Agent SDK 给的也都是 `max_turns` 这类步数上限。

token 管的是烧钱和撑爆上下文。它的阈值得按真实用量分布标定，而且该在成本控制那一层统一处理。把它塞进这里的后果是：阈值估偏一次，工具链就被整条掐断，而且掐的位置是在模型已经决定调工具之后，用户那边只看到半句「我这就去查」，然后没了。

## 几个节点

### classify\_intent

```python
async def classify_intent(state) -> dict:
    """意图四件套:八类 + confidence + 「其他」兜底。吃 resolved_query(空则回落原话)+ 最近历史
    判当前意图(应对物流→退款→物流漂移)。把归属出口 route 落进 State(供 _agent_messages 判注入、
    log 留痕;route_by_intent 条件边按同一 INTENT_TO_ROUTE 分流,单一来源不漂移)。"""
    query = state.get("resolved_query") or _user_text(state)
    r = await intent_mod.classify(query, _history_text(state))
    intent, conf = r["intent"], r["confidence"]
    route = INTENT_TO_ROUTE.get(intent, "business")
```

节点把 `route` 也算了一遍写进 State。条件边等会自己还会算一次，重复了，但下游的日志和后面章节的节点都要读这个值，落进 State 比让每个用到的地方各查一次表省事。

`_history_text(state)` 那个参数是为了应对意图漂移。用户先问物流，再说要退款，又回头问物流，只看当前这句话很容易判错。

本章验收要看的是 `trace: {"forced_rag": True}` 这一条，它证明这个节点确实被走到了。

### main\_agent

```python
async def main_agent(state, config=None) -> dict:
    """ReAct 推理步:调模型(带工具),累加 steps 与 token 消耗。
    注:streaming=True 下 ChatOpenAI 默认不回传 usage_metadata;usage 回传已在
    get_chat_model 统一收口(ch09 stream_usage=True),这里不再单独 bind。"""
    specs = await registry.get_all_specs()   # ch08 现问现拿:内置+MCP 合并清单,每轮现拉
    model = get_chat_model(streaming=True).bind_tools([s.tool for s in specs])
    msgs = _agent_messages(state)
    _log_model_context(state, msgs)   # ch07:摘要+滑窗进日志,验收 tail -f 可见
    ai: AIMessage = await model.ainvoke(msgs, config)
    usage = ai.usage_metadata or {}
    used = usage.get("total_tokens", 0)
    ...
    return {"messages": [ai],
            "steps": state.get("steps", 0) + 1,
            "tokens_used": state.get("tokens_used", 0) + used}
```

一次 ReAct 推理步：拿工具清单、绑上、调模型、累加计数。

返回值只有三个键。`messages` 走 `add_messages`，追加进历史。`steps` 和 `tokens_used` 是普通标量，累加得在节点里手写，`state.get(...) + 1` 这种写法看着土，但它明确表达了「读旧值、加一、写回」，比再造一个 reducer 通道好读。

`get_all_specs()` 每轮现拉是第 8 章的动态工具清单，`_agent_messages` 那套滑窗拼装是第 7 章的上下文管理。本章这里就是一句 `bind_tools` 加一句 `ainvoke`。

### 答复从哪来

```python
def resolve_answer(state) -> str:
    """最终答复:确定性节点写在 state['answer'];Agent 答复取最后一条 AIMessage 文本。"""
    if state.get("answer"):
        return state["answer"]
    for m in reversed(state.get("messages", [])):
        if isinstance(m, AIMessage):
            content = m.content
            if isinstance(content, str):
                return content
            return "".join(p.get("text", "") for p in content if isinstance(p, dict))
    return ""
```

答复有两个来源。确定性节点写在 `state["answer"]` 里，Agent 的答复在消息列表最后一条 `AIMessage` 上。这个函数把两种统一成一个字符串，接口层和日志层都调它，不用各自判断这一轮走的是哪条路。

`log_node` 兼两职，往日志里写一行完整留痕，再往 MySQL 落一条 assistant 消息。因为所有出口都连到它，这两件事一定会发生。

## 运行时

### checkpointer

```python
async def init_graph() -> None:
    """lifespan 起:开持久 checkpointer + setup + 编译图。"""
    global _graph, _cm
    _cm = AsyncSqliteSaver.from_conn_string(settings.checkpointer_db_path)
    checkpointer = await _cm.__aenter__()
    await checkpointer.setup()
    # ch09:编译时挂一次 Langfuse 回调,全图自动 trace(未配置时原样返回,零依赖)
    _graph = attach_observability(build_graph(checkpointer=checkpointer))
    logger.info("图已编译,checkpointer=%s", settings.checkpointer_db_path)
```

`checkpointer` 是 LangGraph 的持久化机制，按 `thread_id` 把 State 存下来，下次带同一个 `thread_id` 进来就能接着上次的状态跑。本课直接拿 `conversation_id` 当 `thread_id`。

`_cm` 这个模块级变量是必须留着的。`AsyncSqliteSaver.from_conn_string` 给的是一个异步上下文管理器，手动 `__aenter__` 之后如果不持有它，对象被回收连接就断了，症状是跑着跑着数据库连接莫名其妙没了。

### \_graph\_input

```python
def _graph_input(user_id: str, message: str, cid: int, msg_id: int,
                 summary: str, summary_upto: int) -> dict:
    # 显式重置每轮的输出通道:checkpointer 按 thread_id 持久化 State,这些无 reducer 的标量
    # 会跨轮残留(如上一轮闲聊/投诉的 answer、建工单可选项串到本轮),须在入口清零。
    # messages 有 add_messages reducer(追加=跨轮历史),不清;steps/tokens_used 是本轮预算。
    # ch07:用户消息带 db-{msg_id} 锚点(滑窗与摘要边界对齐);summary 两字段每轮从库刷新。
    return {"messages": [HumanMessage(message, id=f"db-{msg_id}")], "user_id": user_id,
            "conversation_id": cid, "steps": 0, "tokens_used": 0,
            "answer": "", "suggested_actions": [], "evidence": "",
            "evidence_strong": False, "citations": [],
```

这个函数存在的唯一理由，就是前面埋下的那个坑。

State 按会话持久化，那些没有 reducer 的标量字段会一直留在里面。上一轮用户投诉，`answer` 里写着安抚话术，`suggested_actions` 里挂着建工单选项。这一轮用户问物流，走的是主力 Agent 那条路，它不会去写 `answer`，于是 `resolve_answer` 读到的还是上一轮那句安抚话术。

症状是「上一轮的东西冒出来了」，看代码看不出来，因为每个节点单独看都没毛病。

哪些清哪些不清有明确的判据：`messages` 有 reducer，跨轮历史全靠它，不能清。`steps` 和 `tokens_used` 是本轮的预算，每轮归零。`trace` 走那个 `None` 哨兵。其余输出型标量一律清空。

这份清零列表得跟着 State 一起长。往 State 里加了新的输出字段，忘了在这里清，坑就又开了一个。

### 四个入口

| 入口              | 流式 | 场景                        |
| --------------- | -- | ------------------------- |
| `run_turn`      | 否  | `/api/agent`、评估脚本，看得到工具轨迹 |
| `stream_turn`   | 是  | `/api/chat`，前端聊天          |
| `resume_turn`   | 否  | 中断后续跑，第 6 章加的             |
| `stream_resume` | 是  | 中断后续跑流式，第 6 章加的           |

新一轮那两个入口 `run_turn` 和 `stream_turn` 先过 `_ensure_conversation`，会话不存在就抛 `ConversationNotFound`。两个续跑入口自己查一次 `repository.get_conversation`，抛的是同一个异常。到了接口层要分开看：非流式的 `/api/agent` 翻成 404，两个 SSE 接口这时已经 200 开了流，改不了状态码，只能吐一帧 `event: error`。学员写前端错误处理时这两条路得分别接。

### \_stream\_events

```python
    async for mode, chunk in get_graph().astream(
        stream_source, config, stream_mode=["messages", "updates"],
    ):
        if mode == "messages":
            msg, meta = chunk
            if meta.get("langgraph_node") in ANSWER_NODES:
                text = msg.content if isinstance(msg.content, str) else ""
                if text:
                    yield {"type": "delta", "text": text}
```

`stream_mode` 同时开两路。`messages` 那一路给的是模型逐 token 吐出来的内容，`updates` 那一路给的是每个节点返回了什么。

`ANSWER_NODES` 这个白名单很关键：

```python
# 会流式吐答复 token 的节点(其余节点的模型调用 token 不进 delta)
ANSWER_NODES = {"main_agent"}
# 确定性节点把答复写在 state['answer'],整块作为 delta 吐出
DETERMINISTIC_ANSWER_NODES = {"script_reply", "complaint_reply", "fallback_reply"}
# 产出编号引用的检索节点(知识路 retrieve_knowledge + 退款政策路 retrieve_policy)
CITATION_NODES = {"retrieve_knowledge", "retrieve_policy"}
```

图里调模型的节点不止一个。意图分类调一次，Query 改写调一次，证据自评还调一次，这些输出全都不该出现在用户屏幕上。不加白名单的话，用户会看到「商品咨询」「订单配送时效是多久」这些内部产物混在答案里蹦出来。

确定性节点的答复走另一路：

```python
            for node, upd in chunk.items():
                if not isinstance(upd, dict):
                    continue
                if node in DETERMINISTIC_ANSWER_NODES and upd.get("answer"):
                    yield {"type": "delta", "text": upd["answer"]}
                if node in CITATION_NODES and upd.get("citations"):
                    yield {"type": "citations", "items": upd["citations"]}
```

它们压根没调模型，没有 token 可以逐个吐，所以整块话术作为一个 delta 发出去。前端两种都当 delta 处理，看不出区别。

`citations` 帧从检索节点的返回值里捞，`tool` 帧从 `agent_tools` 返回的消息里捞。`interrupt` 那段是第 6 章的中断机制。

### dedup\_actions

```python
def dedup_actions(actions: list) -> list:
    """跨多个 ReAct 轮次累积的 suggested_actions 可能重复(如 agent 多次提议
    create_ticket);按 type 去重,保留每种 type 首次出现的那条。"""
    seen = set()
    out = []
    for action in actions:
        t = action.get("type")
        if t in seen:
            continue
        seen.add(t)
        out.append(action)
    return out
```

ReAct 环可能走好几轮，每一轮模型都可能提议同一个动作。前端收到两个一模一样的「建工单」按钮很难看，所以攒到流末尾统一去重再发，这也是 `actions` 帧不在中途发的原因。

## 验收怎么写

```python
        b = await agent(c, "我手机尾号1001那个订单发货没?到哪了?")
        names = {tc["name"] for tc in b["tool_calls"]}
        chained = {"query_order", "query_logistics"} <= names
        results.append(("验收5 ReAct 顺序多步(order→logistics 链)", chained, sorted(names)))
```

这一条验的是真·多步。问物流要先查订单拿到物流单号，再拿单号查物流，模型必须连着调两个工具。单轮 Function Calling 做不到这件事，能过说明 ReAct 环真的转起来了。

验收走的是 `/api/agent` 非流式接口，因为要看 `tool_calls` 这份轨迹，流式接口只给帧。

Agent 的端到端验收本来就不是百分之百确定的，同一道题跑两遍可能一次调了两个工具、一次只调了一个。这件事要写在报告里，而不是反复重跑到全绿再截图。
