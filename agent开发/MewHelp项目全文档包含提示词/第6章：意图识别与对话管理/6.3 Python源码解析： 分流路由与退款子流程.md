
## 指代消解

### coref.resolve

```python
async def resolve(query: str, history: str = "") -> str:
    """指代消解 + 口语归一。结合历史把半截话补成完整问句;已完整则原样。
    出错兜底:返回原句(不阻断下游)。"""
    try:
        model = get_chat_model()
        r = await (COREF_REWRITE_PROMPT | model).ainvoke(
            {"query": query, "history": history or "(无)"})
        text = (r.content if isinstance(r.content, str) else "").strip()
    except Exception:
        return query
    return text or query
```

用户上一句问「订单 1001 到哪了」，这一句说「那它什么时候能退」，「它」得先还原成订单 1001，后面的意图识别和检索才有东西可用。

这里没走结构化输出，要的就是一句话，`Field` 那套约束没有意义。

`except` 兜底和末尾的 `text or query` 是同一件事的两道保险。消解是整条链的第一步，它挂了不能把后面全带崩。模型超时也好、返回空串也好，回落到用户原话，至少后面还能正常走，最多是那句「那它呢」判不准意图。

消解的结果写进 `resolved_query`，原始消息还在 `messages` 里。两者并存，下游想要哪个取哪个，意图识别和检索用消解后的，日志和落库用原话。

### \_history\_text

```python
def _history_text(state, max_turns: int = 6) -> str:
    """摘要行 + 滑窗内最近若干轮(不含本轮最后一条 human),供 coref/意图读上下文。
    ch07:先按摘要边界切窗再取尾——跨滑窗的指代(「最开始那个订单」)靠摘要行兜住。"""
    msgs = memory.build_window(state.get("messages", []),
                               state.get("summary_upto_msg_id") or 0,
                               state.get("layer1_from_msg_id") or 0)
    prior = msgs[:-1] if msgs else []
```

消解和意图识别共用这份上下文。

`prior = msgs[:-1]` 这一刀不能少。最后一条是本轮那句待消解的话，它是被处理的对象，不能同时当自己的上下文。不切掉的话，模型会看到「那它呢」既在历史里又在问题里，容易原样返回。

`build_window` 的三个参数分别是全量消息、摘要已覆盖到哪条、半压层从哪条开始。后两个锚点是第 7 章三层上下文管理的核心，本章先知道它从这里读上下文就行。

## 退款子流程

分流表里「退款退货」和「售后」都指向 `refund_flow`。前两步是写死的节点接力，先取单、再检索政策，拿到的订单数据和政策证据一起交给主力 Agent，由它判能不能退。所以退款这条路照样有 ReAct 环，后面讲 `agent_tools` 拦 `submit_refund`，拦的就是模型在这个环里调出来的那次。

理由是这条流程的顺序是确定的：先知道是哪一单，再拿到相关政策，然后才谈得上判断能不能退。既然确定，就没必要每次让模型现想一遍，尤其是模型偶尔会跳过取单直接开始讲政策。

### fetch\_order

先看抽订单号：

```python
# 4+ 位连续数字视作订单号;用 lookaround 而非 \b——CJK 与数字同属 \w,\b 在「订单1001」处不成立
_ORDER_RE = re.compile(r"(?<!\d)(\d{4,})(?!\d)")
```

这条注释救了不少时间。`\b` 是「单词边界」，判据是两侧一个属于 `\w` 一个不属于。中文汉字在 Python 的 Unicode 模式下属于 `\w`，数字也属于 `\w`，所以「订单1001」里「单」和「1」之间根本不构成边界，`\b\d{4,}\b` 一个都匹配不到。改成前后不是数字的 lookaround 才对。

```python
async def fetch_order(state) -> dict:
    """退款子流程第一步:抽订单号;缺了、或者报的不是自己的单,都 interrupt 弹订单选择器
    等前端点选(resume 回填);拿到后 order_snapshot 取订单数据。
    interrupt 之前只做只读(resume 时本节点从头重跑)。

    归属校验放在这里而不是只放在工具里:退款子流程是确定性节点,不经 agent_tools,
    工具那道校验够不着。用户随口报的号、resume 端点回传的号,都得过同一道判断。"""
    uid = state.get("user_id", "")
    oid = state.get("order_id") or _extract_order_id(
        state.get("resolved_query") or _user_text(state))
    while not business.owns_order(uid, str(oid or "")):
        orders = business.list_user_orders(uid)                        # 只读,可安全重跑
        oid = interrupt({"type": "select_order", "orders": orders})    # resume 回填订单号
    data = business.order_snapshot(oid)
```

这个 `while` 循环是本章最值得看的一段。

抽不到订单号，或者抽到了但那单不是这个人的，都走 `interrupt`。这一行会让整个图停在这里，把订单列表发给前端，用户点一个，`resume` 把订单号送回来成为 `interrupt()` 的返回值，循环再判一次。用户点了别人的单，接着弹。

写成 `while` 而不是 `if`，正是因为 `resume` 回来的值同样不可信，得走同一道校验。

docstring 里那条纪律更重要：**`interrupt` 之前只做只读操作**。

`resume` 的时候，被中断的节点是从头重新执行的，不是从 `interrupt` 那一行接着跑。所以 `interrupt` 之前的代码会执行两遍，写库、扣款、发消息这类有副作用的动作放在前面就会做两次。这个函数里 `interrupt` 之前只有抽号和列订单，都是只读的，重跑安全。

归属校验放在这里的理由写在了 docstring 第二段。退款子流程是确定性节点，不经过 `agent_tools`，所以工具里那道 `owns_order` 对这条路径完全够不着。而用户随口报的号、前端 `resume` 端点回传的号，都是外部输入，都得过同一道判断。

### retrieve\_policy

```python
    base = state.get("resolved_query") or _user_text(state)
    od = state.get("order_data") or {}
    seed = f"{base} {od.get('status', '')}".strip()
    queries = await query_understanding.expand_queries(seed)

    merged: dict = {}                       # chunk id -> 最高分 hit
    for q in queries:
        for h in await retrieval.search_knowledge(q, strategy="hybrid_rerank", bm25_text=q):
            cur = merged.get(h["id"])
            if cur is None or h["rerank_score"] > cur["rerank_score"]:
                merged[h["id"]] = h
```

跟知识路那个 `retrieve_knowledge` 比，这里多做了两件事。

一是把订单状态拼进种子问题。同样问「能退吗」，已签收和未发货适用的条款不一样，不带状态去检索，召回的政策可能压根用不上。

二是扩写成三条各查一遍再合并。退款政策散落在退货条款、运费规则、时效说明好几处，单条 query 很难一次全捞到。

合并按 chunk id 去重，保留每个 id 的最高分。同一块知识被两条 query 都命中很正常，取它命中得最好的那次分数来排序才合理，取最后一次或者平均都会让排序失真。

```python
async def expand_queries(query: str) -> list[str]:
    """把一句问题泛化成检索友好查询(强制 JSON 单字段,扁平 list[str] 避开 glm 502)。
    严格取前 3 条非空;模型异常/全空则回落 [query],保证 retrieve_policy 至少有一条可查。
    只在 refund_flow 的 retrieve_policy 检索侧调(核心场景),商品咨询走 understand 的轻扩。"""
```

`qs[:3] or [query]` 这个兜底跟 `coref.resolve` 是一个思路：扩写失败也得保证至少有一条能查，不能让这一步的失败把整条退款链掐断。

它跟第 4 章的 `understand` 分工不同，那个是改写加同义词，主要服务 BM25。这个是泛化成多条独立查询，各查一遍再合并。开销大，所以只在退款这条核心链路上用。

扩写只在检索侧现查现用，库里的知识还是一份，不会因为扩写多存几条。

## 拦成表单的写操作

### submit\_refund

```python
@tool
async def submit_refund(
    order_id: Annotated[str, Field(description="要退款的订单号")],
    user_id: Annotated[str, InjectedToolArg],
    reason: Annotated[str | None, Field(description="退款原因(可选,最终以前端固定类目下拉为准)")] = None,
) -> dict:
    """判定这一单可以退款后,调用本工具发起退款申请。实际提交由前端退款表单确认后落库,
    本工具只表示『这一单可以退,已把提交入口交给用户』。
    发起人身份由系统注入,你不要传 user_id。"""
    # 写操作有二次确认门,但那道门确认的是「要不要退」,不是「这单是不是你的」,归属得单独校验
    if not owns_order(user_id, order_id):
        return dict(NOT_OWNED)
    return {"status": "待用户确认", "order_id": order_id}
```

这个工具的语义得看清楚：它不退款。它表示的是「我判断这一单符合退款条件，已经把提交入口交给用户了」。

这层语义必须写进 docstring 给模型看。不写的话，模型调完工具看到 `status` 是个成功的返回，下一句就会跟用户说「已为您办理退款」，而实际上什么都还没发生。

那行注释区分了两件容易混的事：二次确认门确认的是「要不要退」，归属校验回答的是「这单是不是你的」。有了前者不等于有了后者，用户在表单上点确认，确认的是自己想退，并不能证明这单属于他。

## 中断怎么传到前端

### interrupt 帧

```python
            if "__interrupt__" in chunk:
                payload = chunk["__interrupt__"][0].value
                # 带上 conversation_id:中断时不发 done 帧,前端要靠这个才知道续跑用哪个会话。
                # ch08:负载按中断类型透传(select_order 带 orders,confirm_ticket 带 preview),
                # 前端按 kind 分发。
                ev = {"type": "interrupt", "kind": payload.get("type", ""), "conversation_id": cid}
                for k in ("orders", "preview"):
                    if payload.get(k) is not None:
                        ev[k] = payload[k]
                yield ev
                return
```

中断发生时这个流就结束了，`return` 直接跳出，后面的 `done` 帧发不出去。所以 `conversation_id` 必须挂在中断帧上，前端拿着它才知道续跑要用哪个会话。这一点是调前端时才暴露出来的，正常结束那条路径上会话号在 `done` 帧里。

负载按类型透传的写法留了余地，第 8 章加工单预览时只需要在 `for k in (...)` 里多一个键，`kind` 交给前端分发。

### /api/actions/resume


这个端点的事件流跟 `/api/chat` 完全同构，`delta` / `tool` / `citations` / `actions` / `interrupt` / `done` 六种帧一样，所以前端两处可以共用同一套解析逻辑。

真正提交退款的是另一个端点，它的入参形状值得看一眼：

```python

    conversation_id: int
    order_id: str = Field(min_length=1)
    reason: Literal["七天无理由", "质量问题", "发错货", "不想要了", "其他"]
```

`reason` 是个 `Literal` 枚举，前端渲染成固定下拉，后端也只收这五个值。`submit_refund` 那个工具的参数说明里写着「最终以前端固定类目下拉为准」，说的就是这里：模型可以顺手填一个自由文本的退款原因，但真正落库的那一份必须是用户从固定类目里选的。工单系统后面要按原因分类统计，自由文本进去就统计不动了。

### resume 值形状守卫

一个端点两种中断，代价是形状可能配错：


这段是第 8 章加的，但它治的正是本章「一个端点两种中断」的设计，放在这里讲完整。

## 小结

本章给图加了一个前置的消解节点和一条确定性的退款链，中间靠 `interrupt` 把「停下来问用户」这件事表达成了一行代码。

代价是被中断的节点必须可重跑，`interrupt` 之前不能有副作用。这条约束会一直管到第 8 章的工具确认流。
