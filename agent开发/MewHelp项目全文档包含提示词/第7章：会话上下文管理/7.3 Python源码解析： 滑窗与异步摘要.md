## 两个锚点划出三段

### 边界存哪

```sql
ALTER TABLE conversations
  ADD COLUMN summary             TEXT            NULL COMMENT '最近若干段摘要拼好的投影' AFTER status,
  ADD COLUMN summary_upto_msg_id BIGINT UNSIGNED NULL COMMENT '摘要已覆盖到哪条消息' AFTER summary,
  ADD COLUMN layer1_from_msg_id  BIGINT UNSIGNED NULL COMMENT '层1(原文)起点,之前渲染成半压形态';
```

两个 id 就把一条会话的历史划成了三段：

```plain&#x20;text
id ≤ summary_upto_msg_id          已进摘要，不再出现在窗口里
summary_upto < id ≤ layer1_from   层 2，渲染成半压形态
id > layer1_from                  层 1，原样
```

这两个数是本章的枢纽。降级不搬数据，只把 `layer1_from_msg_id` 往后挪。消息一直躺在 State 里没动过，变的只是渲染方式。所以同一份输入渲染多少次结果都一样，不必额外记「这条压过没有」。

摘要段落另开一张表，一段一行：

```sql
CREATE TABLE conversation_summaries (
  conversation_id BIGINT UNSIGNED NOT NULL,
  seq             INT             NOT NULL COMMENT '第几段,从 1 开始',
  from_msg_id     BIGINT UNSIGNED NOT NULL COMMENT '这段覆盖的消息区间,闭区间',
  upto_msg_id     BIGINT UNSIGNED NOT NULL,
  content         TEXT            NOT NULL,
  UNIQUE KEY uk_conv_seq (conversation_id, seq)
);
```

为什么不把几段拼一起塞回 `conversations.summary` 就算了？因为段落是只追加的，用表能直接按 `seq` 倒序取最近几段，也能按 `upto_msg_id` 反查某条消息落在哪一段里。`conversations.summary` 那一列留着，存的是**最近若干段拼好的投影**，读的时候少一次查询。

配套的旋钮在 `config.py` 分两组。一组管预算：

```python
    model_context_window: int = 0           # 0=按 chat_model 查表,填非 0 则以此为准
    context_budget_turns: int = 20          # 预算按多少轮的最坏情况留
    max_user_input_tokens: int = 2000       # X:单轮用户输入上限
    max_output_tokens: int = 10000          # Y:单轮输出上限,兼作 API max_tokens
```

另一组管分层：

```python
    layer1_ratio: float = 0.7               # 层1 占滑窗预算的比例,其余归层2
    layer2_reply_keep_chars: int = 60       # 降到层2 的客服答复留多少字
    layer2_tool_keep_tokens: int = 200      # 工具结果小于这个数原样留,大块的压成一行
    summary_inject_segments: int = 3        # 注入时带最近几段摘要
```

摘要模型那个口子还留着：摘要是离线任务，对延迟不敏感，可以单独换个便宜模型，不配就跟着聊天模型走。

边界字段必须和内容一起更新。摘要新了、边界还是旧的，下次算滑窗时会把已经压过的那段又当成原文喂一遍，模型看到同一段对话两次。

### db-{msg\_id} 锚点

边界是 MySQL 的消息 id，而滑窗要切的是 LangGraph State 里那个消息列表。两边本来没有共同坐标：State 里的 `HumanMessage` 只是内存对象，它不知道自己在数据库里是第几行。

解法是入口那一行：

```python
    return {"messages": [HumanMessage(message, id=f"db-{msg_id}")], "user_id": user_id,
```

用户消息先落库拿到自增 id，再把这个 id 塞进 `HumanMessage` 的 `id` 字段带进图。从此 State 里的每条用户消息都背着自己的数据库坐标。

取的时候反解一次：

```python
def _db_msg_id(m: BaseMessage) -> int | None:
    """从消息 id 解出 MySQL 消息 id(入口约定 HumanMessage.id=f"db-{msg_id}");非锚点返回 None。"""
    mid = getattr(m, "id", None)
    if isinstance(mid, str) and mid.startswith(_DB_ID_PREFIX):
        try:
            return int(mid[len(_DB_ID_PREFIX):])
        except ValueError:
            return None
    return None
```

三层容错：没有 `id`、前缀对不上、解不出整数，一律返回 `None`。这不是防御性编程凑数，本章上线之前的会话，它们的消息压根没有这个锚点，`checkpointer` 里存着的老 State 读出来就是这样。

## 滑窗层

### 预算：滑窗能用多少

滑窗的上限不是常量，每次现算：

```python
def window_budget() -> int:
    """滑窗能用多少 token。配置里 context_window_max_tokens 填了非 0 就以它为准
    (回滚用),否则按窗口预算算。"""
    if settings.context_window_max_tokens > 0:
        return settings.context_window_max_tokens
    return budget.compute().sliding
```

`budget.compute()` 在 `core/budget.py` 里，是个不碰 IO 的纯计算：

```python
    fixed = (settings.system_prompt_tokens + evidence_tokens() + summary_tokens()
             + settings.max_output_tokens + settings.budget_safety_margin)
    room = w - fixed - turn_peak_tokens()
    by_turns = settings.context_budget_turns * history_per_turn()
    sliding = min(by_turns, room)
```

固定开销是四块：系统提示与工具 schema、检索证据、要注入的几段摘要、输出预留，再加一点估算误差余量。

`room` 那行还多扣了一个 `turn_peak_tokens()`，这一刀不能省。它是当前这一轮跑起来的瞬时占用：ReAct 最多走 `max_agent_steps` 步，每步的 AI 消息和工具结果都要同时挂在消息列表里喂给下一步。不扣它，三万二的窗口也会报「健康」，而那种窗口第四步就撞墙。

轮数项乘的是 `history_per_turn()` 而不是峰值。这两个数合成一个必有一边错：峰值管「这一轮跑不跑得起来」，稳态管「历史能留住几轮」。旧轮的工具结果早被 `compress_tool_result` 压成一行了，拿峰值去乘二十轮，等于给一个系统自己承诺不会出现的状态留位置，白白把覆盖轮数砍掉一多半。

窗口大小 `w` 自己会找：

```python
def resolve_window() -> int:
    """窗口取值优先级:配置显式填写 > 按模型名查表 > 保守默认。"""
    if settings.model_context_window > 0:
        return settings.model_context_window
    return lookup_window(settings.chat_model)[0]
```

为什么要查表？因为 OpenAI 兼容的 `/v1/models` 只返回 `id`、`object`、`created`、`owned_by` 四个字段，拿不到窗口大小，只能本地维护一张模型名到窗口的映射。查不到就落到一个保守值，宁可估小也别撞墙。查表还得先剥掉 provider 前缀，硅基流动那类上游给的模型名是 `deepseek-ai/DeepSeek-V4-Flash`，直接前缀匹配会落空。

`healthy` 这个字段是给启动自检用的：预算连一轮最坏情况都装不下就是 `False`，`lifespan` 里据此打一条 error，别等运行时撞墙才知道换错了模型。

### token 怎么数

```python
def count_tokens(messages) -> int:
    return count_tokens_approximately(
        messages, chars_per_token=settings.zh_chars_per_token)
```

这个薄封装是必须的。`count_tokens_approximately` 默认 `chars_per_token=4.0`，那是照英文定的，实测 29 个汉字被估成 12 个 token，低估四倍多。裁剪、预算判断、日志统计全走这一个入口，口径才对得齐。

口径和上限得一起改。只把口径校准、上限还是原来那个数，等于把闸门一下收紧好几倍，本来装得下的历史被白白裁掉。反过来只调大上限不校准口径，闸门看着松了，实际发出去的还是超。两边动一边，都是往反方向走。

还有一处更隐蔽。这个校准值的方向必须全局统一：`count_tokens_approximately` 的 `chars_per_token` 参数是拿它当**除数**用的，要是别的地方顺手写成 `字数 × 校准值`，两条路能差出一倍多，判据就会系统性地比预算严一截。所以凡是拿字数换 token 的地方都收口到同一个函数里，别各写各的。

### build\_window

```python
def build_window(messages: list[BaseMessage], summary_upto_msg_id: int,
                 layer1_from_msg_id: int = 0,
                 max_tokens: int | None = None) -> list[BaseMessage]:
    window = messages[_index_after(messages, summary_upto_msg_id):]
    if layer1_from_msg_id:
        split = _index_after(window, layer1_from_msg_id)
        if split:
            window = to_layer2(window[:split]) + window[split:]
    trimmed = trim_history(window, max_tokens=max_tokens or window_budget())
    return trimmed or window
```

三步。先按摘要边界砍掉已经压走的那段，再按层 1 锚点把前半截渲染成半压形态，最后交给第 1 章那个 `trim_messages` 按 token 上限兜一道。

`_index_after` 找的是第一条 id 大于给定边界的用户消息，两个锚点复用同一个函数：

```python
def _index_after(messages: list[BaseMessage], msg_id: int) -> int:
    if not msg_id:
        return 0
    for i, m in enumerate(messages):
        if isinstance(m, HumanMessage):
            did = _db_msg_id(m)
            if did is not None and did > msg_id:
                return i
    return 0
```

只找 `HumanMessage` 是有讲究的。一轮对话从用户提问开始，从助手回复中间切进去，窗口开头会是一段没有问题的答案，模型读到一半悬空的上下文。

锚点缺失或为 0 时那一刀不切，整段照旧进 trim，行为退化成单层原文加 token 兜底。老会话没有这两个字段也能跑。

`return trimmed or window` 这个兜底不能省。`trim_messages` 在单条消息本身就超预算的情况下会返回空列表，用户粘了一大段日志进来就是这种情况。这时候宁可超预算把原窗发出去，也不能给模型一个空的消息列表，那必炸。

最后那句「只在调模型前现拼，不改 State」是一条纪律。全量历史一直原样留在 State 里，切窗每次现算。这样切窗策略随时能改，改完对历史会话立刻生效，而不用去动已经存下来的数据。

### 层 2 长什么样

三个纯函数，不依赖模型也不依赖数据库：

```python
def compress_reply(text: str, keep_chars: int | None = None) -> str:
    """客服答复降到层 2 的形态:留头部。客服答复第一句通常就是结论。"""
    n = settings.layer2_reply_keep_chars if keep_chars is None else keep_chars
    if not text or len(text) <= n:
        return text
    return text[:n] + "…(略)"


def compress_tool_result(name: str, content: str) -> str:
    if chars_to_tokens(len(content)) <= settings.layer2_tool_keep_tokens:
        return content
    return f"(已调用 {name or '工具'},结果从略)"
```

工具结果按大小分开处理。订单字段那种一百多字的原样留着，下一轮追问还用得上。检索证据那种三千多字的压成一行，那份证据是某一轮用来答某一个问题的，答完就不该再占位，真要数据下次实时查还更新。

`to_layer2` 把一批消息整体渲染一遍，用户消息原样返回，AI 消息过 `compress_reply`，工具消息过 `compress_tool_result`。渲染时保留原来的 `id`，因为 id 是切窗的锚点，丢了下一轮就定位不到。

AI 消息上的 `tool_calls` 也得原样带上，这一条踩过坑。压的是正文，不是这一轮的调用结构：后面那条 `ToolMessage` 拿 `tool_call_id` 指着它，新建 `AIMessage` 时漏掉 `tool_calls`，这对引用就断了，上游直接回 400 说「tool result's tool id not found」，整轮回复挂掉。造测试数据时很容易只写 `content`，这个洞因此能一直藏着，直到层 2 真被接进请求路径才炸。

这几个函数是幂等的：同一批消息进来，渲染多少次结果都一样。这条性质决定了降级可以随时重算，不必额外记状态。

### 同一份摘要，两种形态

```python
def summary_line(summary: str | None) -> str:
    """coref/意图的历史文本前缀:单行摘要;无摘要空串。"""
    return f"(早前对话摘要:{summary})" if summary else ""


def summary_system(summary: str | None) -> SystemMessage | None:
    """把摘要包成带标题的文本块;无摘要 None。"""
    if not summary:
        return None
    return SystemMessage(f"## 早前对话摘要(更早轮次已压缩,其中事实可信)\n{summary}")
```

名字里带 system，可它的返回值从来没当 system 消息用过。两类消费方拿的都是里头那段文本：指代消解和意图识别把它压成一行前缀塞在纯文本历史最上面，主力 Agent 那边只取 `.content`，并进本轮材料那条 `HumanMessage`。摘要要是真单独占一条 `SystemMessage`，就跟后面「整条列表只有一条 SystemMessage」那条约束撞上了。

两处都在没有摘要时返回空值，调用方拿到空串或者 `None` 就跳过，不用各写一遍判断。

`summary_system` 那句「其中事实可信」是写给模型看的。不点明的话，模型容易把摘要当成一段可疑的二手转述，答题时反而绕开它。

### \_agent\_messages

```python
def _agent_messages(state) -> list:
    ...
    window = memory.build_window(state.get("messages", []),
                                 state.get("summary_upto_msg_id") or 0,
                                 state.get("layer1_from_msg_id") or 0)
    turn_ctx = _turn_context(state)
    if turn_ctx:

    return [SystemMessage(AGENT_SYSTEM), *window]
```

顺序是固定的：人设加红线的 system 打头，滑窗原文垫底，摘要和本轮的材料紧跟在用户那句话之后。

整条列表里**只有一条 SystemMessage**，内容恒等于 `AGENT_SYSTEM`，一个字的可变内容都不许拼进去。这条约束是拿真金白银换来的，值得单独说清楚。

各家的 prompt caching 都按**前缀精确匹配**：OpenAI 自动生效、门槛 1024 token，官方明确写「静态内容放开头、可变内容放末尾」。而 system 是 `messages[0]`，把每轮都变的检索证据拼进去，等于让整个前缀从第一个 token 就对不上。这个项目里被挡在变量后面的是 `AGENT_SYSTEM` 加工具 schema 那两千来个 token，本该次次命中。更要命的是 ReAct 环每走一步都重新拼一次 system 发出去，一轮对话里这笔损失是乘上去的。

摘要为什么也不能单独占一条 system，说起来有点反直觉。上游的 chat template 会把消息列表里**所有** system 消息上提、合并成一个头部块渲染，所以「摘要放第二条 system」实际等于把它拼在了 `AGENT_SYSTEM` 后面，工具 schema 又一次被挤到可变内容之后。而摘要是每个会话各不相同的，于是前缀照样作废。这一条是实测撞出来的，不是推演：摘要一进 system，命中数直接归零。

所以本轮才有的那些材料另起一条消息：

```python
def _turn_context(state) -> str:
    """本轮才有的材料:检索证据 + 退款路的订单数据。没有就返回空串。

    顺序不能反:REFUND_JUDGE_HINT 的措辞是「下面给出该订单数据与检索到的退换货政策证据」,
    它假设证据已在前文给过。"""
```

用的是 `HumanMessage` 而不是把 `SystemMessage` 换个位置。原因是有的 chat template 会把消息列表里**所有** system 消息上提、合并到最前面渲染，那样挪了等于没挪，而且从 API 层面完全看不出来。

插入位置也有讲究，它落在滑窗里最后一条用户消息之后，不是整个列表的末尾：

```python
    msg = HumanMessage(turn_ctx, id=TURN_CTX_ID)
    for i in range(len(window) - 1, -1, -1):
        if isinstance(window[i], HumanMessage):
            return [*window[:i + 1], msg, *window[i + 1:]]
    return [*window, msg]
```

为的是 ReAct 轮内也能命中。插在用户那句之后，第 2 步的消息列表 `[Sys, 问, 材料, AI, Tool]` 完整包含第 1 步的 `[Sys, 问, 材料]` 作为前缀。追加到末尾的话第 2 步变成 `[Sys, 问, AI, Tool, 材料]`，公共前缀只到「问」那一条。倒着找、找不到就退化成追加，是因为滑窗被极端裁剪时理论上可能一条用户消息都不剩，不能让它抛异常。

这条材料消息只在拼装时现拼，不写回 `state["messages"]`，跟 `build_window` 那条「只在调模型前现拼，不改 State」是同一个约定。

```python
_KNOWLEDGE_EVIDENCE_HINT = (
    "\n\n## 已检索到的知识证据(请据此作答,每个关键结论后标注来源编号如[1];"
    "证据已给,不要再调用 query_faq;仍可按需调用订单/物流等工具)\n"
```

「证据已给，不要再调用 query\_faq」这句是必需的。知识路已经强制检索过一遍了，不明确叫停的话模型看到手上有 `query_faq` 这个工具，还会再查一次，白花一轮。后半句「仍可按需调用订单/物流等工具」也不能少，不然模型会理解成「所有工具都别调了」。这段文本在证据搬家时一个字都没改，只换了位置。措辞要是跟着一起动，出了问题就分不清是缓存改动惹的还是提示词改动惹的。

### \_log\_model\_context

```python
    # 本轮材料块虽然也是 HumanMessage,但它不是用户说的话,从滑窗里摘出来单独报,
    # 否则「window=N条」会凭空多一条,验收时读不准
    ctx_block = next((m for m in msgs if getattr(m, "id", None) == TURN_CTX_ID), None)

              if not isinstance(m, SystemMessage) and getattr(m, "id", None) != TURN_CTX_ID]
```

上下文管理最难受的地方是看不见。模型答得不对劲，你不知道是它笨还是当时喂进去的东西不对，而喂进去的东西是每轮现拼的，事后翻不出来。

所以每轮把实际发出去的内容打进日志。摘要打全文，反正就一两百字。滑窗每条打角色加前 40 字，够看出这轮带了几条、都是什么话题。再加一个近似 token 数，一眼看出有没有逼近上限。

那个 `TURN_CTX_ID` 是给本轮材料块打的哨兵。它也是 `HumanMessage`，不摘出来的话会被算进滑窗，日志上凭空多一条「用户消息」，验收时数不准。哨兵只能挂在 `id` 上，不能挂 `name`。`name` 会被序列化发给上游，改变请求字节，等于亲手把刚修好的缓存前缀又搞乱了。

真跑起来这一行长这样：

```log
model_ctx conv=91 step=0 summary='(无)' window=1条 本轮材料=722字 tokens≈399
agent_step conv=91 step=1 input=2223 cache_read=2176 total=2560
```

`cache_read` 是判断前面那套安排到底有没有生效的唯一证据。验的时候有个坑要绕开：拿**同一个问题**问两次是测不出东西的，同一个问题检索到的证据也相同，改之前 system 本来就一样、照样会命中。得拿**不同的问题**问，那才是这次改动要解决的场景。

拿两个不相干的问题各开一个会话跑下来是这样：

| 会话      | 问题      | input | cache\_read |
| ------- | ------- | ----- | ----------- |
| conv 91 | 退货政策是什么 | 2223  | 2176        |
| conv 92 | 运费怎么算   | 2266  | 2176        |

两次检索回来的证据完全不同，但共用的那段前缀被完整复用了 2176 个 token，占输入的九成六。这就是把可变内容请出 system 换来的东西。

还有一点值得知道：**这个数字换家上游可能就测不出来**。缓存的粒度各家不一样，有的按大块记，共用前缀不满一整块就报 0。同一份代码在那种上游上跑，看到的是一片零，并不代表安排错了。所以别拿单一上游的数字下「有用没用」的结论，先弄清它的粒度。上游压根不报这个字段时同理，得去服务商控制台看。

## 摘要层

### 摘要边界就是层 1 起点

摘要吃的是层 2，边界不用另算一套，`conversations.layer1_from_msg_id` 就是它的上沿。

```python
    boundary = conv.layer1_from_msg_id or 0
    old_upto = conv.summary_upto_msg_id or 0
    if boundary <= old_upto:
        logger.info("summary skip conv=%s 层2 是空的(边界=%s upto=%s)",
                    conversation_id, boundary, old_upto)
        return
```

两个锚点一夹，`(old_upto, boundary]` 这段就是层 2 的全部内容，压完把摘要边界推到 `boundary`，层 2 当场清空，等着层 1 下一次降级再往里填。相等就说明层 2 是空的，这一趟没活干，直接回。

这里原本不长这样。第一版按轮数算边界，留最近八轮原文、更早的全压掉。那时候滑窗写死三千 token，八轮之外必然溢出，数轮数和看用量说的是同一件事，规则是自洽的。改成从窗口倒推之后两者就脱节了：按轮数那条每次都比层 1 起点伸得更远，一口把还在层 1 的内容吞掉，层 2 于是永远是空的。讲的是三层，跑起来只有两层。

这个错法特别难发现。锚点在动、日志在打、摘要在落库，从外面看一切正常，只有把渲染出来的消息列表逐条摊开，才看得出层 2 那一段压根没被压过。

### run\_summary

边界定下来，接着就是把那一段切出来压掉：

```python
    seg = [m for m in msgs if old_upto < m.id <= boundary]
    dialog = "\n".join(
        f"{'用户' if m.role == 'user' else '客服'}:{m.content}"
        for m in seg if m.content)
    summary = await summarize_dialog(conv.summary or "", dialog)
    if not summary:
        raise ValueError("摘要为空,放弃更新")
    n = await repository.append_summary_segment(
        conversation_id, from_msg_id=old_upto + 1,
        upto_msg_id=boundary, content=summary)
```

`from_msg_id` 取 `old_upto + 1`，跟上一段的 `upto_msg_id` 首尾相接，段与段之间不留缝也不重叠。事后查某条消息进了哪一段，一个区间比对就够。

摘要压出来是空的就抛异常，不写库。写进去一个空段落，锚点照样往前推，那批对话就等于凭空蒸发了，比不压还糟。

`seg` 只取上次边界到这次边界之间那一段。已经压进摘要的不重复压，这既省钱，也避免模型在同一段对话上反复重写导致细节漂移。

```python
    summary = await summarize_dialog(conv.summary or "", dialog)
    if not summary:
        raise ValueError("摘要为空,放弃更新")
    n = await repository.append_summary_segment(
        conversation_id, from_msg_id=old_upto + 1, upto_msg_id=boundary, content=summary)
```

摘要为空按失败处理，抛出去。要是照写不误，库里就多一段空白，前面那批对话等于白压了一次，而且没有任何报错。这种「静默地把好数据换成坏数据」是最难查的一类问题。

写库走 `append_summary_segment`：插一行新段落，同时把 `conversations` 那两个字段更新成新的边界和新的投影，一个 session 一次提交。

投影那段有个坑值得单独说。拼投影要读「已有的最近几段」，这一步必须放在 `s.add(新段)`**之前**：

```python
        prev = (await s.execute(
            select(ConversationSummary.seq, ConversationSummary.content)
            .where(ConversationSummary.conversation_id == conversation_id)
            .order_by(ConversationSummary.seq.desc())
            .limit(max(settings.summary_inject_segments - 1, 0))
        )).all()
        seq = (prev[0].seq if prev else 0) + 1
        s.add(ConversationSummary(...))
```

反过来的话，SQLAlchemy 的 autoflush 会把还没提交的新段也算进这次查询，拼投影时它就出现两次。这个 bug 不看投影内容根本发现不了，段落表本身是对的，只有拼好的那一列多了一行。

### maybe\_schedule\_summary

```python
async def maybe_schedule_summary(conversation_id: int) -> None:
    """轮结束后调用:新增消息数达阈值且无在跑任务 → create_task 后台跑,不 await(不阻塞回复)。
    本函数在用户回复路径上,任何异常只 log 不外抛(触发条件仍在,下一轮重来)。"""
    try:
        if conversation_id in _running:
            return
        conv = await repository.get_conversation(conversation_id)
        if conv is None:
            return
        if not await _should_summarize(conversation_id, conv):
            return
        # 上面两个 await 期间可能有并发触发已入表(TOCTOU),入表前再查一次防双起
        if conversation_id in _running:
            return
```

这个函数挂在 `run_turn` 和 `stream_turn` 的末尾，`create_task` 之后不 `await`，摘要在后台慢慢跑，用户那边该返回就返回。

判断要不要压的那一步单拎出来了：

```python
async def _should_summarize(conversation_id: int, conv) -> bool:
    upto = conv.summary_upto_msg_id or 0
    layer1_from = conv.layer1_from_msg_id or 0
    if layer1_from <= upto:                      # 层 2 是空的
        return False
    msgs = await repository.list_dialog_messages(conversation_id)
    layer2_tok = memory.chars_to_tokens(
        sum(len(m.content or "") for m in msgs if upto < m.id <= layer1_from))
    l2_budget = int(budget.compute().sliding * (1 - settings.layer1_ratio))
    return layer2_tok > l2_budget
```

只有一条判据：层 2 超了自己那份预算才压。

判据看用量不数条数。一轮的长短根本不固定，更要命的是工具消息压根不落 MySQL，`list_dialog_messages` 只取 user 和 assistant 两种角色。数条数看不见工具结果在涨，而它恰恰是历史里最占地方的一块，工具越密集的会话条数看着慢悠悠，实际早就撑爆了。

这里原本还并着一条「距上次摘要新增满 30 条就压一次」的定时器，后来删了。它是双层时代的遗产，留在三层里会坏事：层 1 刚降级一批下来，定时器就把层 2 清空，中间那层根本没机会攒。压缩要花一次模型调用，是实打实的成本，装得下就不该压。

删掉之后有个副作用得知道：默认窗口一百万，层 1 的预算十八万多，按真实会话每轮一百多 token 算，得聊上千轮才轮得到降级。也就是说出厂配置下这条链根本不会启动，那是对的，历史都装得下凭什么要压。想看它跑起来，光调窗口不够。固定开销和单轮峰值是按默认的 X、Y 和步数算的，只把窗口压到两万，`room` 直接变成负数，滑窗归零，启动自检会报「上下文预算不足」。得连着一起压：

```bash
MODEL_CONTEXT_WINDOW=18000 MAX_OUTPUT_TOKENS=2000 MAX_USER_INPUT_TOKENS=2000 \nMAX_AGENT_STEPS=3 TOOL_RESULT_MAX_TOKENS=1200 RERANK_TOP_K=5
```

这组算出来滑窗 5650、层 1 预算 3954、层 2 预算 1695，健康。按真实会话每轮一百多 token 估，二十来轮就会撞到第一次降级，再聊十几轮层 2 攒满，摘要跟着起来。

三处细节值得看。

第一处是整个函数体包在 `try` 里，任何异常只记日志不往外抛。它在用户的回复路径上，抛出去会把一次正常的回复带崩。而摘要没跑成其实无所谓，触发条件还在，下一轮进来自然重新触发。为了一个可以稍后重来的后台任务，牺牲当次回复，不划算。

第二处是那两次 `if conversation_id in _running`。中间隔着两个 `await`，协程在那里会让出控制权，同一会话的另一次触发完全可能在这期间把任务起了。查一次不够，入表之前得再查一次。这是典型的检查与使用之间存在时间窗的问题。

第三处在回调里：

```python
        def _done(t: asyncio.Task) -> None:
            if _running.get(conversation_id) is t:   # 只清自己,防误清后来者
                _running.pop(conversation_id, None)
```

任务结束时从 `_running` 里摘掉自己，但得先确认表里那个确实是自己。直接 `pop` 的话，如果这个任务结束得晚、而新任务已经登记进去了，一 `pop` 就把新任务的登记抹了，防抖失效。

`_running` 是进程内的字典，单机够用。多副本部署时同一个会话可能在两个进程上同时触发摘要，各自算出的边界还不一样，要换成数据库行锁。

## 小结

本章把上下文分成三层：最近几轮留原文，中间一层把客服答复截短、工具结果压成一行、用户原话原样留着，更早的压成一段段梗概。三层的边界由两个消息 id 划出来，降级只挪 id、不搬数据。每层多大不写死，从模型窗口扣掉固定开销再倒推。摘要跑在后台，失败不影响回复。
