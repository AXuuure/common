再看回我们的Agent部分，物流系统的接口、仓储系统、第三方查询，都等着往它手里递。这几样怎么接进来，接进来之后又归谁管，以后要接更多系统怎么办，因此我们需要换成一套注册一下就能用、还不必回头改核心代码的工具生态。

## 五个写死的工具，撑不起真实客服台

先回忆一下第 2 章那五个工具是怎么用起来的。每个工具是一个 Python 函数，`@tool` 装饰器从函数上自动抽出名字、用途描述和参数 Schema，凑成模型要看的说明书。五个工具塞进一个列表 `tools = [...]`，用 `bind_tools` 挂到模型上，再配一张按工具名找函数的注册表 `TOOL_REGISTRY`。模型想要进行工具调用的时候，代码就照着注册表找到函数、执行、返回结果。



它有个绕不过去的前提：那份工具列表是写死在代码里的。想加一个工具，得有人去改源码、往列表里添一行、重新部署、重启服务。



真实客服要伺候的场面，远不止这五样。课程项目为了演示，物流、库存这些数据都是在工具内部随机造出来的；可真上了生产环境，物流系统、仓储系统，还有别的要接的系统，各家的接口各种各样、种类繁多，还随时会变，要接的外部系统一大把。

![](<images/理论学习：工具系统与 MCP 接入-01-external-systems-to-connect.png>)

按第 2 章那套做法，每接一家就是一轮同样的工作：工程师写个新函数、往工具列表里加一行、重新部署、重启服务。更烦的是格式。这家的接口返回长这样，那家的返回长那样，出入参字段各叫各的名，每接一家都得写一层适配代码，把它捏成模型读得懂的统一模样。外部系统接得越多，这层适配代码就堆得越厚，改一处还容易牵动别处。

![](<images/理论学习：工具系统与 MCP 接入-02-adapter-code-pile.png>)

所以在工具调用这块很需要一套「即插即用」的工具标准。新工具注册一下就能用，核心代码一行都不用动，谁提供的工具、内部怎么实现，我们这边不用挨个去迁就。这套标准，正是这一章的主角「MCP」，全称 Model Context Protocol。

## 工具系统的全貌：内置、外部，加一层统管

站在主力 Agent 的角度看，它其实不关心工具是打哪来的，它只想拿到一份「现在能调哪些工具」的清单。真实系统里，这份清单有两个来源。



一个来源是「内置工具」，就是第 2 章那批 `@tool` 写的函数，活在我们自己的代码库里，查的是我们自己的库或者模拟数据。另一个来源是「外部工具」，物流系统、仓储、第三方各自把自己的能力包成一个「MCP Server」，我们这边连过去，就能把它们的工具接过来用，只需要一个入口，非常方便。

![](<images/理论学习：工具系统与 MCP 接入-03-unified-tool-list.png>)

现在有两种来源的工具后，肯定工具数量会变多，所以肯定需要进行管理，这里有两层策略应对。



第一层是「动态发现与注册」。内置工具在服务启动时就登记进来；外部的 MCP 工具则是连上 Server 之后现问现拿，问它「你都有哪些工具、各要什么参数」，把回来的说明书注册进同一份清单。所谓「动态」，就是工具不写死在代码里，运行时去发现。



第二层是统一的「注册管理」和「执行引擎」。不管工具从哪来，都走同一套契约校验、权限控制、超时、重试、结果格式化、审计。

![](<images/理论学习：工具系统与 MCP 接入-04-tool-system-architecture.png>)

这一章接下来就顺着这张全貌往下走：先讲清 MCP 怎么把外部工具做成即插即用，再讲清清单之上那两层统管怎么把内置和外部工具一并管起来，最后落回主力 Agent，看它怎么把业务 MCP 当普通工具来调。

## MCP：外部工具靠什么做到即插即用

回到痛点上：每接一家物流、每接一个仓储，就写一层适配、改一次代码、重启一次服务。各家的工具接口自成一套，我们这边只能一家一家去将就。



MCP 就是来立这套标准的。想想 USB 普及之前，每个外设都有自己的插口和驱动，换个设备就得换根线、装套驱动；USB 把插口和通信方式统一成一个标准之后，任何设备只要做成 USB 的样子，插上任意一个 USB 口就能用。



MCP 干的是同一件事，把「AI 应用怎么跟外部工具对接」这件事，统一成一套开放标准。工具提供方只要把自己的能力按这个标准包成一个 MCP Server，我们这套客服系统按同一个标准做一个「MCP Client」连过去，两边就能对上话，不必再为每一家单独写适配。

![](<images/理论学习：工具系统与 MCP 接入-05-mcp-like-usb.png>)

分工其实很清楚。Server 那边是工具的提供方：物流系统把「查物流」包成一个 MCP Server，仓储系统把「查库存」「查发货仓」包成另一个，每个 Server 对外声明自己有哪些工具、每个工具叫什么、干什么用、要哪些参数。



至于 Server 内部怎么查数据库、怎么调自己的系统，那是它自己的事，我们这边看不见也不用管。Client 那边是工具的使用方，也就是我们的客服系统，连上 Server，把它声明的工具接过来用。Server 提供，Client 消费，两边靠 MCP 这套标准对接。

![](<images/理论学习：工具系统与 MCP 接入-06-mcp-client-server.png>)

即插即用的关窍，藏在 Client 连上 Server 那一刻发生的一件事里。Client 会先问 Server「你都有哪些工具」，Server 就把每个工具的说明书回过来，一个工具一份，里头是工具名、用途描述，还有一份用 JSON Schema 写的参数说明。



拿物流 Server 的「查物流」举个例子，它回过来的说明书长这样：

```json
{
  "name": "query_logistics",                    // 工具名，模型照它点名调用
  "description": "根据订单号查询包裹的物流轨迹",   // 用途说明，模型靠它判断该不该用
  "inputSchema": {                              // 参数说明，就是一份 JSON Schema
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",                       // 参数类型
        "description": "要查询的订单号"
      }
    },
    "required": ["order_id"]                     // 哪些参数必填
  }
}
```

这份说明书你应该觉得眼熟。`@tool` 装饰器从函数上自动抽出来的那份东西，工具名、`description`、参数 Schema，跟 MCP Server 声明的说明书是一个模子里出来的。内置工具的说明书由装饰器在代码里生成，MCP 工具的说明书连上 Server 现问回来，长相一致，拿到手都能直接塞进模型要看的那份工具清单。



物流系统哪天在自己的 Server 上新加了一个「查退货物流」的工具，我们这边什么都不用改，Client 连上去请求一遍，这个新工具就自动冒进清单里了。工具的增减发生在 Server 那边，我们这靠动态发现自动跟上。

![](<images/理论学习：工具系统与 MCP 接入-07-dynamic-tool-discovery.png>)

至于 Client 和 Server 之间具体怎么通信，MCP 留了两种常见接法：Server 跟客服系统跑在同一台机器上时，可以当成一个本地子进程直接对接；Server 是远端的独立服务时，走 HTTP 这类网络协议连过去。本地还是远程，对上层调用工具的方式没影响，这里知道有这层区分就够。

![](<images/理论学习：工具系统与 MCP 接入-08-local-vs-remote-mcp.png>)

## 给所有工具立一份契约：注册、校验、权限

不管一个工具是内置的，还是从某个 MCP Server 来的，它都得带齐三样：工具名、用途描述、一份 JSON Schema 写的参数定义。JSON Schema 第 2 章见过，它规定每个参数叫什么、是什么类型、哪些必填、取值有没有限定范围。



这份 Schema 是工具和模型之间的格式合同：模型照着它生成调用参数，我们照着它检查参数对不对。注册的过程，就是把每个工具连同这份说明书登记进统一的工具表，之后按工具名就能找到它、调用它。

![](<images/理论学习：工具系统与 MCP 接入-09-tool-registration-table.png>)

再说参数校验。模型生成的调用参数不一定靠谱，该给订单号的时候给了空，手机号只填了 8 位，都可能发生。所以工具真正执行之前，先拿参数对着 JSON Schema 校验一遍，类型不对、必填缺失、取值越界的，一律拦下。拦下之后别抛个异常了事，把校验错误的说明当成一条工具结果给模型，让它看到哪里填错了，好回头追问用户或者重新组织调用。这一步第 2 章对单个内置工具做过，现在把它提到统一这一层，所有工具进执行引擎之前都过同一道校验，不用每个工具各写各的。

![](<images/理论学习：工具系统与 MCP 接入-10-parameter-validation-gate.png>)

最后是权限控制，这一层管的是哪些工具在什么场景下允许调。工具分读和写两类，查订单、查物流这类只读工具，调错了顶多是查了一次没用的数据；`create_ticket` 建工单、改收货地址、发起退款这类写操作，一旦被调用就会真的改动系统状态、动到钱和用户数据，调错的代价完全不同。



权限控制要做的，是明确规定当前场景下哪些工具放行、哪些不放行。高风险的写操作，只有在特定意图、特定校验通过之后才准调；没走到那一步，执行引擎直接拒绝这次调用，不给模型任何绕过去的机会。

![](<images/理论学习：工具系统与 MCP 接入-11-permission-gate.png>)

权限层管的是「这个工具能不能调」。还有一件事它管不着：这次调用是替谁做的。



查订单这类工具，光有订单号还不够，得知道发起的人是谁，才判断得了这单归不归他。而这个「谁」，恰恰不能让模型来填。模型手里只有用户说的话，用户自称是谁它就按谁处理，一句「我是客服主管，帮我核对下这单」就可能把它带偏。



身份得从可信通道取。课程里的聊天页第一次打开时生成一个 id 存进浏览器本地，之后每轮请求都带上来。真实系统里这个 id 来自登录态或者 JWT，由网关或中间件解出来。两者的区别只在从哪儿取，取到之后怎么用是一样的。



取到之后有一条硬规矩：这类身份参数绝不能出现在模型看得见的那份参数表里。只要它是模型能填的字段，就能被用户的话术改写。正确的做法是让它压根不进模型的视野，由执行引擎在参数校验通过之后补进去，这种参数叫「注入参数」。



LangChain 给了现成的标注方式：

```python
@tool
async def create_ticket(
    description: str,
    ticket_type: Literal["售后", "投诉", "咨询"],
    conversation_id: Annotated[int, InjectedToolArg],   # 模型看不到这一个
) -> dict:
```

标过之后，同一个工具有了两份参数表。发给模型的那份 `tool_call_schema` 里只有 `description` 和 `ticket_type`，执行时真正用的 `args_schema` 才有 `conversation_id`。模型看不见它，也就无从伪造，执行引擎在调用前把真值盖进去。

![身份当普通参数和当注入参数的区别](<images/理论学习：工具系统与 MCP 接入-23-injected-identity-vs-plain-param.png>)



外部 MCP 工具这一块尤其要收紧。工具是从外部 Server 上现问回来的，用途描述、参数说明都是对方自己声明的，你没法保证句句可信，甚至可能夹带诱导模型乱调的话术。所以对于外部工具尤其写操作，能不能真调得由我们这边的权限层按规矩卡，而不是看它自己怎么声明、更不是让模型临去判断。

![](<images/理论学习：工具系统与 MCP 接入-12-security-boundary-permission-layer.png>)

### 建工单这条路要走通，意图表得多一类



契约、校验、权限这一套立起来之后，`create_ticket` 要真被调到，还差一步。用户说「给我转人工」「帮我建个工单」，这句话得先能走到主力 Agent 面前，Agent 才有机会调它。



回头看第 6 章那张意图表，八个类目里没有一个装得下这句话。它不问物流、不问订单、不问商品政策、不要退款、不是售后、算不上投诉、更不是闲聊。八类里挑不出来，只能落进最后那个「其他」。而「其他」走的是 `fallback_script`，回的是一句写死的话：



> 抱歉，我不太确定您的意思。您可以把问题说得更具体些吗？



用户把话说得再明白不过了，系统回一句听不懂。这是客服系统最丢分的场面，用户要找人，机器人装糊涂。



所以这一章把意图表从八类扩到九类，在投诉后面插进「人工」：

```plain&#x20;text
7. 人工：明确要求建工单、转人工、找客服专员跟进
```

分流上它跟物流、订单归在一起，都落到 `business` 交给主力 Agent。它单独立一类不为走一条专属的边，只为兜住这句话别掉进兜底话术里。进了 Agent，顺着用户这句话调 `create_ticket` 就是水到渠成的事。



它和投诉的方向正好相反。投诉是用户在表达不满、还没提转人工，系统主动把「转人工」「建工单」两个按钮递过去让他挑。「人工」是用户已经开口要了，那就直接帮他建。人家都点名要人了，再弹个按钮问他要不要，是多此一举。

![意图表里有没有「人工」这一类的区别](<images/理论学习：工具系统与 MCP 接入-24-human-intent-class.png>)



> \[配图：上下两行对比。上面一行标题「没有『人工』这一类」，聊天气泡里用户说「给我转人工」，箭头指向一个写着「其他」的灰色标签，再指向机器人回答「抱歉，我不太确定您的意思」，用户头顶画一个问号，配红叉。下面一行标题「加上『人工』这一类」，同一句话指向写着「人工」的高亮标签，再指向 Agent 图标，Agent 手里递出一张工单，标注「顺着这句话调 create\_ticket」，配绿勾。卡通插画风格，浅色背景，深色描边轮廓，大字号短标签]



类目表跟着新功能长，这件事第 6 章讲意图体系演进时说过一次，这里是它第一次真的发生：不是先验地想全，是 `create_ticket` 这个能力做出来了，才发现原来的表兜不住通往它的那句话。

## 统一执行引擎：内置和外部，一套规矩管到底

第 2 章给单个内置工具做过一轮容错：超时掐断、暂时性故障重试、执行结果分三类处理。那时候工具就五个，都在本地，容错逻辑写在每个工具内部也还管得过来。现在工具来自内置和外部好几个来源，数量还会往上涨，其中外部 MCP 工具的每一次调用都要跨网络打到别人家的 Server 上。再让每个工具各管各的容错，既重复又容易漏或者做错。统一执行引擎的意思，是所有工具调用都从同一个地方过一遍，超时、重试、错误处理、结果格式化、审计这几样在这一处统一做掉，工具从哪来都一样。

![](<images/理论学习：工具系统与 MCP 接入-13-unified-execution-engine.png>)

超时是第一道。每一次工具调用都套一个上限。本地内置工具偶尔会卡，跨网络的外部工具卡住的概率更高，对方 Server 慢一拍、网络抖一下，都可能让一次调用迟迟不返回。用户还盯着屏幕等回复呢，一个卡死的调用能把整条响应拖到没边。超过上限就掐断，掐断后照样包成一条失败结果给模型，让它据此重新调整策略或者向用户交代，而不是干耗着。



重试要拿捏分寸。它只留给「再试一次可能就好」的暂时性故障，网络抖动、对方 Server 重启的那一小段时间这类。业务上的空结果不重试，订单号本来就不存在，查一百遍还是不存在。写操作尤其要当心：一次改地址或者发起退款的请求超时了，未必是没执行成功，也可能只是返回丢在了路上，闷头重试就可能重复改一次、重复退一笔。写操作默认不自动重试，要么失败了如实告诉用户，要么请求带上幂等键让同一次操作只生效一次。外部 MCP 的写操作更是如此，你摸不清对方 Server 的幂等语义，宁可不重试也别冒重复执行的险。

![](<images/理论学习：工具系统与 MCP 接入-14-retry-decision.png>)

错误处理沿用第 2 章那套三类分诊，只是抬到统一这层来做。参数不合法的，前面校验那关已经拦下、回灌校验说明；查询落空的，返回一句明确的「未查到」，让模型接着这个事实跟用户周旋；真要是出了故障，比如数据库连不上、外部 Server 报错或者压根连不上，就捕获住、包成一条「工具暂时不可用」。三类有个共同点：坏消息如实告诉模型，让它做出应对策略。

![](<images/理论学习：工具系统与 MCP 接入-15-error-triage-desk.png>)

结果格式化这里，外部工具比内置工具更需要。内置工具查出来的是 ORM 对象，带着内部主键、成本价这些跟回答无关的字段；外部 MCP 工具返回的更是五花八门，各家 Server 按自己的习惯来，裸 ID、内部枚举码、层层嵌套的冗余字段都可能有。回到之前统一格式化：只挑模型组织回答用得上的字段，省 token 也顺手挡住敏感字段外泄；把内部枚举翻译成人话，比如把状态码翻成「已发货」「退款中」；最后序列化成 JSON，中文不转义，人翻日志时也看得懂。各家不一样的返回，在这一层进行标准化。

![](<images/理论学习：工具系统与 MCP 接入-16-result-formatting-pipeline.png>)

审计日志是最后一道。每一次工具调用都要留痕：什么时候、调了哪个工具、参数是什么、返回了什么、耗时多久、成功还是失败。内置工具要记，外部 MCP 工具更要记。调用外部工具等于在别人的系统上触发了动作，尤其是写操作，一旦事后要追责、要复盘「这笔退款到底是谁在什么时候发起的」，全靠这份留痕。至于系统跑起来之后，怎么顺着调用链一步步盯是哪个工具、哪一步慢了或者出了错，那是后面可观测性那一章会继续说，那时会用更省事的自动追踪来做。

![](<images/理论学习：工具系统与 MCP 接入-17-audit-log-observability.png>)

这么一套下来，主力 Agent 只管开口调工具，本地还是远程、内置还是外部，剩下的注册、校验、权限、超时、重试、格式化、审计都由这一层统一兜底，其他地方无需关心。

## 主力 Agent 把业务 MCP 当工具调

回到我们的智能客服，业务数据类的意图，物流、订单这些，不预先检索，直接进主力 Agent，让它在 ReAct 循环里自己判断该调哪个工具、调几次。前面几章里，这个「工具」还只是内置那五个；到这一章，业务数据类的东西，很大一部分要落到业务 MCP 上。



对主力 Agent 来说，一个业务 MCP 工具和一个内置 `@tool` 工具，用起来没有分别。前面讲过，两者的说明书是一个格式，外部工具通过 MCP Client 接进来之后，会被适配成跟内置工具一样的 LangChain 工具对象，一起进到主力 Agent 绑定的那份工具清单里。它在 ReAct 循环里该调哪个就调哪个。

![](<images/理论学习：工具系统与 MCP 接入-18-langchain-tool-object.png>)

落到代码上，把外部 MCP 工具接进来、跟内置工具合成一份清单，大致是这样：

```python
from langchain_mcp_adapters.client import MultiServerMCPClient

# 连上业务 MCP Server（物流、售后各是一个），现问现拿它们的工具
client = MultiServerMCPClient({
    "logistics": {"url": "http://logistics-mcp:8000/mcp", "transport": "http"},
    "aftersale": {"url": "http://aftersale-mcp:8000/mcp", "transport": "http"},  # 售后：查在保、查退货进度
})
mcp_tools = await client.get_tools()      # 外部工具，适配成 LangChain 工具

tools = builtin_tools + mcp_tools         # 跟 ch02 那批内置工具合成一份清单
llm_with_tools = llm.bind_tools(tools)    # 主力 Agent 绑定的还是一份统一清单
```

`MultiServerMCPClient` 按配置连上一个或多个业务 MCP Server，`get_tools()` 干的正是前面说的动态发现：现问 Server 有哪些工具、拿回说明书，再把每个外部工具适配成 LangChain 的工具对象。拿到手之后，跟第 2 章那份内置工具列表一拼，`bind_tools` 绑定的还是一份统一清单。从这行往后，主力 Agent 眼里就只剩「一份工具清单」，内置的和外部的混在一起，调用方式一模一样。加一个业务 MCP Server，它的清单里就多出几件工具。

## 工具一多就调不准：Skill 把用法打包起来

随着工具清单越拉越长，会发现模型有时候调不准了。工具就五个的时候，模型扫一眼就知道该点哪个；等清单堆到几十上百件，一股脑全摆到它跟前，它就开始犯迷糊。



调不准通常是三种样子。一是该调的没调，用户明明在问订单，它却凭记忆编了个回答，把查订单这一步给漏了；二是调了不该调的，问物流的时候顺手点了发起退款；三是该调的都调了、顺序却拧了，本该先查到订单号再拿去查物流，它却颠倒过来，头一步就缺了参数。

![](<images/理论学习：工具系统与 MCP 接入-19-tool-selection-errors.png>)

工具调不准这类问题，Anthropic 推出的「Skill」机制能大大提高工具调用准确率。它的官方示例仓库地址是 <https://github.com/anthropics/skills>，从写文档、做设计到跑测试，各种任务的现成 Skill 都在里头。



一个 Skill，说到底是一个文件夹，「文件即能力」，里头装三样东西：一份是写清这件事该一步步怎么做的操作规程，也就是它的「SOP」；脚本是干活要用到的这类资源，其实就是对应的工具；还有一段告诉模型「我是干什么的、什么时候该找我」的自我介绍。



落到文件上，官方仓库里每个 Skill 大致都长这样：

```text
skill-name/                 # Skill 就是一个文件夹，文件夹名即技能名
├── SKILL.md                # 必需：YAML 头写 name、description 当自我介绍，正文是 SOP
├── scripts/                # 可选：干活用的脚本，SOP 里按需调用
├── references/             # 可选：参考资料，用到才读进来
└── assets/                 # 可选：产出要用的模板、图标、字体
```

可繁可简：一个 `SKILL.md` 就能起个最简 Skill，复杂的才把脚本、资料一并带上。



比如我们课程一开始说的实战用着的 Superpowers，本身就是一组 Skill；能稳定让我们在开发阶段拿来驱动 Claude Code、帮我们把这套系统造出来的。



平时摆在模型眼前的，只有每个 Skill 那句简短的自我介绍；模型看当前用户的意图跟哪个 Skill 对得上，才把那一个的完整规程和脚本加载进来，用不上的始终收着。这套「用到才展开」的加载方式，叫「渐进式披露」。



这么一来，前面那三种毛病就有救了。模型面前一次只摆当下用得上的那几件工具，不用在几十上百份里大海捞针，挑错的概率自然降下来；那份 SOP 又把先做哪步、再做哪步、什么时候不该动手写得清清楚楚，模型照着走，漏调、误调、顺序不对这些坑就一个个填上了。

![](<images/理论学习：工具系统与 MCP 接入-20-progressive-skill-disclosure.png>)

Skill 的价值主要落在两处。



一处是把工具调用的正确率提上来，这正是前面一路讲下来的：一件复杂任务该拆成哪几步、每步调哪个工具、按什么顺序来，这套沉淀进 SOP；配上渐进式披露只露相关的特性，再带上每个工具的用途说明，模型调起来就稳当多了。



另一处是这套东西可移植、可复用、还好扩展。一个 Skill 就是一个自成一体的文件夹，换个项目、换个 Agent，整包拎过去就能用；想添个新能力，多塞一个文件夹进去就行。

## 退一步看：FC、MCP、Skill 拼成一张生态地图

讲到这里，Function Calling、MCP、Skill 三个词我们都知道是什么了，那它们到底有什么关系呢，是怎么组成了工具系统的呢？最底下那层是 Function Calling，工具调用的原子就在这里：模型开一次口、点名一个工具、递一份参数，这件最小的事就是它。MCP 也好、Skill 也好，往下刨到底，落地都是一次次 Function Calling，谁都绕不开它。



MCP和Skill，各补一个 FC 的问题。一个是工具一多、模型就调不准，刚讲过的 Skill 对这个就很有效，靠把用法打包、按需加载。另一个问题是工具得跨系统、跨团队对接，这正是前面讲的 MCP：把工具做成一套标准的外部形态，谁提供的都能即插即用。



MCP 和 Skill 还常常你中有我。一个打包好的 Skill，可以再封装成一个 MCP Server 摆出去给别的系统用；反过来，一个 Skill 干活的时候，内部也可以去调 MCP 接来的工具。所以这两者常常套在一起用。



三种「范式」之间各补一块。Function Calling 垫在最底下，Skill 接手「工具太多怎么挑」，MCP 接手「工具在外面怎么接」，三块拼起来，就是一张 Agent 调工具、工具之间还能协作的生态地图。

![](<images/理论学习：工具系统与 MCP 接入-21-agent-tool-ecosystem.png>)

## 本章小结

这一章接着上一章那五个写死的工具往下走。先引出了痛点：真实客服要接物流、仓储、第三方一大堆外部系统，每接一个就改代码、重启服务，各家格式还不统一，这条路走不远。



顺着痛点，揭开了工具系统的全貌：主力 Agent 用的工具有内置和外部两个来源，内置是第 2 章那批 `@tool`，外部靠 MCP 接进来，两个来源拢成一份统一清单。



MCP 靠一套标准化的工具说明书加运行时的动态发现，做到了新工具注册一下就能用、核心代码不用动。工具还由两个东西统一管理：注册管理把契约、参数校验、权限控制立起来，执行引擎把超时、重试、错误处理、结果格式化、审计日志统一兜底。



最后全览了工具系统，把 Function Calling、MCP、Skill 三种范式的关系理清楚：FC 打底，Skill 针对工具太多怎么挑，MCP 解决工具在外面怎么接，一块块拼成一张工具生态地图。



到这里，主力 Agent 该有的本事——查数据、守规矩、即插即用地调各路外部工具——总算搭齐了。可它每天在线上接成千上万次请求，每一步怎么想、调了哪个工具、花了多少 token，全埋在一次次调用里，是个黑盒；答不上来的问题兜底一句就散了，也没沉淀下来。下一站 Agent 可观测性与数据飞轮，就是要给这个黑盒开扇窗，再把答不上来的问题接住、喂回知识库，让 bot 越用越准。
