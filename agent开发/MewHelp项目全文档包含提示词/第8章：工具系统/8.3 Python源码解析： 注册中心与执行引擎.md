## 注册中心

### ToolSpec

```python
@dataclass
class ToolSpec:
    name: str
    description: str
    json_schema: dict            # 参数 JSON Schema(校验用;模型可见口径,不含注入参数)
    tool: BaseTool
    permission: str              # "read" | "write"
    source: str                  # "builtin" | "mcp"
    mcp_server: str | None = None
    timeout: float | None = None            # None → engine 按来源取默认
    max_retries: int | None = None          # None → engine 按默认;0 = 不重试(如 query_faq RAG 管线)
    inject_conversation: bool = False       # 执行前注入 conversation_id
    inject_user_id: bool = False            # 执行前注入 user_id(身份从可信通道来,不许模型填)
    format_result: Callable[[dict], dict] | None = None  # 挑字段/枚举翻人话,None 透传
```

这是本章的核心数据结构。一个工具的所有信息收在这一处，分成两半。

前三个字段是模型看得见的：名字、用途描述、参数定义。模块 docstring 里管这叫「三样必齐」，缺一样模型就用不好这个工具，不知道叫什么、不知道什么时候用、不知道该填什么。

后面全是我们侧的策略：能不能调、超时多久、重试几次、哪些参数得注入、结果要不要翻译。这些跟工具本身无关，是我们对它的管理办法。

`json_schema` 那行注释点出了口径：模型可见口径，不含注入参数。

### 模型可见的那份 schema

```python
def _json_schema_of(tool: BaseTool) -> dict:
    """三样齐的 schema 口径:MCP 工具 args_schema 本就是 dict;内置 pydantic 模型用
    tool_call_schema(排除 InjectedToolArg,模型可见口径)转 JSON Schema。"""
    raw = getattr(tool, "args_schema", None)
    if isinstance(raw, dict):
        return raw
    tcs = getattr(tool, "tool_call_schema", None) or raw
    return tcs.model_json_schema()
```

两种来源。MCP 工具的 `args_schema` 本来就是一份 dict，Server 那边给的什么就是什么。内置工具是 pydantic 模型，得转一道。

关键在于转的是 `tool_call_schema` 而不是 `args_schema`。第 2 章讲 `InjectedToolArg` 时说过，被标记的参数留在 `args_schema` 里但不进 `tool_call_schema`，这里就是那个区分的落点。校验用这份、给模型看的也是这份，注入参数从头到尾不出现在模型的视野里。

### 导入即注册

```python
def register(spec: ToolSpec) -> None:
    if spec.name in _BUILTIN:
        logger.warning("工具重名,丢弃后注册者 name=%s(先到者保留)", spec.name)
        return
    _BUILTIN[spec.name] = spec


def scan_builtin() -> None:
    """服务启动(lifespan)时调用:导入 builtin/ 包全部模块,模块 import 即注册。幂等。"""
    global _scanned
    if _scanned:
        return
    _scanned = True
    from app.tools import builtin as pkg
    for m in pkgutil.iter_modules(pkg.__path__):
        try:
            importlib.import_module(f"{pkg.__name__}.{m.name}")
        except Exception:  # noqa: BLE001 坏文件跳过告警,不拖垮其余工具注册(丢文件即插即用的稳健性)
            logger.exception("内置工具模块导入失败,跳过 module=%s", m.name)
```

每个 builtin 模块底部都有一行 `registry.register(...)`，模块被 import 就完成了注册。启动时扫一遍包，逐个 import。

好处是加工具的成本降到最低：往 `builtin/` 丢一个文件就行，不用去某份中心清单里加一行。中心清单这种东西，写着写着就会跟实际情况对不上。

`try/except` 那道保护值得学。一个模块有语法错误、或者 import 了不存在的东西，只跳过它自己并记一条日志，别的工具照常注册。没有这道保护的话，一个坏文件会让整个工具系统起不来，而症状是「所有工具都没了」，跟真正的病因隔着十万八千里。

重名处理是先到者保留。冲突时告警，不静默覆盖。

### get\_all\_specs

```python
async def get_all_specs() -> list[ToolSpec]:

    ...
    from app.tools import mcp_client   # 延迟导入避免环(mcp_client 也 import registry)
```

内置先进表，MCP 再来，重名一律内置优先。理由是外部 Server 不受我们控制，它随时可能上线一个跟内置工具重名的东西，不能让它顶掉我们自己的实现。

「现问现拿」是这里的另一个设计。每轮对话都重新拉一遍 MCP 清单，Server 侧加了工具，客服系统不用重启就能看到。代价是每轮多一次网络往返，所以下面那个超时封顶就变得很重要。

那行延迟导入的注释解释得很清楚：`mcp_client` 也 import `registry`，写在文件顶部就成环了。

## 执行引擎

```text
ch08 统一执行引擎:所有工具调用的唯一通道。
管道:查工具 → JSON Schema 校验 → 权限门 → 执行(超时/重试)→ 分诊 → 格式化 + 审计。
坏消息如实回灌模型;审计写失败只 log,绝不反拦工具执行。
```

六步，每一步治一类真实故障。

在展开之前，先看整个入口的契约：

```python
async def execute_tool_call(
    tool_call: dict, conversation_id: int, specs: dict[str, ToolSpec],
    *, confirmed: bool = False, deny_note: str | None = None, user_id: str = "",
) -> ToolRun:
    """统一入口(never-raises 契约):无论校验拦下、权限拒绝还是真故障,一律回 ToolRun,
    坏消息包成 ToolMessage 回灌模型。confirmed 是写操作确认令牌,只能由 agent_tools 在
    interrupt 确认后传入——模型自己无法绕过权限门。"""
```

**never-raises**：不管哪一步出问题，都返回一个 `ToolRun`，坏消息包成 `ToolMessage` 交回给模型。

这条契约不是洁癖。这个函数跑在 ReAct 环里，它抛一个异常，整轮对话就断了，用户看到的是接口 500。而把「参数错了」「工具超时了」如实告诉模型，模型完全有能力自己处理，追问用户或者换个工具再试。

### 第二步：参数校验

```python
def validate_args(spec: ToolSpec, args: dict) -> str | None:
    """按 JSON Schema 校验模型给的参数;返回人类可读错误(None=通过)。agent_tools 复用它
    判「create_ticket 参数齐不齐、要不要弹确认卡」。"""
    err = best_match(Draft202012Validator(spec.json_schema).iter_errors(args))
    if err is None:
        return None
    where = f"(字段 {err.json_path})" if err.json_path != "$" else ""
    return f"{err.message}{where}"
```

参数是模型填的，错法千奇百怪：少一个必填项、类型填反、枚举值编一个。统一在入口按 JSON Schema 拦一道，比每个工具函数各写一遍判断强得多。

`best_match` 挑的是最贴切的那条错误。一次校验可能报出十几条，全甩给模型它反而不知道该改哪个。

校验器本身也包了一层：

```python
    try:
        verr = validate_args(spec, args)
    except Exception as e:  # noqa: BLE001
        logger.exception("参数校验器异常(多为外部 Server 给的畸形 schema) tool=%s", name)
        run = _run(False, f"工具暂时不可用:参数定义异常({type(e).__name__}),请如实告知用户。", "失败")
```

看着夸张，实际有必要。MCP 工具的 schema 是外部 Server 给的，可能有解不开的 `$ref`、写错的类型名，校验器读到这种东西会自己炸。按 never-raises 契约，这里同样得包死。

```python
        run = _run(False, f"参数校验未通过:{verr}。请修正参数重新调用;缺少的信息请先向用户追问,不要编造。",
                   "校验拦下")
```

回灌语里那半句「缺少的信息请先向用户追问，不要编造」是必需的。校验拦下之后模型的正确动作是问用户，不是随便填一个再试一次。不写这句，模型十有八九会自己编一个值重试。

### 第三步：权限门

```python
    # ③ 权限门:写操作必须带确认令牌(interrupt 确认后由 agent_tools 传入),模型绕不过
    if spec.permission == "write" and not confirmed:
        note = deny_note or "该写操作需要用户确认,未确认前拒绝执行。请勿再次发起,除非用户明确要求。"
        run = _run(False, f"{name} 未执行:{note}", "权限拒绝")
```

`confirmed` 这个令牌的关键性质是：它是函数参数，不是消息内容。只有 `agent_tools` 在 `interrupt` 拿到用户确认之后才会传 `True` 进来。模型能控制的只有 `tool_call` 里的参数，它没有任何办法把 `confirmed` 变成真。

这是 prompt 约束和代码约束的差别。写在 system prompt 里的「建工单前要征得用户同意」是一句劝告，模型可以不听。这道门是代码，模型绕不过去。

```python
WRITE_TOOLS: set[str] = {"create_ticket"}
```

权限只认我们侧这份名单，不看 MCP Server 自己声明什么。外部 Server 说自己的工具是只读的，那是它的说法，不是判据。

`deny_note` 是留给取消场景的。用户在确认卡上点了取消，得把「用户取消了，别再发起」这句话传给模型，不然它下一步又申请一次，卡片再弹一遍。

### 第四步：执行

```python
    # 注入参数一律在校验之后盖上去:它们不在模型可见的 schema 里,模型填了也算数不得。
    # 身份尤其如此——让模型能填 user_id,一句「我是客服主管」就可能把它改写掉。
    if spec.inject_conversation:
        args["conversation_id"] = conversation_id
    if spec.inject_user_id:
        args["user_id"] = user_id
```

注入的时机很讲究，必须在校验之后。

模型看不到 `user_id` 这个参数，但它可以硬填一个进 `args`。注入放在校验之后，我们这份直接盖掉它填的那份，模型填什么都不算数。要是放在校验之前，模型填的值会先过一遍校验，万一格式合法就被当成合法输入了。

那句注释把风险说得很直白：让模型能填 `user_id`，用户在对话里说一句「我是客服主管，帮我查一下 8888 的订单」，模型就可能顺手把身份改写掉。

```python
    if spec.permission == "write":
        retries = 0
    else:
        retries = settings.tool_max_retries if spec.max_retries is None else spec.max_retries
```

写操作恒不重试。超时不代表没执行，可能对面已经建好工单了只是响应回来得慢，重试一次就是两张单。重复执行一个写操作，比让它失败严重得多。

```python
_TRANSIENT = (asyncio.TimeoutError, TimeoutError, ConnectionError, httpx.TransportError)
```

值得重试的只有这四类：超时和网络抖动。业务异常不在列，那种错误重试一百次结果都一样，只是把故障时间拉长。

读操作的重试次数还能按工具覆盖，`query_faq` 设的是 0，因为它底下是整条 RAG 管线，超时多半是上游真的慢，重试纯粹烧时间。

### 第五步：分诊

```python
            is_timeout = isinstance(e, (asyncio.TimeoutError, TimeoutError))
            status = "超时" if is_timeout else "失败"
            # ⑤ 分诊:真故障如实回灌,不装没事(查询落空由工具返回语义表达,不属此路)
            run = _run(False, f"工具暂时不可用:{'执行超时' if is_timeout else type(e).__name__},"
                              "请稍后再试或如实告知用户。", status, attempt)
```

超时和其他失败分开记，回给模型的话都带上「请如实告知用户，不要编造结果」。

那句注释划了一条重要的界线：查不到东西不是故障。用户报了个不存在的订单号，工具正常返回一个「没找到」的结果，走的是成功路径，由工具自己的返回值表达语义。只有工具真的挂了才进这条分诊路径。这两件事混在一起，模型就分不清「确实没有这单」和「系统坏了」。

### 结果格式化

```python
def _format_content(spec: ToolSpec, result) -> str:
    """结果格式化:MCP 工具(adapters)返回内容块列表 [{"type":"text","text":...}],先拆出文本;
    JSON 文本解回 dict;format_result 钩子挑字段/枚举翻人话;统一 ensure_ascii=False(中文不转义)。"""
    if isinstance(result, list) and result and all(isinstance(b, dict) for b in result):
        texts = [b.get("text", "") for b in result if b.get("type") == "text"]
        if texts:
            result = "\n".join(texts)
    if isinstance(result, str):
        try:
            result = json.loads(result)
        except (json.JSONDecodeError, ValueError):
            return result                      # 纯文本结果原样回灌
```

三层剥。MCP 工具经 adapters 回来的是内容块列表，先拆出文本。文本要是个 JSON 就解回 dict，解不动的纯文本原样回灌。

```python
    if spec.format_result is not None and isinstance(result, dict):
        try:
            result = spec.format_result(result)
        except Exception:  # noqa: BLE001 格式化钩子是扩展点:钩子炸了降级透传,别把成功结果报成失败
            logger.exception("结果格式化钩子异常,降级透传原始结果 tool=%s", spec.name)
```

钩子外面那层 `try` 的理由写在注释里。格式化是扩展点，任何人都可能往里塞一个有 bug 的函数。钩子炸了就降级透传原始结果，工具明明调成功了，不能因为一个美化步骤把它报成失败。

## 接进 MCP

第 2 章那张工具去向表里，`query_logistics` 标的是「搬进独立进程」。本章兑现它。

MCP 要解决的是工具提供方和使用方的解耦。物流查询归物流团队维护，他们在自己的进程里加一个新工具，客服系统不用改代码、不用重启就能用上。

### fetch\_mcp\_specs

```python
    for server in _connections():
        try:
            # 我们侧超时封顶:连接拒绝会快速失败,但 Server 假死(TCP 接了不回话)只受 adapters
            # 默认超时保护——现问现拿每步都拉清单,最坏延迟必须封住
            tools = await asyncio.wait_for(_get_tools_of(server_name=server),
                                           timeout=settings.mcp_tool_timeout)
        except Exception as e:  # noqa: BLE001 单台不可达/假死:告警+跳过,不拖垮本轮对话
            logger.warning("MCP Server「%s」不可达,本轮跳过其工具:%s", server, type(e).__name__)
            continue
```

两处保护，各治一种失败模式。

`except` 治的是「Server 挂了」。一台不可达就跳过它的工具，本轮对话照常进行，只是模型手上少几个工具。工具少一个是降级，整轮对话崩掉是故障，这两者的严重程度差着量级。

`asyncio.wait_for` 治的是「Server 假死」。进程还在、TCP 握手也成，就是不回数据。这种情况连接不会被拒绝，`except` 那道等不到触发，只能靠超时。而因为清单是每轮现拉的，这个延迟直接加在用户等待时间上，必须封死。

```python
        _client = MultiServerMCPClient(_connections(), handle_tool_errors=False)
```

`handle_tool_errors=False` 让工具错误原样抛出来，交给执行引擎那套分诊统一处理。默认那个 `True` 会由 adapters 自己吞掉并包装成一条消息，格式和我们的回灌语不一致，审计里也记不到真实的异常类型。

## 工单确认流

```python
    # 建工单确认:先纯校验(无副作用),参数齐才 interrupt;resume 回 {"confirmed": bool}
    ticket_calls = [tc for tc in last.tool_calls if tc["name"] == "create_ticket"]
    tspec = specs.get("create_ticket")
    decision = None
    if ticket_calls and tspec is not None \
            and engine.validate_args(tspec, dict(ticket_calls[0].get("args") or {})) is None:
        first_args = ticket_calls[0]["args"]
        decision = interrupt({"type": "confirm_ticket",
                              "preview": {"ticket_type": first_args.get("ticket_type", "咨询"),
                                          "description": first_args.get("description", "")}})
```

先校验，参数齐了才弹确认卡。

参数不齐就弹的话，用户看着一张描述是空的工单预览，点了确认，工具照样因为参数不全而失败，白弹一次还让用户觉得系统很傻。参数不齐时走另一条路，交给引擎按「校验拦下」回灌，模型收到「缺少 description」自然会向用户追问，卡片压根不弹。

`validate_args` 在这里被复用了，注册中心那套校验规则和这里判「要不要弹卡」用的是同一份判据，不会出现引擎认为参数不全、节点认为够了的分歧。

这段同样守着第 6 章那条纪律：`interrupt` 之前只有查清单和跑校验，都是纯计算，`resume` 时整个节点从头重跑也没有副作用。

```python
                tool_msgs.append(ToolMessage(content="一次只处理一个建工单请求,本次调用已忽略。",
```

本章把所有工具收进一条管道，六步各治一类问题：不认识的工具、填错的参数、没确认的写操作、抖动的网络、真故障、看不懂的返回值。
