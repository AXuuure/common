## 看得见：接 Langfuse

### attach\_observability

```python
def langfuse_enabled() -> bool:
    return bool(settings.langfuse_public_key and settings.langfuse_secret_key
                and settings.langfuse_base_url)
```

```python
def attach_observability(graph):
    """编译后挂一次 Langfuse 回调,全图自动 trace(README:「编译时挂一次,节点里一行不用动」)。
    未配置时原样返回——不挂、不 import langfuse。"""
    if not langfuse_enabled():
        return graph
    _init_client()
    return graph.with_config({"callbacks": [_make_handler()]})
```

接法是编译时挂一次回调，全图自动 trace。节点代码一行不用改，每个节点的输入输出、每次模型调用的耗时和 token，Langfuse 那边都能看到。

未配置时原样返回，连 `import langfuse` 都不执行。这一点在课程里很重要：学员不想搭一套 Langfuse，全课照样跑得通，只是少一块观测面板。观测是增强，不是依赖。

配置走 `settings` 显式传参，不读 `os.environ`。整个项目的配置口径是 `.env` 加 pydantic-settings，Langfuse SDK 默认认环境变量那套在这里不适用。

### run\_inline 那个坑

```python
    class _InlineCallbackHandler(CallbackHandler):
        """run_inline=True:让 LangChain 在调用方协程内联执行回调,而不是丢进独立 task。
        没有它,handler 的 OTel context.attach 挂在别的 task 上,节点代码里没有活动
        span 上下文,tag_intent 的 propagate_attributes 写不进当前 trace(实测踩坑)。"""
        run_inline = True
```

一行子类，治的是一个不容易发现的问题。

LangChain 默认把回调丢进独立 task 去跑，handler 里那个 OTel `context.attach` 就挂在那个 task 的上下文上。回到节点代码里时，当前协程没有活动的 span 上下文，后面 `tag_intent` 想往 trace 上补属性就写不进去。

难受的地方在于表面看一切正常：Langfuse 上 trace 有了、节点有了、耗时有了，只有「按意图打标」这一件事静默失效。不是去用那个功能，根本发现不了。

这类框架集成的坑值得记一笔：功能通了不等于全通了，附加能力得单独验一遍。

### tag\_intent

```python
    try:
        from langfuse import get_client, propagate_attributes
        # 不能只 with...pass 写"当前活动 span"——LangGraph 异步调度下它可能已 ended,
        # OTel 对 ended span 的写入静默丢弃(实测踩坑)。改为在传播上下文内新建一个
        # event 观测:新 span 必然存活,trace 级属性(metadata/tags)随它上提到整条 trace。
        with propagate_attributes(
            metadata={"intent": intent, "intent_confidence": f"{confidence:.2f}"},
            tags=[f"intent:{intent}"],
        ):
            get_client().create_event(name="intent-tagged")
    except Exception:
        logger.warning("langfuse tag_intent 失败(已忽略)", exc_info=True)
```

意图要写进 trace 的 metadata 和 tag，后面按意图分堆算成本才有依据。

又是一个静默失效的陷阱。直觉写法是打开传播上下文然后什么都不做，让属性落到当前活动 span 上。但 LangGraph 异步调度下那个 span 可能已经结束了，而 OTel 对已结束 span 的写入是**静默丢弃**的，不报错、不告警，就是没写进去。

解法是在传播上下文里现建一个 event。新建的 span 必然是活的，trace 级的 metadata 和 tags 随它上提到整条 trace 上。

整个函数包在 `try` 里，失败只记一条 warning。这是本章那条纪律的第一次出现：观测失败不许影响业务流。

## 看得见：用量收口

### 一个把成本账放大一个量级的 bug

```python
class _CumulativeUsageChatOpenAI(ChatOpenAI):
    """修正流式用量被重复累加的问题。

    有些 OpenAI 兼容通道在**每个** chunk 上都重报一遍**累计**用量,而 langchain-openai
    把各 chunk 的用量**相加**。两件事凑到一起,一次调用的 token 数会被放大到 chunk 条数倍
    ——实测 24 个 chunk、input 恒为 11,聚合出来是 264。ch09 的成本账按这个数统计,
    整体虚高一个量级;ch05 早先那道 token 预算闸也因此第一步就跳闸,工具从没执行过。
    开关救不了:`stream_usage=False` 时上游照发、库照加。
    ...
    """
```

这个 bug 值得整节讲，因为它示范了「两个各自合理的设计凑在一起就出事」。

上游通道在每个 chunk 上重报一遍累计用量，这个做法本身说得通，客户端随时断开也能拿到当前用量。langchain-openai 把各 chunk 的用量相加，这个做法也说得通，规范通道只在最后一个 chunk 报一次，相加正好等于总量。

两件事凑一起，24 个 chunk 就把 11 个 input token 累成 264。

后果有两处。本章的成本统计整体虚高一个量级，拿它做任何决策都是错的。更隐蔽的是第 5 章：那时候 ReAct 的停止条件里还有一道 token 预算闸，被这个虚高的数字第一步就顶穿，`should_continue` 直接返回停止，工具从来没被执行过。表面症状是「模型不爱调工具」，谁会想到是用量统计的问题。

`stream_usage=False` 关不掉，那个开关只管我们要不要主动请求用量，上游照发、库照加。

### \_diff\_usage

```python
    def _convert_chunk_to_generation_chunk(self, chunk, default_chunk_class, base_generation_info):
        usage = chunk.get("usage") if isinstance(chunk, dict) else None
        if usage:
            prev = self._prev_usage
            # 任何一项变小 = 上一条流已经结束,这是新一条流的第一个 chunk,基准清零。
            # 同一实例被复用时(结构化输出的链会多次 invoke)靠这条自愈。
            if any(isinstance(v, (int, float)) and v < prev.get(k, 0)
                   for k, v in usage.items() if not isinstance(v, dict)):
                prev = {}
            chunk = {**chunk, "usage": _diff_usage(usage, prev)}
            self._prev_usage = usage
```

修在 chunk 转换的入口：把累计值换成相对上一个 chunk 的增量，再交给上游那套逻辑去加。加完正好等于最后一个 chunk 的累计值，也就是真实用量。

对规范通道无害。只在末尾报一次的话，增量就等于它本身，减去的是零。

那个「任何一项变小就清零基准」的自愈值得看。同一个模型实例会被复用，结构化输出的链会在它上面多次 invoke，第二条流的第一个 chunk 用量会突然变小。认出这个信号就把基准清零，不然第二条流的用量会被算成负数然后被 `max(0, ...)` 抹成 0。

```python
def _diff_usage(cur: dict, prev: dict) -> dict:
    """把累计用量换成相对上一个 chunk 的增量,嵌套的 *_details 一起换。"""
    out: dict = {}
    for k, v in cur.items():
        p = prev.get(k)
        if isinstance(v, dict):
            out[k] = _diff_usage(v, p if isinstance(p, dict) else {})
        elif isinstance(v, (int, float)):
            out[k] = max(0, v - (p if isinstance(p, (int, float)) else 0))
        else:
            out[k] = v
    return out
```

递归处理是因为用量结构里有嵌套的 `*_details`，缓存命中数、推理 token 数这些都在里面，只改外层那几个数会让明细对不上总数。

### 四个信号

```text
信号(全部来自检索/精排结果,零额外模型调用):
  top1_score     精排 Top1 的 rerank_score(证据里最强的一条有多强)
  valid_count    有效证据数:rerank_score >= VALID_SCORE_FLOOR 的条数(强证据是孤证还是成群)
  margin         Top1 - Top2 分差(证据聚焦度:断崖式领先 vs 一堆似是而非;单条时取 top1 自身)
  key_clause_hit Top3 文本是否命中关键条款词表(复用 ch03 入库同款 KEY_TERMS 启发式——
                 hit 里没有 is_key_clause 字段,按同词表现算,口径与入库标记一致)
```

第 4 章那道机械闸只看 Top1 分数，这一章升级成四个信号加权。

`compute_evidence_confidence` 算的这四个信号各捕捉一件事。`top1_score` 说的是最强的那条证据有多强。`valid_count` 说的是强证据孤零零一条还是有一群。`margin` 说的是证据聚不聚焦，第一名断崖式领先跟一堆分数差不多的似是而非，完全是两种局面。`key_clause_hit` 说的是有没有命中退款、时效这类关键条款词。

「零额外模型调用」这五个字是这套设计的前提。四个信号全部来自已经算出来的检索和精排结果，这道闸不额外花一分钱、不加一毫秒延迟。要是它需要再调一次模型，就该重新掂量值不值。

### 阈值怎么定

```text
ch09 置信度阈值校准:拿 ch04 评估集,A/B/C 桶(应可答)与 D 桶(应拒答)分别算
evidence_confidence 分布,扫阈值取 Youden J(=可答通过率 - 应拒放行率)最大的分离点。
输出分布表 + 推荐阈值 → 人工回填 settings.evidence_confidence_threshold(不拍脑袋)。
```

阈值不拍脑袋定。拿第 4 章那份评估集，应该能答的题和应该拒答的题分别算一遍置信度，得到两条分布，然后扫阈值找最佳分离点。

判据是 Youden J，等于可答通过率减去应拒放行率。它同时惩罚两类错误：阈值定高了会误拦真能答的问题，定低了会误放本该拒答的。只看其中一个都会跑偏。

最后一步是人工回填 `settings`。脚本给推荐值，不自动改配置。这个数字影响的是线上的拒答率，值得有人看一眼再决定。

## 转起来：答不了的问题去哪

低置信池有三个入口，`source` 字段区分。前两个来自 `retrieve_knowledge` 的两道闸，第三个来自用户点踩。

```python
    # 快照语义三态:走了检索且有召回=列表;走了检索但零命中=[](审核页显示「已检索,零命中」,

```

召回快照有三种状态，别混。查了并且有召回，存的是那几条的原文和分数。查了但一条都没召回，存空列表。压根没走检索，存 `NULL`。

空列表和 `NULL` 的差别很关键。空列表意味着「检索器认真找过，库里确实没有」，这是真缺知识的强信号，审核页上应该优先处理。`NULL` 只说明这次没走那条路，什么都推不出来。用同一个值表示这两种情况，审核的人就没法排优先级了。

## 转起来：飞轮流水线

```text
批处理语义(用户拍板:定时批处理,不做近实时):
- 游标 = low_confidence_questions.matched_review_id IS NULL,处理完回写,天然幂等可重跑;
- 串行逐条:同批同义问题第二条能命中第一条刚建的行,不重复建缺口;
- 命中任何状态的候选都只累加 occurrence_count(驳回即终审,不复活);
- 解析失败/幻觉 id:该条跳过并告警,游标留在原地下轮重试。
```

四条语义把整个流水线的行为定死了，值得逐条看。

游标是「有没有回写归并落点」，不是时间戳也不是自增位置。处理完一条就回写，中途挂掉重跑时，已处理的自然被过滤掉，天然幂等。

串行逐条是刻意的，不并发。同一批里五条「运费怎么算」的口语变体，第一条建了缺口，后面四条要能命中它。并发跑的话四条同时看不到彼此，会建出五个重复缺口。

驳回即终审这条是业务判断。一个问题被人工驳回过，说明它不该进知识库，之后再出现同类只累加计数，不重新变回待审状态。不然被驳回的问题会反复冒出来烦人。

缺口落在本章新建的 `review_queue` 上：

```sql
  id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '缺口主键,也是查重命中要返回的 matched_question_id',
  normalized_question VARCHAR(512)    NOT NULL                COMMENT '标准化后的 FAQ 式问题',
  ai_suggested_answer TEXT            NULL                    COMMENT '模型生成的示例答案,备查',
  occurrence_count    INT UNSIGNED    NOT NULL DEFAULT 1      COMMENT '出现次数,查重命中累加,越高越该优先补',
  review_status       ENUM('待审','通过','驳回') NOT NULL DEFAULT '待审' COMMENT '人工审核状态',
```

一行就是一个去重后的知识缺口。`occurrence_count` 那句注释点明了这张表的用法：越高越该优先补。低置信池里堆的是一条条原话，归并成缺口之后按出现次数一排，该先补哪一块一目了然。

`id` 的注释也值得留意，它就是下面查重时模型要返回的那个 `matched_question_id`，两处是同一个东西。

同一份 DDL 还给第 4 章那张低置信池加了两列，`matched_review_id` 记这条原话归并到了哪个缺口，`retrieved_chunks` 存落池时的召回快照。前者是飞轮的游标，后者是审核页给人看的材料。

```python
                    " [候选已截断200,查重覆盖不全]" if truncated else "")
```

截断时在日志里明说「查重覆盖不全」。这类降级必须说出来，不然报告上写着「本轮新建 12 个缺口」，看的人以为查重是完整的，实际上有一批同义问题因为没进候选而被重复建了。

### 审核写回

```python
    chunk_ids: list[int] = []
    try:
        chunk_ids = await _write_chunks([chunk])
        await _vectorize()
    except Exception:
        logger.exception("审核写回知识库失败 review=%s(状态保持待审,可重试)", review_id)
        if chunk_ids:
            # 回滚本次插入的 pending 行:vectorize_pending 处理全部 pending,
            # 残留会让重试造出重复知识条目(spec 8.2「整体回滚」)
            try:
                await repository.delete_knowledge_chunks(chunk_ids)
            except Exception:
                logger.exception("回滚 pending chunk 失败 ids=%s(需人工清理)", chunk_ids)
```

审核通过就地建一个 `Chunk` 写进 `knowledge_chunks`，向量化，下一个问同类问题的用户立刻就能检索到。飞轮到这里闭合。

这段写了两步：先写库，再向量化。中间失败的处理是本章最需要细看的地方。

写库成了、向量化挂了，那条 pending 行就留在库里。第 3 章讲过 `vectorize_pending` 处理的是全部 pending，所以下次不管谁触发向量化，这条残留都会被处理掉。而这次审核因为报了错，状态还是待审，人会再点一次通过，于是又插入一条一模一样的知识。

解法是整体回滚，把本次插入的行删掉。回滚本身也可能失败，那就记一条写着「需人工清理」的日志，至少留下线索。

```python
    if not await repository.update_review_status(review_id, "通过", approved_answer=req.approved_answer):
        # 并发窗口:KB 已写入但状态被他人先变更——如实报出,不装成功
        logger.warning("审核状态更新落空(并发变更?)review=%s,KB 已写入 %s", review_id, chunk_ids)
        raise HTTPException(status_code=409, detail="状态已被他人变更;知识已写入,请人工核对")
```

最后还有个并发窗口。知识库已经写进去了，但这条待审记录的状态被另一个人先改了。这时候不能装作成功，得如实报 409，并且在错误信息里说清「知识已写入」，让人知道要去核对而不是简单重试。

## 账算给谁看

前面 `tag_intent` 费劲往 trace 上打的那个标，用处在这里兑现：

```text
ch09 Cost Control:按意图统计 token 花销(README:「按意图把 token 分堆一算,
哪类意图最烧钱立马现形」)。数据源 = Langfuse Metrics API(意图在 classify_intent 打成 intent:xxx tag)。

产物:data/ch09/reports/cost_by_intent.{txt,json};「观测与成本」页只读这份 json,不另算一份。
```

统计不自己埋点，直接查 Langfuse 的 Metrics API，按 `intent:xxx` 这个 tag 分组。所以那个静默失效的坑要是没修，这份报告出来会是一片空白，而且看不出哪里错了。

两处口径写得很实在。一是产物落成 JSON，前端那个「观测与成本」页只读这份，不另算一份，避免页面和报告两个数对不上。二是关于钱：

```text
说明:自定义模型名(glm-5.2 等)在 Langfuse 无内置单价,统计以 token 数为准;
要看钱在 Langfuse 界面配模型单价即可,不在本脚本范围。
```

自建模型在 Langfuse 里没有内置单价，脚本就只统计 token 数，不硬算一个金额出来。想看钱去界面上配单价。这个边界划得对，一个统计脚本自己编一套价格表，用的人迟早会拿着它去跟财务对账。
