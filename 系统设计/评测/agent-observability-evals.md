> **一句话结论**
>
> 这期要讲清两件事：Agent Observability（观察能力）和 Evals 分别是什么，以及为什么在建造 AI Agent 系统时必须记得它们（0:05–0:17）。作者不只用系统设计图讲，还拿两个工具跑了一遍真实任务——Trek 是 Agent 工具的开放路由器，Waku Memory 是跟着你所用 Agent Harness 走的记忆——从提问、查记忆、调工具、出报告，一路看到每一步花了多少钱（0:30–1:19）。

> **我的理解**
>
> 作者的判断是这两个概念「并不是很复杂」，但属于必须记住的那部分（0:11–0:14），所以他用比喻（相机 / 裁判）加一次完整演示来降低理解成本。对象说得很明确：「如果您在建造 AI Agent，您的生意或产品中」（0:05–0:08）。如果你不自己搭 Agent、也不需要为模型调用和工具调用付账，视频里没有给出别的适用场景。

## 核心概念与原理

### 要解决的痛点：不透明（2:19）

做 Agent 最常见的困境是过程不透明。作者说，很多时候当人们在建立这些 Agent、让它们做研究或使用工具时，会感到「完全黑了」，因为没有理解什么正在发生（2:19–2:26）。要明白这一点，关键在于每一次过程都要能看到细节——你应该能看到正确的每一步，像是 Trek 和 Waku Memory 在其中做了什么（2:29–2:39）。

这一节的演示就是先把「黑盒」变成可逐条查看的记录，再谈怎么判定好坏。

### Agent Harness 与两个工具（0:30）

整个链路是从 Agent Harness 开始，一直到 Evals 和 Agent Observability 的确诊（0:19–0:30）。演示里用了两个主要工具。

```
Agent Harness        链路终点是 Evals 与 Agent Observability 的确诊 (0:19–0:30)
   │
   ├─ 提问           先查 Waku Memory 里是否已有这条信息 (1:15)
   ├─ 调工具         Trek 开放路由器 → tinyfish.web.search (1:24)
   ├─ 出报告         执行 / 费用 / 查看 / 计算，横向比较若干平台 (1:56)
   ├─ Observability  相机：看每一步的成败、工具、记忆来源、花费 (3:23)
   └─ Evals          裁判：判这个过程是好还是不好 (3:45)
```

- **Trek：Agent 工具的开放路由器。** 用它来运行 Agent 所要的工具，让它能够做研究（0:32–0:41）。它的价值在于接入成本：你的 Agent 只需要用一条 API 键，就能使用所有 Trek 的工具；作者说他相信他们有超过 3800 个 endpoint 和 108 个供应商（1:32–1:41）。
- **Waku Memory：跟着 Harness 走的记忆。** 它会跟随你使用的任何 Agent Harness，让你的团队和你自己的 Agent 永远不会失去这个识别（0:43–0:52）。具体形态是：按进 Waku.1 的确认器，会开启 Waku Agent Checker，在右边的聊天中，主要标题是「记忆」（0:54–1:02）。

> **我的理解**
>
> 两者的分工很清楚：Trek 解决的是「Agent 能调什么外部能力」，Waku Memory 解决的是「Agent 记不记得住、跨不跨 Harness」。前者是能力边界，后者是上下文边界，正好对应后面要拆的成本指标与记忆指标。

### 一次任务是怎么跑起来的（1:02）

作者给的任务是：研究 Agent Observability 的 AI 工具，给出一个完善的分析——市场上有什么功能、需要什么改善、市场的缺点（1:02–1:14）。按「传」之后，执行的顺序本身就是可观测性的一部分。

1. 首先检查这个信息是否已经存在于 Waku Memory 中（1:15–1:18）。
2. 然后开始启动 Trek 的工具，开始调用研究器（1:19–1:22）。
3. 整个研究过程一直使用从 Trek 拿到的 endpoint，这次用的是 `tinyfish.web.search`（1:24–1:29）。
4. 报告生成后可以打开数据让它更清楚，按「开报告」会看到整份报告，里面提供了一些发现（1:42–1:56）。报告里涉及执行、费用、查看、计算这些维度，并把若干平台做了比较：LangFuse、Arise、Phoenix、Langsmith、BrainTrust、Helicom、Promptful，还包括价格和所有的资源（1:56–2:13）。

### Observability 是什么（3:19）

观察能力本质上是一个相机，它会查询它所看到的什么情况（3:23–3:28）。它盯住的不是最终答案，而是过程，包括：某一步是失败了还是赢了、用过什么工具、从哪里取得了记忆，以及它在模型运行或工具运行上花了多少钱（3:29–3:40）。所以作者的说法是：这是一个相机，它会监视正确的行动（3:41–3:44）。

> **老师原话（3:23）**
>
> 观察能力基本上就是一个相机，它会查询它所看到的什么情况

### 成本：Agent 在花钱，你见得到吗（3:00）

作者用一个很简单的问题切入：「你的代理人在花钱，你见到吗？」（3:00–3:03）。在 Waku 的界面最底端，可以看到每个步骤、每个被使用功能的费用（3:04–3:10）。这次的实际账单结构是：他从 Trek 用了一些免费的工具，没有花他任何钱；记忆是花钱的；最贵的是 Claude Sonnet，为了这些研究花了 29 元（3:10–3:18）。

> **这一节真正要记住的是**
>
> 成本不是一个总数，而是能按步骤、按被使用的功能拆开的明细。正因为能拆开，才能分辨出「工具免费、记忆花钱、模型最贵」这种结构，也才知道钱具体花在哪一环。

### Evals 是什么（3:45）

Evals 是一个相当不同的东西（3:45–3:47）。它像是一个选手、像是一个判决（3:50–3:53）。做判决的可以是人工智能，也可以是一个真人，或者是一个定位性的数据，比如 CI 的 GitHub 计算程（3:54–4:02）。但它的目的是判决这个过程是好还是不好，并且它可以预先做一些测试（4:03–4:10）。

至于起点，作者说通常会用某种 harness 固定下来——例如他们刚才是用 Waku 开始的，但你肯定也可以从 Claude Code、Codex、Cursor 开始（4:11–4:20）。

> **老师原话（4:03）**
>
> 它的目的是要判决如果计算程是好还是不好

### Tracing：一次提问从开始到结尾（4:22）

当你问一个问题，比如「市场上关于观测和 Evals 的流行工具有哪些」，它会经过一条从头到尾的记录，这条记录监控你问一个问题从开始到结尾（4:24–4:42）。在这条记录里，前面它可能会给你计算预算，然后它会记录费用，就像是水费——因为每个调用会通过一个 meter（4:43–4:50）。这也是为什么前面那些「某一步是否失败、用了什么工具、花了多少钱」能被逐条看到。

### 三个主要指标（4:52）

作者说应该想到的三个主要标志是：模型调用、工具调用、记忆。

- **模型调用：** 你花多少钱用这个模型调用（4:54–4:58）。
- **工具调用：** 你让你的 Agent 使用一些 API、使用一些 MCP。前面问 Trek 做研究，用的就是 Trek 的研究工具；你也可以用 Gmail、Google Calendar、你的 Node 工具比如 Notion，或者你的 CRM（如果你在经营商务）（4:59–5:17）。
- **记忆：** 这是相当不同的一个东西（5:29–5:30）。

关键的区分在于：模型调用和工具调用是相似的，因为它们是「通过一个很相似的门」，都是 API——你要么用模型的 API，要么用工具的 API，用的都是外部的东西（5:18–5:28）。而记忆是一个共同的脑，你的整个脑都会使用它，每个工具都会使用同样的记忆，如果你在同一种的环境（5:31–5:36）。

### 记忆：本地与网络（5:37）

记忆有两种放法。一种是本地记忆，比如 Hermes、Claude Code，它们都会使用本地的文件来存放你的记忆（5:37–5:45）。另一种是网络记忆，这些网络记忆会把你的行为、用途以及一些你认识的事……（视频里没有展开）。它带来的效果是：你去到你的 Hermes，你都会记得它们（5:46–5:57）。

### 验证记忆：问它「你记得什么」（5:58）

验证方式很直接。打开 Claude Code，进到 MCP，你会看到我们和 Waku 联系；如果看 Tools，可以看到我们有所有的记忆 Tools（5:58–6:08）。然后问它：「你记得什么？在市场上有什么观察能力和什么 Trek Tools、你用的记忆 Tools 来做这个研究？」（6:08–6:21）

它的回答是：我们使用 Trek Tools 的结果叫做 `tinyfish.web.search`，这是对的；而且你还记得它们找到的平台——LangFuse、Iris Phoenix、Landsmith、BrainTrust、Helicon、Promptful（6:29–6:44）。作者由此说，那就是记忆的称号（6:44）。

> **我的理解**
>
> 这一段的意义不只在于「记忆能用」，而在于记忆的内容是可被追问、可被核对的：它复述出的 endpoint 名字和平台清单，正好可以和前面 1:24 那次工具调用、1:56 那份报告对上。这也是为什么作者把它放在观察性演示的后面——记忆是另一个需要被观察的对象。

## 可操作步骤

1. **接入 Waku：** 按进 Waku.1 的确认器，开启 Waku Agent Checker，右边的聊天标题是「记忆」（0:54）。
2. **下任务：** 让它研究 Agent Observability 的 AI 工具，给出市场上有什么功能、需要什么改善、市场的缺点（1:02）。
3. **看它先查记忆：** 检查这个信息是否已经存在于 Waku Memory 中（1:15）。
4. **看它调工具：** 启动 Trek 的工具，这次调用的 endpoint 是 `tinyfish.web.search`（1:20）。
5. **看报告：** 按「开报告」打开整份报告，打开数据让它更清楚（1:42）。
6. **看成本：** 在界面最底端查每个步骤、每个被使用功能的费用（3:04）。
7. **在 Claude Code 里验证记忆：** 进 MCP 看到和 Waku 的联系，进 Tools 看到所有记忆 Tools（5:58）。
8. **用问题验证记忆：** 问「你记得什么？在市场上有什么观察能力和什么 Trek Tools、你用的记忆 Tools 来做这个研究？」（6:08）。

## 常见坑 / 反直觉点

- **最大的坑是看不见。** 让 Agent 做研究、用工具时，人很容易「感到完全黑了」，因为完全没理解什么正在发生（2:19–2:26）。这不是 Agent 的问题，是缺观察能力。
- **记忆不能按 API 调用的方式理解。** 模型调用和工具调用都是外部的 API，走的是相似的门；记忆是同一个脑，同一种环境下每个工具共用同一份记忆（5:18–5:36）。把它归到「一次调用」里去算，会看错结构。
- **免费不等于没有记录。** 作者从 Trek 用的免费工具没有花他任何钱，但这些调用仍然出现在明细里（3:10–3:13）。
- **Evals 的裁判不一定是 AI。** 可以是人工智能、真人，或者定位性的数据，比如 CI 的 GitHub 计算程（3:54–4:02）。
- **成本要看结构，不要看总数。** 这次研究里工具免费、记忆花钱、Claude Sonnet 花了 29 元（3:10–3:18），三者分开才看得出钱花在哪。

> **前提条件**
>
> 这套演示依赖两个外部件：Trek 提供工具端点，Waku Memory 提供跨 Harness 的记忆（0:30–0:52）。作者说这两个概念本身「并不是很复杂」（0:11），但对工具的具体选择没有做对比评测——视频里没有展开这一点。
