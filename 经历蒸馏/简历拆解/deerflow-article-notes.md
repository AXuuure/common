## 1. 项目定位

DeerFlow 基于 LangChain / LangGraph 搭建，但与 LangChain 的区别是**完成度**：LangChain 只是一个 Agent 框架，DeerFlow 是一个成熟产品，可以直接拿来用。

它专注 **Long-Horizon Agent**——需要经过很多相互依赖步骤才能完成的长程任务。"时间长"只是表象，核心是**前后步骤相互依赖**。

1.0 的原始目标很窄：把"联网查资料 → 分析 → 生成研究报告"做成一套可部署、可修改的开源系统。2.0 的方向是社区使用推出来的：开发者拿它做数据流水线、演示文稿、看板、内容自动化，超出最初的研究用途，于是团队重写系统，把文件、记忆、Skill、沙箱和子 Agent 组织成**通用任务执行环境**。

> 作者观点：不推荐完全从 0 到 1 自己搭一个 Agent，最好用开源框架或成熟框架起步，效果更好。

## 2. 1.0 的四块地基

### 2.1 AIO Sandbox：为什么研究型 Agent 一定要有沙箱

因为 AI 会自己写程序，而程序可能有错。让 AI"分析这份 Excel、运行 Python、生成销量图"，执行过程就该被关进容器：

```
你的电脑或业务服务器
  │
  ├─ 创建一个临时容器
  │    ├─ 放入 Excel 的副本
  │    ├─ 配好 Python 和需要的库
  │    └─ 限制可访问的文件、网络、CPU 和内存
  │
  ├─ AI 写的 Python 在容器里执行
  │    └─ 读取 Excel → 分析数据 → 生成图片
  │
  └─ 取出图片，销毁临时容器
```

关键边界：**只有执行 Python 的那一步进入容器**，大模型和 Agent 调度程序留在容器外，通过接口发送任务、接收结果。沙箱主要在程序出错时起作用——错误被限制在容器内，宿主文件与凭证不越界。

### 2.2 可插拔的 Skill 体系

把一项任务的操作方法做成独立技能包，需要时加入、启用，不需要时停用或移除。模型先看目录，需要时才读正文。

### 2.3 跨会话长期记忆（DeerMem + 自动记忆）

默认模式可以理解为**有两个 AI**：

```
回答你的 AI   ：负责这一次回答
记笔记的 AI   ：负责分析哪些内容值得以后记住
      ↓ 通过检查后
写入该用户的持久文件 memory.json
```

每条记忆除内容外还带 ID、类别、置信度、来源会话、创建与更新时间；用户摘要与各 Agent 的具体事实分开存储。文件写入成功后，关闭会话甚至重启服务，只要持久存储还在，这条记忆就还在。

### 2.4 动态 Sub-agent 调度

预先配置好可用助手的角色、工具和模型；主 Agent 通过 `task` 工具委派任务，程序限制子助手数量、执行时间和轮次；通过线程池并发，有依赖关系还要形成 DAG。主 Agent 在运行时才决定调用谁、交给它什么任务。

## 3. 系统性 Context Engineering

**Context = 模型这一次调用能看到的全部材料**：任务说明、聊天历史、记忆、检索结果、工具返回。上下文窗口有限，DeerFlow 用几种机制整理它。作者的类比是**一个研究团队**：文件柜保存材料，桌面只放需要的内容，旧讨论整理成摘要，分工人员各有自己的讨论记录。

| 动作 | 团队类比 | 机制 |
|---|---|---|
| **Write** | 材料归档进文件柜 | 工具返回的大文本由 `ToolOutputBudgetMiddleware` 自动保存；AI 自己整理的研究笔记需主动调 `write_file`。后续要核对细节，模型用 `read_file` 取原文 |
| **Select** | 桌面只放当前要用的 | `format_memory_for_injection()` 整理用户摘要与记忆事实，算 token 用量、排优先级，按预算选择能放下的内容；默认主预算 **2,000 token**，纠错类记忆有专门保护额度 |
| **Compress** | 旧讨论整理成摘要 | 历史达到压缩阈值就整理成短摘要（官方示例：达 **32,000 token** 触发，保留最近 **10 条**消息）；移除旧消息前交给记忆模块后台异步提炼长期信息 |
| **Isolate** | 分工者各有讨论记录 | Sub-agent 默认不带主 Agent 的全部聊天历史，只拿任务描述 + 自己的角色、规则和工具；完成后回传关键结论、来源与成果路径；沙箱按 `thread_id` 隔离，同会话内子助手通常复用父任务沙箱与目录 |

token 不够导致关键信息没加载进来怎么办？作者的答复是工程手段：拆小任务、排除其他信息、再压缩。

**"每轮注入"的准确含义**：不是模型自己回头看，而是 `DurableContextMiddleware` 在每次模型调用前，从任务状态里取出历史摘要、子任务交付记录、已加载 Skill 的引用，整理成精简提醒——让模型知道做到哪里、哪些结果可用、哪些说明书读过。

**异步提炼的代价**：记忆在后台写入，下一次请求来得太快时，这条记忆可能还没保存完成。

## 4. "可处理多层级 long-horizon 任务"怎么落地

用"整理三款游戏的新手攻略，比较入门难度，生成一份带来源的报告"举例。DeerFlow 靠的是**分阶段计划 + 多轮执行 + 保存中间成果 + 整理上下文 + 检查完成条件**，作者类比：像一个项目负责人，带着任务清单和工作文件，做完一步再决定下一步。

### ① 拆阶段，用清单跟踪进度

启用计划模式后提供 `write_todos` 工具，让模型建立和更新任务清单：

```
总目标：完成游戏入门对比报告

阶段一：收集资料      - 查游戏 A  - 查游戏 B  - 查游戏 C
阶段二：整理比较      - 提取基础操作、养成要求、上手难点；比较三款游戏
阶段三：交付          - 写报告；检查来源与遗漏
```

发现资料不够时，模型可以修改计划、增加调查步骤。**这张清单主要用于跟踪工作，不是一张自动保证所有依赖正确的任务图**。

### ② 每一步反复"看结果，再行动"

底层是 LangChain / LangGraph 的 Agent 执行循环（文章给的示意，非 DeerFlow 原码）：

```python
while 未结束且未超过执行限制:
    下一步 = 模型判断(任务、当前状态、已有结果)
    if 下一步需要工具:
        结果 = 执行工具(下一步)
        把结果加入当前状态      # 下一轮模型看到结果，再决定继续查、处理或交付
    else:
        返回最终回答
        break
```

例如查到游戏 A 的攻略已过期，模型看到检索结果后可以继续找新版资料。子助手也有自己的模型与工具循环，因此一次委派能包含多个具体步骤。

### ③ 主助手分批调度子助手，逐阶段收回成果

三款游戏的资料收集相互独立，可以并行：

```
主助手
  ├─ 子助手 A：调查游戏 A → 返回结论和证据
  ├─ 子助手 B：调查游戏 B → 返回结论和证据
  └─ 子助手 C：调查游戏 C → 返回结论和证据
主助手收齐结果 → 比较入门难度 → 写报告 → 核对遗漏
```

**"多层级"的边界**：可以是 总目标 → 阶段 → 具体步骤；但当前内置通用子助手明确禁止再调 `task` 派子助手，所以默认实现**不是**无限递归的"助手套助手"。

### ④ 中间成果放文件，长历史压成摘要

```
工作目录/                 # 示例
├── game-a-notes.md
├── game-b-notes.md
├── game-c-notes.md
├── comparison.md
└── final-report.md
```

模型继续工作时用任务清单、摘要、近期消息和必要文件；需要核对细节再 `read_file` 读原文，避免上下文越堆越大。

另有一个**默认关闭**的 `task_continuity` 增强：开启后可用任务笔记保存约束和下一步，并搜索、读取压缩归档的历史原文——即"AI 自己决定要不要去看没被压缩的历史"。它服务于继续当前任务，与跨会话的长期用户偏好记忆分开管理。

### ⑤ 检查目标是否完成，并限制无效循环

用 `/goal` 设置完成条件后，一次执行结束时由**另一个评估模型**检查可见结果；符合条件但目标尚未完成时，系统可自动发起继续执行。遇到缺少用户输入、外部等待、执行失败或持续无进展会停止自动推进，同时有次数上限。

## 5. 2.0 的四个升级

### 5.1 Agent Teams Harness

按简历描述，可以把 DeerFlow 2.0 想成"一个组长带几个临时助手干活"：

```
玩家：比较三款游戏，写一份报告
                 ↓
          Lead Agent 组长
          准备资料、决定分工
                 ↓ task
       ┌─────────┼─────────┐
    助手 A     助手 B     助手 C
    查游戏 A   查游戏 B   查游戏 C
       └─────────┼─────────┘
          共用目录和沙箱
          进度 → 前端
          结论 → 组长
                 ↓
          核对、补查、写报告
```

1. 从流水线变成组长决策：1.0 像必须依次经过五个工位的流水线（说白了就是 Agent workflow），2.0 由 Lead Agent 根据问题决定直接回答、查资料还是派助手，看到结果后还能调整下一步。依托的是计划模式和 Agent Loop。
2. `system_prompt` 动态写入——按当前启用的 skill 列表、跨会话持久化记忆、sub-agent 并发规则组装。即提示词按 skill 按需加载，加载持久化记忆，同时告知子 agent 并发个数有限。
3. Lead Agent 通过 `task` 派活：`subagentExecutor` 为每个子助手建立独立 Agent 执行实例，"调度池"与"执行池"分别负责安排工作与实际干活；简历中的配置是**最多 3 并发、单任务超 900 秒超时**。
4. sub-agent 继承父线程目录 + 复用父沙箱：每个子助手有自己的对话上下文，但沿用父任务目录和沙箱，所以能读取同一批上传文件。
5. 每步实时推流至前端：保存调查成果并把执行进度实时展示。作者点评——这体现她知道怎么监控和评测 Agent 的执行效果，而这个能力目前是 Agent 最重要的能力之一。
6. 完成后压缩摘要回传 lead agent：子助手返回关键结论、来源和文件路径等摘要，主助手据此补查、汇总或生成最终报告，整个任务可经历多轮"派活 → 收结果 → 调整 → 继续"。

### 5.2 Middleware Chain

1.0 的问题是职责混在一起：聊天代码里管沙箱，工具代码里管压缩，回答代码里管记忆，改一个能力容易牵动好几处。2.0 抽成 11 层有序流水线，新增或修改能力只动对应层，Agent 推理代码零改动。

作者认为这套描述总结起来就两个思想：**把可复用的场景和流程抽象成组件**；**用 AOP 的思想，在 Agent 执行过程中插入这些过程**。

| # | 层 | 管什么 |
|---|---|---|
| 1 | ThreadData | 会话线程的数据准备 |
| 2 | Uploads | 上传文件接入 |
| 3 | Sandbox | 沙箱准备与执行 |
| 4 | DanglingToolCall | 处理悬空的工具调用 |
| 5 | Summarization | 历史压缩 |
| 6 | Todo | 任务清单 |
| 7 | Title | 标题生成 |
| 8 | Memory | 记忆读写 |
| 9 | ViewImage | 图片查看 |
| 10 | SubagentLimit | 子 Agent 并发/轮次限制 |
| 11 | Clarification | 向用户澄清 |

> 简历原文里这几层名有拼写偏差（TreadData、Sandboxs、Clarfication），上表按规范拼写整理。各层的具体职责描述以简历口径为准，逐层细节需回源码核对。

**"有序流水线"的准确理解**：不代表每次推理前都完整执行 11 件事。组件各自在**执行前、模型调用前后、工具调用时、执行结束后**接入自己的处理逻辑——例如沙箱在工具执行前准备，记忆更新在任务结束后触发。

### 5.3 Skill System

每个 Skill 是一个目录，内含 `SKILL.md`；`system_prompt` 只注入索引，Agent 按需 `read_file` 渐进加载，避免全量注入导致 token 爆炸。模型先看目录，需要时才读正文。支持自定义 skill：`custom/` 下新增目录即可，框架会发现新的 Skill 包。

### 5.4 Context Engineering

即第 3 节的 Write / Select / Compress / Isolate 四动作，在 2.0 被写成一组明确规则（Write 落盘 + 每轮注入索引；Select 按 token 预算裁剪；Compress 超限压历史 + 异步提炼持久记忆；Isolate 子 Agent 只见任务描述、沙箱按 thread_id 隔离）。

## 6. 其他概念澄清

| 术语 | 含义 |
|---|---|
| **ReAct 风格子 Agent** | "先判断下一步做什么 → 调用工具 → 看结果 → 再调整下一步"。ReAct 来自 Reasoning（推理）+ Acting（行动） |
| **Meta Prompt** | 写 Prompt 的规范，要说清楚目标与约束。OpenAI 和 Anthropic 都有自己的 Meta Prompt；简历称 1.0 的 Prompt 由 OpenAI Meta Prompt 生成 |
| **Agent workflow** | 1.0 那种"必须依次经过固定节点"的编排方式，与 2.0 的组长动态决策相对 |

## 7. 这份拆解里最值得带走的三条

1. **长程任务的瓶颈是上下文组织，不是模型能力**。五步里真正难的是"中间成果落文件 + 长历史压摘要 + 每轮重新准备便签"这三件工程事，`write_todos` 只是跟踪，不保证依赖正确。
2. **子 Agent 的价值首先是隔离，其次才是并行**。默认禁止子助手再派子助手，说明"无限递归"在生产上不是想要的性质；隔离上下文（Isolate）才是委派的主要动机。
3. **可观测与评测正在变成一等公民**。2.0 把"每步实时推流至前端"写进架构，而简历另一段（Agent Tracer / Rubric / Failure Onset）把同一件事做到了训练数据层面——这两处的呼应是这份简历最强的信号，见 [简历逐段解析 §4.2](resume-breakdown.md)。
